# 12.8 README와 제출 패키징

::: lead
과제를 다 짜고 나면 보통 30분이 남는다. 그 30분을 코드에 더 쓰는 사람과 README에 쓰는 사람의 점수가 갈린다. 평가자는 저장소를 열고 **README부터 연다.** 거기서 실행 명령을 못 찾으면 코드는 읽히지 않고, 실행 명령을 찾았는데 안 돌아가면 나머지가 전부 무효가 된다. 이 절은 무엇을 만들었는지 자랑하는 문서가 아니라 **평가자가 5분 안에 당신의 프로그램을 돌리고 당신의 판단을 읽게 만드는 절차서**를 쓰는 법이다. 그리고 그 절차서가 실제로 돌아가는지 **직접 리허설하는 법**까지 간다.
:::

## 평가자는 README를 읽지 않는다 — 실행한다

[12.1](#/takehome-eval)에서 채점자가 첫 5분에 하는 일이 셋이라고 했다. README를 열고, 파일 트리를 훑고, 테스트를 돌린다. 그 5분 동안 평가자의 머릿속에 도는 것은 감상이 아니라 다음 다섯 개의 질문이다.

```text nolines
  Q1  무엇을 만들었나    -> 첫 세 줄로 안다. 못 알아내면 코드를 읽어야 한다
  Q2  어떻게 돌리나      -> 복사할 명령이 있나. 붙여넣으면 도나
  Q3  어떻게 검증하나    -> 테스트 명령이 있나. 실제로 통과하나
  Q4  왜 이렇게 짰나     -> 다르게 할 수 있었던 지점을 알고 있었나
  Q5  뭘 못 했나         -> 자기 코드의 구멍을 아는 사람인가
```

Q1~Q3은 **탈락 필터**다. 못 넘으면 그 아래를 안 본다. Q4~Q5는 **가점 항목**이다. 여기서 같이 일할 수 있는 사람인지가 갈린다. 그래서 README는 이 순서대로 쓴다. 순서를 바꾸면 안 된다. 설계 자랑을 맨 위에 두면 평가자는 실행 명령을 찾느라 스크롤을 내리고, 스크롤을 내리는 동안 인상이 나빠진다.

같은 프로젝트에 붙은 두 개의 README 첫 화면을 비교해 보자. 먼저 A다.

```text nolines
# inventory-task

## Architecture
Clean Architecture 를 적용하여 도메인 계층과 인프라 계층을 분리했습니다.
의존성 역전 원칙에 따라 저장소는 인터페이스로 추상화되어 있으며 ...
```

그리고 B다.

```text nolines
# Stockroom - 창고 재고 정산 CLI

입출고 기록 CSV 를 읽어 재고를 계산하고 재주문 대상을 리포트로 낸다.

## 1. 실행
    python -m stockroom data/items.csv data/movements.csv
```

A를 여기까지 읽은 평가자는 **아직 아무것도 실행하지 못했다.** 이 프로그램이 무엇을 입력받아 무엇을 내는지도 모른다. B는 세 번째 줄에서 목적이 끝났고 여섯 번째 줄에 복사할 명령이 있다. 아키텍처 이야기는 B에도 있다 — 다음 절에서 볼 다섯 칸 중 **네 번째 칸인 설계 결정**에(뒤에 나올 README 전문에서는 5번 항목이다). **읽히려면 실행부터 통과해야 한다.**

::: warn 도구가 만들어 준 README 를 그대로 두지 마라
`# project-name` 한 줄, 또는 프레임워크 스캐폴딩이 남긴 "Getting Started" 문단. 둘 다 **아무도 안 읽은 문서**라는 신호로 읽힌다. 4시간짜리 과제에서 README를 손대지 않았다는 것은 제출 직전 점검을 안 했다는 뜻이고, 평가자는 그 추론을 코드에도 적용한다.
:::

## README의 다섯 칸

칸은 다섯 개면 충분하다. 각 칸이 평가자의 어떤 행동을 대신하는지 못 박아 둔다.

| 칸 | 평가자가 이걸로 하는 일 | 없으면 |
| --- | --- | --- |
| **무엇을 만들었나** | 3줄 안에 도메인과 입출력을 파악한다 | 코드에서 역추적한다. 인상이 나빠진다 |
| **실행** | 명령을 복사해 붙인다 | 진입점을 찾아 헤맨다. 여기서 탈락자가 가장 많다 |
| **테스트** | 명령을 복사해 붙인다 | "테스트가 있다"는 주장이 검증되지 않는다 |
| **설계 결정** | 대안을 알고 골랐는지 본다 | 우연히 그렇게 짠 것과 구별되지 않는다 |
| **알려진 한계** | 자기 코드의 구멍을 아는지 본다 | 못 한 것이 **못 본 것**으로 읽힌다 |

여기에 하나를 더 붙이면 좋다. [12.1](#/takehome-eval)과 [12.6](#/test-strategy)에서 만든 **요구사항 → 코드 → 테스트 역추적 표**다. 이 표는 새로 쓰는 것이 아니라 이미 있는 것을 옮기는 것이라 3분이면 끝나는데, 평가자가 명세 충족 여부를 코드를 열기 전에 확인하게 해 준다.

::: tip 다섯 칸에 없는 것은 안 쓴다
"기술 스택", "폴더 구조 설명", "설치 가이드", "향후 계획 v2.0". 과제형에서 이 넷은 전부 빼도 된다. 폴더 구조는 트리 다섯 줄로 충분하고([12.7](#/project-structure)), 기술 스택은 "표준 라이브러리만 씀" 한 줄이면 끝난다. 남는 시간을 **설계 결정** 칸에 써라. 거기가 유일하게 코드로 대체 불가능한 칸이다.
:::

## 실행 절차는 복사해서 붙이면 돌아가야 한다

실행 칸에는 규칙이 셋 있다.

**① 한 덩어리로 복사되게 쓴다.** 명령 사이에 설명 문장을 끼우지 마라. 평가자는 블록을 드래그해서 붙여넣는다.

**② 어디서 실행하는지 밝힌다.** 대부분의 과제는 프로젝트 루트를 전제한다. 그 전제가 깨지면 이렇게 된다.

```pyrepl
>>> import importlib
>>> importlib.import_module("stockroom")
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    importlib.import_module("stockroom")
    ~~~~~~~~~~~~~~~~~~~~~~~^^^^^^^^^^^^^
  ... (생략)
ModuleNotFoundError: No module named 'stockroom'
```

셸에서도 같다. 루트가 아닌 곳에서 `python -m stockroom` 을 치면 `No module named stockroom` 이 나온다. 이유는 [1.19 import 시스템](#/imports)에 있다 — 인터프리터를 띄운 디렉터리가 `sys.path` 에 들어가기 때문이다. 평가자가 이 메시지를 보면 **당신 코드가 깨진 줄 안다.**

**③ 샘플 데이터를 저장소에 넣는다.** "적당한 CSV를 만들어서 넣으세요"는 평가자에게 숙제를 내는 것이다. `data/` 에 파일 두 개를 커밋해 두면 실행 칸이 한 줄로 끝난다.

### 두 가지 실행 방식 — 무엇을 고를 것인가

과제형에서 실행 방식은 크게 둘로 갈린다.

| | **안 A — 의존성 0, `python -m`** | **안 B — `pyproject.toml` + 설치** |
| --- | --- | --- |
| 평가자가 치는 명령 | 1개 | 3~4개(가상환경, 설치, 실행) |
| 실패 지점 | 파이썬 버전뿐 | 버전, 네트워크, 빌드 백엔드, 권한 |
| 얻는 것 | 즉시 실행 | 콘솔 스크립트, 어디서나 실행, src 레이아웃 |
| 어울리는 과제 | 표준 라이브러리로 되는 4~8시간 과제 | 서드파티가 꼭 필요하거나 배포까지 요구된 과제 |

**요구사항에 라이브러리 지정이 없다면 안 A를 골라라.** 실행 실패는 과제형에서 가장 흔한 탈락 사유이고([12.1](#/takehome-eval)), 안 B는 실패할 수 있는 지점을 셋 더 만든다. 패키징 자체는 [6.5](#/packaging)에서 다뤘다 — 거기서 배운 것을 **여기서 안 쓰는 것이 판단력**이다.

::: danger 파이썬 버전을 적었으면 그 버전에서 실제로 돌려 봤어야 한다
README에 "Python 3.9+" 라고 적어 놓고 3.14에서만 개발한 제출물은 놀랄 만큼 많다. 평가자의 손에는 다른 버전이 있다.

```python title="pager.py"
from itertools import batched

def pages(rows, size=2):
    return [list(b) for b in batched(rows, size)]

print(pages(["a", "b", "c"]))
```

같은 파일, 두 개의 인터프리터.

```text nolines
$ python3.11 pager.py
Traceback (most recent call last):
  ... (생략)
ImportError: cannot import name 'batched' from 'itertools' (unknown location)

$ python3.14 pager.py
[['a', 'b'], ['c']]
```

`itertools.batched` 는 3.12에, `tomllib` 는 3.11에, `type` 문([2.3](#/pep695))은 3.12에 들어왔다. **적을 버전을 정하는 방법은 하나뿐이다 — 그 버전으로 실제로 돌려 보고 적는다.** 못 돌려 보겠으면 "3.14에서 개발·검증했다"라고 사실만 적어라. 검증 안 한 하한선보다 검증한 한 줄이 낫다.
:::

::: warn 종료 코드가 0이 아닌 정상 경로가 있으면 반드시 적어라
아래 예제의 CLI는 거부된 이동이 하나라도 있으면 `1` 로 끝난다. 설계상 맞다. 그런데 이 사실을 안 적으면 평가자의 셸에서, 그리고 CI 스크립트([6.6](#/ci))에서 **정상 동작이 실패로 읽힌다.** 실행 명령 바로 밑에 종료 코드 한 줄을 붙이는 것이 비용의 전부다.
:::

## 어떤 결정을 왜 했는가

이 칸이 이 절의 핵심이다. 왜 특히 높게 평가되는가에는 구조적인 이유가 있다.

> **코드는 결과만 보여준다. 대안은 안 보여준다.**

`Inventory` 가 수량을 누적하고 있는 코드를 보면 평가자는 "이렇게 짰구나"까지만 안다. 이 사람이 **이동 기록을 매번 다시 접는 방식을 고려했다가 버린 것인지**, 아니면 **다른 방식이 있다는 생각 자체를 안 한 것인지** 코드로는 구별되지 않는다. 그 구별을 만드는 것이 이 칸이다. 그리고 실무에서 같이 일할 때 실제로 필요한 능력이 정확히 그것이다.

한 항목은 네 조각으로 쓴다.

```text nolines
  결정   무엇을 그렇게 했는가            한 문장
  대안   무엇을 안 골랐는가              한 문장
  근거   왜 이 조건에서 이게 나은가       한두 문장
  변경점 조건이 바뀌면 어디를 고치는가    파일 이름까지
```

네 번째 조각이 있고 없고가 인상을 가른다. **"바뀌면 여기를 고친다"까지 적힌 결정은 확장성을 코드로 증명한 것과 같은 효과를 낸다.** 그러면서 지금 코드에는 안 쓰는 추상층이 하나도 안 늘어난다. [12.4](#/boundaries-di)에서 "포트를 만들지 말고 README에 한 줄 적어라"라고 한 것이 이 문장이다.

나쁜 예와 좋은 예를 나란히 놓는다.

```text nolines
# X  결정이 아니라 코드 요약이다
- Inventory 클래스에서 재고를 관리합니다.
- 예외는 StockError 를 상속받아 처리했습니다.
- 클린 아키텍처를 적용했습니다.
```

```text nolines
# O  대안과 근거와 변경점이 있다
**거부된 이동에서 멈추지 않고 끝까지 진행한다.**
명세에는 "재고보다 많이 출고할 수 없다"만 있고 중단 여부가 없다. 첫 오류에서
종료하는 안도 검토했지만, 하루치 파일에서 한 줄 때문에 리포트 전체를 못 받는
쪽이 손해가 크다고 판단했다. 대신 조용히 넘기지 않도록 REJECTED 목록과
종료 코드 1로 드러낸다. 즉시 중단이 맞다면 cli.apply_all 의 except 를
raise 로 바꾸는 것이 전부다.
```

아래쪽 문단은 여섯 줄이다. 위쪽 세 줄보다 정보량이 열 배다. 특히 **"클린 아키텍처를 적용했습니다"** 같은 문장은 쓰지 마라. 이름을 댔을 뿐 판단이 없고, 이름을 댄 순간 평가자는 그 이름의 정의대로 코드를 검사하기 시작한다. 스스로 불리한 채점표를 꺼내 주는 셈이다.

::: tip 안 만든 것도 결정이다 — 오히려 이쪽이 더 강하다
"저장소 계층을 만들지 않았다. 명세에 저장 요구가 없다. 필요해지면 `Inventory` 생성자로 주입한다." 이 세 문장이 안 쓰는 `Repository` 추상 클래스 세 개보다 높게 평가된다. YAGNI를 지켰다는 증거가 코드에는 **남지 않기 때문에**, 안 만든 것은 README에만 적을 수 있다([12.2](#/requirements-to-model)).
:::

::: warn 결정은 3~5개. 그 이상은 역효과다
모든 선택을 결정으로 승격시키면 진짜 결정이 묻힌다. 기준은 하나다 — **다르게 할 수 있었고, 다르게 했다면 코드 구조가 달라지는 것**만 적어라. 변수명을 `qty` 로 한 이유, `dataclass` 를 쓴 이유는 결정이 아니다. 열두 개짜리 결정 목록은 "무엇이 중요한지 모르는 사람"으로 읽힌다.
:::

::: note README 안에 쓸 것인가, `docs/DECISIONS.md` 로 뺄 것인가
- **README 안** — 평가자가 파일을 하나만 연다. 4~8시간 과제에서는 결정이 다섯 개를 안 넘으므로 README가 두 화면이면 끝난다.
- **별도 파일(ADR)** — 결정이 열 개를 넘고 각각에 배경 설명이 필요한 규모에서 의미가 있다. 대신 평가자가 그 파일을 안 열 위험이 있다.

**과제형에서는 README 안에 두는 쪽을 권한다.** 링크 한 번을 더 누르게 만드는 비용이, 문서가 잘 정리돼 보이는 이득보다 크다. 실무 저장소로 넘어가면 반대가 된다.
:::

## 알려진 한계와 남은 일

정직함이 점수가 되는 것은 **조건이 맞을 때만**이다. 조건은 셋이다.

**① 구체적이어야 한다.** "테스트가 부족합니다", "예외 처리가 미흡합니다"는 한계가 아니라 사과다. 평가자는 이미 그걸 안다. 정보가 없는 문장은 신뢰를 만들지 않는다.

**② 비용을 알아야 한다.** "CSV 헤더 검증 — 약 30분"처럼 걸릴 시간을 적으면, 못 한 것이 **판단이었다**는 것이 드러난다. 시간이 없어서 못 한 것과 할 줄 몰라서 못 한 것이 여기서 갈린다.

**③ 코드와 일치해야 한다.** 이게 가장 중요하다.

::: danger README와 코드가 어긋나면 README의 나머지 줄까지 못 믿을 것이 된다
"입력 검증은 하지 않았다"라고 적었는데 코드에 검증이 있으면, 평가자는 이 사람이 **자기 코드를 모른다**고 판단한다. 반대로 "모든 경계값을 테스트했다"라고 적었는데 테스트가 다섯 개면, 그건 과장이 아니라 **거짓말**로 읽힌다.

## README 전문 — 재고 정산 과제

이제 전체를 하나로 본다. 다음 요구사항으로 받은 과제다.

> **창고 재고 정산 CLI (제한 4시간)**
> ① 품목은 SKU, 이름, 재주문점(최소 재고)을 가진다. ② 입고와 출고를 기록한다. 재고보다 많이 출고할 수 없다. ③ 재주문점 미만인 품목을 목록으로 낸다. ④ 이동 기록은 CSV 파일로 들어온다. ⑤ 결과는 표준출력 리포트로 낸다.

눈치챘겠지만 [12.2](#/requirements-to-model)의 사내 비품 재고와 같은 도메인이다. 일부러 그렇게 했다. **12.2에서 모델링한 것을 CLI·CSV 판으로 이어 쓴다.** 요구사항 문장에서 명사와 동사를 뽑아 `Item` 과 `Inventory` 를 세우는 일은 거기서 이미 끝냈고, 이 절이 볼 것은 그 결과물을 **어떻게 넘겨주느냐**이기 때문이다. 소재를 새로 꺼내면 독자가 모델을 다시 읽느라 README에 집중하지 못한다. 달라진 것은 둘이다 — 입력이 사람 손이 아니라 CSV 파일이고, 입출고 이력 조회 대신 **리포트와 종료 코드**가 요구된다. 경계 설계가 주제였던 [12.4](#/boundaries-di)가 굳이 다른 소재(충전 스탠드)를 쓴 것과 반대 이유다. 거기서는 외부 시스템이 필요했고, 여기서는 이미 아는 도메인이 필요하다.

트리에서 설명이 필요한 것은 `conftest.py` 하나다. [12.1](#/takehome-eval)은 이 문제의 기본 해법으로 **`pyproject.toml` 의 `pythonpath = ["."]`** 를 권했고, [12.2](#/requirements-to-model)·[12.3](#/state-machine)·[12.7](#/project-structure)의 프로젝트는 전부 그쪽을 쓴다. 여기서는 설정 파일을 하나도 안 늘리려고 다른 안을 골랐다. 대신 12.1이 못 박은 조건을 지킨다 — **빈 파일로 두지 않는다.**

```python title="conftest.py — 파일 전체"
# tests/ 에서 프로젝트 루트를 import 할 수 있게 한다. 지우면 pytest 가 깨진다.
```

이 파일이 실제로 일하는 지점은 하나뿐이다. **평가자가 `pytest` 만 쳤을 때다.** `python -m pytest` 는 현재 디렉터리를 `sys.path` 에 넣어 주므로([1.19](#/imports)) `conftest.py` 가 없어도 그냥 통과한다. 그래서 아래 README의 테스트 칸도 `python -m pytest` 가 아니라 `pytest` 로 적었다. 평가자가 실제로 치는 명령이고, 그 명령에서만 이 파일의 유무가 드러나기 때문이다. 지워 보면 이렇게 된다.

```text nolines
$ rm conftest.py && pytest -q
ERROR tests/test_cli.py
ERROR tests/test_inventory.py
!!!!!!!!!!!!!!!!!!! Interrupted: 2 errors during collection !!!!!!!!!!!!!!!!!!!!
2 errors in 0.09s
```

같은 상태에서 `python -m pytest -q` 는 `11 passed` 로 통과한다. **두 명령의 결과가 다른 제출물은 실행되지 않는 제출물과 같은 취급을 받는다**([12.1](#/takehome-eval)). 아래가 이 저장소의 README 전문이다.

````text nolines
# Stockroom — 창고 재고 정산 CLI

입출고 기록 CSV를 읽어 품목별 재고를 계산하고, **재주문점 미만인 품목**과
**거부된 이동**을 리포트로 출력한다.

- Python 3.14 에서 개발·검증했다. 표준 라이브러리만 쓰므로 3.10 에서도 돌 것으로
  보지만, 3.10 으로는 돌려 보지 않았다.
- 실행에 필요한 외부 의존성이 없다. 테스트에만 `pytest` 가 필요하다.

## 1. 실행

```bash
python -m stockroom data/items.csv data/movements.csv
```

```text
STOCK LEVELS
  SKU-A    Bolt M6         90
  SKU-B    Nut M6          35
  SKU-C    Washer M6       15
  SKU-D    Spring 12mm     10

  line 7: SKU-C: 출고 20, 재고 15
  line 9: 등록되지 않은 품목: SKU-X
```

종료 코드는 `0` 전부 처리, `1` 거부된 이동이 있음, `2` 인자나 파일 오류다.

## 2. 테스트

```bash
python -m venv .venv && source .venv/bin/activate
pip install pytest
pytest -q
```

```text

```

## 3. 입력 형식

`items.csv` — 등록된 품목. 여기 없는 SKU의 이동은 거부된다.

```text
sku,name,reorder_point
SKU-A,Bolt M6,50
```

`movements.csv` — 위에서 아래 순서로 적용된다.

```text
sku,kind,qty
SKU-A,IN,120
SKU-A,OUT,30
```

## 4. 요구사항 대응

| 요구사항 | 구현 | 테스트 |
| --- | --- | --- |
| 품목은 SKU·이름·재주문점을 가진다 | `models.py` `Item` | `test_new_item_starts_at_zero` |
| 입고와 출고를 기록한다 | `Inventory.receive` / `.issue` | `test_receive_then_issue_updates_quantity` |
| 재고보다 많이 출고할 수 없다 | `Inventory.issue` | `test_issue_more_than_stock_is_rejected_and_leaves_stock_untouched` |
| 재주문점 미만 품목을 낸다 | `Inventory.below_reorder_point` | `test_item_at_reorder_point_is_not_listed` |
| 이동 기록은 CSV로 들어온다 | `feed.py` | `test_clean_run_returns_zero_and_prints_levels` |
| 결과는 표준출력 리포트 | `report.py` | `test_rejected_movement_returns_one_and_names_the_line` |

"재주문점과 같은 수량"은 명세에 없어서 **미만일 때만** 목록에 넣기로 정했고,
그 결정을 `test_item_at_reorder_point_is_not_listed` 로 고정했다.

## 5. 설계 결정

**① 재고를 수량 하나로 누적한다. 이동 기록을 매번 다시 접지 않는다.**
대안은 조회 때마다 `movements` 를 합산하는 것이다. 그런데 출고 초과 판정에는
"그 시점의 재고"가 필요해서 어차피 순서대로 접어야 한다. 누적이 규칙과 같은
모양이라 골랐다. 이동 이력 조회(감사 로그)가 요구되면 `Inventory` 가 적용된
이동을 함께 보관하면 된다 — `inventory.py` 한 파일만 바뀐다.

**② 거부된 이동에서 멈추지 않고 끝까지 진행한다.**
명세에는 "재고보다 많이 출고할 수 없다"만 있고 중단 여부가 없다. 하루치 파일에서
한 줄 때문에 리포트 전체를 못 받는 쪽이 손해가 크다고 판단했다. 대신 조용히 넘기지
않도록 `REJECTED` 목록과 종료 코드 `1` 로 드러낸다. 즉시 중단이 맞다면
`cli.apply_all` 의 `except` 를 `raise` 로 바꾸는 것이 전부다.

**③ 저장소(영속화) 계층을 만들지 않았다.**
명세에 저장 요구가 없다. 지금 만들면 구현이 하나뿐인 인터페이스가 생긴다.
파일이나 DB에 남겨야 할 때는 `Inventory` 생성자로 저장소를 주입하고
`receive`/`issue` 끝에서 기록한다.

**④ 리포트는 문자열을 만들어 돌려주고, 출력은 `cli.py` 만 한다.**
`report.render` 가 `print` 하지 않으므로 형식 검증이 문자열 비교로 끝난다.

## 6. 알려진 한계

- `items.csv` 에 같은 SKU가 두 번 나오면 **뒤엣것이 이긴다.** 검증하지 않는다.
- 수량은 정수만 다룬다. 무게·길이 단위 품목은 지원하지 않는다.
- CSV 헤더 이름이 다르면 `KeyError` 로 죽는다. 사용자용 메시지가 아니다.
- 입력을 전부 메모리에 읽는다. 수백만 행이면 스트리밍으로 바꿔야 한다.
- 리포트는 표준출력 고정이다. 기계가 읽을 형식은 없다.

## 7. 남은 일 (하려던 순서)

1. CSV 헤더 검증과 사용자용 오류 메시지 — 3번째 한계. 약 30분.
2. `--json` 출력 플래그 — 5번째 한계. `report.py` 에 함수 하나 추가. 약 20분.
3. 중복 SKU 정책 확정 — 명세를 되물어야 하는 항목이라 임의로 정하지 않았다.
````

**110줄, 2,915자다.** 스크롤 두 번이면 끝난다. 여기서 확인할 것 다섯 가지를 짚는다.

1. **실행 출력을 붙여 놓았다.** 평가자는 명령을 치기 전에 무엇이 나올지 안다. 그래서 결과가 다르면 즉시 알아챈다.
2. **거부 사례가 들어 있는 샘플 데이터를 골랐다.** `REJECTED (2)` 가 보이는 순간 예외 처리 요구사항이 구현돼 있다는 것이 증명된다. 깨끗하게만 도는 샘플은 절반만 보여준다.
3. **`SKU-D` 는 재고 10, 재주문점 10인데 목록에 없다.** 경계값 판단이 출력에 그대로 노출돼 있고, 4번 칸이 그 판단을 테스트 이름으로 못 박는다.
4. **결정 ③이 "안 만든 것"이다.** 저장소를 안 만든 이유와 필요해질 때 손댈 자리가 함께 있다.
5. **한계 3·5번이 남은 일 1·2번과 번호로 이어진다.** 두 목록이 하나의 계획으로 읽힌다.

## 제출 패키징 — 무엇을 넣고 무엇을 빼는가

README를 다 썼어도 제출물에 `__pycache__` 가 200개 들어 있으면 첫인상이 무너진다. 먼저 `.gitignore` 다.

```text nolines
__pycache__/
*.pyc
.venv/
.pytest_cache/
.coverage
.idea/
.vscode/
.DS_Store
```

이걸 안 두면 어떻게 되는지 실제로 세어 봤다. 위 프로젝트를 한 번 실행하고 테스트를 한 번 돌린 직후 `.gitignore` 없이 `git add -A` 를 하면 **25개 파일이 스테이징되고 그중 11개가 `__pycache__` 안의 `.pyc` 다.** 진짜 소스는 14개뿐이다. 평가자가 보는 파일 트리는 절반이 쓰레기다.

::: perf zip 으로 제출할 때 실제로 무슨 일이 벌어지는가
같은 프로젝트를 두 방식으로 묶었다. 개발 중이라 `.venv/` 와 캐시가 남아 있는 상태다. `.venv` 는 README에 적힌 대로 `python -m venv .venv` 로 만들고 `pip install pytest` 까지 한 것이다.

| 방법 | 크기 | `unzip -l` 항목 수 |
| --- | --- | --- |
| `zip -r submit.zip .` (폴더 통째로) | 56 MB | 2,492 |
| `git archive --format=zip HEAD -o submit.zip` | 8.3 KB | 18 (파일 15 + 디렉터리 3) |

(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다.)

**네 자릿수 차이다.** 그리고 56 MB의 정체가 중요하다. 프로젝트 폴더 전체가 디스크에서 17 MB인데 압축본이 그보다 세 배 넘게 큰 이유는 **`zip` 이 기본적으로 심볼릭 링크를 따라가기 때문**이다. `.venv/bin` 에는 같은 인터프리터를 가리키는 링크가 **넷** 있다 — `python`, `python3`, `python3.14`, 그리고 `𝜋thon` 이다. 마지막 것은 3.14의 `venv` 가 하나 더 만든다(`venv/__init__.py` 에 `if sys.version_info[:2] == (3, 14) ...: suffixes.append('𝜋thon')` 이 있다. 3.14에서만, 파일 시스템 인코딩이 UTF-8일 때만 생긴다). `zip` 은 이 30 MB짜리 실행 파일을 **네 번 복사해 넣었다** — 압축 전 합계가 122 MB다. 링크를 링크로 보존하려면 `zip -y` 를 써야 한다. 같은 폴더가 4.6 MB로 줄어든다.

`git archive` 는 저장소가 아는 파일만 담는다. 즉 `.gitignore` 를 제대로 썼다면 제출물도 자동으로 깨끗해진다. `git clean -ndx` 로 지워질 것을 미리 볼 수도 있다.

```bash
git clean -ndx
```

```text
Would remove .pytest_cache/
Would remove .venv/
Would remove __pycache__/
Would remove stockroom/__pycache__/
Would remove tests/__pycache__/
```
:::

| | **git 저장소(원격 링크 또는 번들)** | **zip 스냅샷** |
| --- | --- | --- |
| 평가자가 보는 것 | 코드 + 커밋 히스토리 | 코드만 |
| 장점 | 작업 순서와 리듬이 드러난다 | 받는 즉시 열린다. 실수할 여지가 적다 |
| 위험 | 커밋 하나에 전부 넣으면 오히려 감점 | 히스토리가 없어 과정을 못 보여준다 |

**과제 안내문이 정한 방식이 있으면 무조건 그것을 따른다.** 안내문에 없으면 git 저장소를 권한다. 커밋 히스토리는 공짜로 얻는 추가 증거다. 단 조건이 있다.

::: warn 히스토리를 꾸미지 마라
커밋을 예쁘게 만들려고 `git rebase -i` 로 다시 쓰거나, 반대로 `git commit -am "wip"` 를 40번 남기는 것 둘 다 좋지 않다. **의미 단위로 5~10개** 정도면 충분하다. "모델 추가", "출고 초과 거부 규칙", "CLI와 리포트", "README" 처럼 커밋 메시지가 작업 단위를 말하면 그걸로 끝이다. 히스토리는 평가 항목이 아니라 **보너스**다. 여기에 30분을 쓰느니 한계 목록을 다시 읽어라.
:::

::: danger 제출물에 절대 들어가면 안 되는 것
- `.env`, API 키, 토큰, 실제 계정 정보. **한 번 커밋되면 히스토리에 남는다.** `git rm` 으로 지워도 이전 커밋에서 그대로 보인다.
- 회사 이름이 박힌 과제 안내문 PDF, 내부 문서, 다른 지원자와 주고받은 것.
- 개인 절대 경로. `/Users/gildong/dev/...` 가 코드나 테스트에 박혀 있으면 평가자 기계에서 실패한다. 경로는 `tmp_path` 픽스처나 `__file__` 기준 상대 경로로([6.2](#/pytest-advanced)).

제출 직전에 `git log -p | grep -i -E "key|token|secret|password"` 를 한 번 돌려라. 30초다. `KeyError`, `dict.fromkeys` 같은 오탐이 섞여 나오니 걸린 줄은 눈으로 확인해라 — 오탐이 나온다는 것 자체가 검사가 돌았다는 증거다.
:::

## 마지막 5분 — 리허설

여기까지 다 했어도 마지막 한 가지가 남았다. **README에 적은 명령을 깨끗한 복제본에서 실제로 실행해 보는 것.** 자기 작업 디렉터리에서는 되는데 남의 기계에서 안 되는 이유는 거의 항상 셋 중 하나다. 커밋 안 한 파일, `.gitignore` 에 걸린 필수 파일, 그리고 이미 설치돼 있어서 안 보이던 의존성.

리허설은 자동화할 수 있다. README의 `bash` 블록을 뽑아서 그대로 돌리면 된다.

```bash title="rehearse.sh"
#!/usr/bin/env bash
# README 의 bash 블록을 순서대로 뽑아 깨끗한 복제본에서 실행한다.
work=$(mktemp -d)
git clone -q "$1" "$work/proj" && cd "$work/proj" || exit 9

python3 - > cmds.sh <<'PY'
import re, pathlib
md = pathlib.Path("README.md").read_text(encoding="utf-8")
for block in re.findall(r"```bash\n(.*?)```", md, re.S):
    print(block.strip())
PY

while IFS= read -r cmd; do
    [ -z "$cmd" ] && continue
    eval "$cmd" > out.txt 2>&1
    echo "[$?] $cmd"
done < cmds.sh
```

위 저장소에 돌린 실제 결과다.

```text nolines
[1] python -m stockroom data/items.csv data/movements.csv
[0] python -m venv .venv && source .venv/bin/activate
[0] pip install pytest
[0] pytest -q
```

**첫 줄의 `[1]` 이 이 리허설의 수확이다.** 버그가 아니다 — 샘플 데이터에 거부되는 이동이 있으니 설계대로 `1` 이다. 하지만 이 스크립트에 `set -e` 를 걸었다면 여기서 멈췄을 것이고, CI에 넣었다면 빨간불이 떴을 것이다. 그래서 README의 실행 칸 바로 밑에 세 가지 종료 코드를 적는 한 줄이 있어야 한다. **리허설은 "돌아가는가"만 확인하는 절차가 아니라, 평가자가 무엇을 오해할지 미리 보는 절차다.**

::: perf 잘 만든 제출물의 리허설은 1초 안에 끝난다
`git clone` → 실행 → 가상환경 생성 → `pytest` 설치 → 테스트 통과까지 전 과정을 다섯 번 측정했다: **0.86 / 0.90 / 0.86 / 0.89 / 1.03 초.**

(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다. 패키지 캐시가 채워져 있고 `uv` 로 환경을 만든 경우다. `pip` 로 네트워크에서 받으면 여기에 수 초가 더 붙는다.)

의존성이 없고 테스트가 11개면 이 정도다. 이 숫자가 중요한 이유는 **평가자의 첫 5분이 거의 통째로 코드를 읽는 데 쓰인다**는 뜻이기 때문이다. 반대로 도커 빌드가 필요하거나([6.7](#/docker)) 설치가 실패하면 그 5분이 통째로 증발한다.
:::

::: tip 제출 직전 7줄 점검
1. 깨끗한 복제본에서 README의 명령이 전부 도는가.
2. 실행 칸의 출력이 지금 코드의 출력과 같은가.
3. 테스트 개수와 통과 문구가 실제와 같은가.
4. 한계 목록에 이미 고친 것이 남아 있지 않은가.
5. 요구사항 대응표의 테스트 이름이 전부 실재하는가.
6. `git clean -ndx` 와 `git ls-files` 로 넣을 것과 뺄 것이 맞는가.
7. 비밀정보·개인 경로·회사 문서가 없는가.

5번은 눈으로 하지 마라. `grep -o 'test_[a-z_]*' README.md` 와 테스트 파일의 `def test_` 목록을 대조하면 10초다.
:::

## 과하게 쓴 README

과제형에서 오버엔지니어링은 코드에만 있는 게 아니다. README에도 있고, 이쪽이 더 자주 보인다.

```text nolines
  X  배지 다섯 개 (빌드/커버리지/라이선스/파이썬 버전/코드 스타일)
  X  아키텍처 다이어그램 3장과 계층 설명 두 페이지
  X  CONTRIBUTING.md, CHANGELOG.md, CODE_OF_CONDUCT.md
  X  "Features" 불릿 20개 (요구사항 5개짜리 과제에서)
  X  로드맵 v1.0 / v2.0 / v3.0
  X  벤치마크 표 (요구사항에 성능 조건이 없는데)
```

이것들이 왜 감점인지는 하나로 설명된다. **읽는 사람의 시간을 쓰게 만들면서 판단은 하나도 안 보여주기 때문이다.** 배지 다섯 개는 CI가 없는 저장소에서는 그냥 그림이다. 기여 가이드는 기여자가 없는 4시간짜리 과제에서 코스프레다. 로드맵 v3.0은 지금 못 한 것 다섯 개를 가린다.

::: warn README가 코드보다 길면 둘 중 하나가 잘못됐다
문서가 과한 것이거나, 코드가 요구사항을 덜 구현한 것이다. 위 예시는 README 2,915자에 소스 8개다. **한 화면 반에서 두 화면 반**이 과제형 README의 실전 범위다. 한 화면보다 짧으면 결정 칸이 비어 있을 것이고, 다섯 화면을 넘으면 평가자가 스킵한다.
:::

여기서 진짜 함정을 하나 더 짚는다. **README를 잘 쓰는 것이 코드의 부족을 덮지는 못한다.** 결정 칸에 훌륭한 문장이 다섯 개 있는데 요구사항 ③이 구현돼 있지 않으면, 그건 "말은 잘하는데 못 만드는 사람"이 된다. 순서는 언제나 **동작 → 테스트 → 문서**다. 남은 30분이 있을 때 README를 쓰는 것이고, 요구사항이 하나 비어 있는데 README를 쓰는 것이 아니다.

## 요약

- README는 감상문이 아니라 **절차서**다. **무엇을 / 실행 / 테스트 / 결정 / 한계** 다섯 칸이면 되고, **순서가 평가자의 행동 순서와 같아야** 한다.
- **실행 칸이 탈락 필터다.** 복사 가능한 한 덩어리, 실행 위치 명시, 샘플 데이터 동봉. 라이브러리 지정이 없으면 **의존성 0 + `python -m`** 이 설치가 필요한 구성보다 안전하다.
- **적은 파이썬 버전은 그 버전에서 실제로 돌려 보고 적어라.** 검증 안 한 하한선보다 "3.14에서 개발·검증했다"가 낫다.
- **설계 결정은 코드로 대체할 수 없는 유일한 칸이다.** 결정 / 대안 / 근거 / **바뀌면 어디를 고치는가** 네 조각으로, 3~5개만. "안 만든 것"이 오히려 강한 항목이다.
- **한계는 구체적이고, 비용이 적혀 있고, 코드와 일치해야 한다.** 코드와 어긋나는 한 줄이 README 전체의 신뢰를 깎는다.
- **패키징은 `.gitignore` 와 `git archive` 로 끝난다.** 같은 프로젝트가 폴더 통째 `zip` 으로는 56 MB / 2,492개, `git archive` 로는 8.3 KB / 18개였다. `zip` 은 심볼릭 링크를 따라가 인터프리터까지 끌고 들어온다.
- **마지막 5분은 리허설이다.** 깨끗한 복제본에서 README의 명령을 그대로 돌려라. 스크립트로 자동화하면 30초다.
- **README에도 오버엔지니어링이 있다.** 배지·로드맵·기여 가이드는 판단을 하나도 안 보여준다. 순서는 언제나 동작 → 테스트 → 문서다.

::: quiz 실습 과제 — 읽지 말고 만들어라

**1. 리허설 스크립트를 완성해라 (코드)**
본문의 `rehearse.sh` 는 각 명령의 종료 코드를 찍기만 한다. 여기에 **기대 종료 코드 검사**를 붙여라. README에 `<!-- expect: 1 -->` 같은 주석으로 기대값을 적어 두고, 스크립트가 그것과 실제 코드를 대조해 하나라도 어긋나면 `1` 로 끝나게 만들어라. 기대값 주석이 없는 명령은 `0` 을 기대한다. 실제로 자기 프로젝트에 돌려서 통과시켜라.

**2. 문서와 코드의 어긋남을 잡는 도구를 짜라 (코드)**
README에서 `test_` 로 시작하는 식별자를 전부 뽑고, `tests/` 의 `def test_...` 목록과 대조해 **한쪽에만 있는 이름**을 출력하는 스크립트를 20줄 안에 짜라. 그다음 이 검사를 어디에 두는 것이 맞는지 결정해라 — ① `tests/test_readme.py` 로 만들어 `pytest` 가 잡게 한다 ② 제출 직전 수동 실행 스크립트로 둔다. **4시간짜리 과제에서 어느 쪽인지 고르고 이유를 세 줄로 써라.** 정답은 없다. 근거를 보는 문제다.

**3. 종료 코드 규약을 결정해라 (설계 판단)**
본문의 CLI는 거부된 이동이 있으면 `1` 로 끝난다. 다음 두 안의 트레이드오프를 각각 세 줄로 적고, **어느 조건에서 어느 쪽이 나은지** 결론을 내라.
- 안 A: 거부가 하나라도 있으면 `1`. (지금 구현)
- 안 B: 프로그램이 정상 종료했으면 항상 `0`. 거부는 리포트로만 알린다.

결론을 그대로 README 설계 결정 항목의 **네 조각 형식**(결정/대안/근거/변경점)으로 옮겨 써라.

**4. 나쁜 README를 고쳐 써라 (설계 판단)**
아래는 실제로 흔한 형태다. 이걸 다섯 칸 구조로 다시 써라. 없는 정보는 **"확인 필요"로 표시**하고 지어내지 마라 — 무엇이 빠져 있는지 세는 것이 이 문제의 핵심이다.

```text nolines
# parking-fee

주차 요금 계산기입니다.
클린 아키텍처와 SOLID 원칙을 적용하여 설계했습니다.
테스트 커버리지는 100%입니다.

## 설치
pip install -r requirements.txt

## 실행
main.py를 실행하세요.
```

**5. 자기 과제를 패키징해라 (코드 + 판단)**
[12.7](#/project-structure)이나 [12.4](#/boundaries-di)에서 만든 프로젝트를 실제로 제출 가능한 상태로 만들어라. ① `.gitignore` 를 쓰고 ② `git archive` 로 zip을 만들고 ③ 그 zip을 빈 디렉터리에 풀어서 README 명령을 그대로 실행해라. ④ **zip 안의 파일 개수와 폴더를 통째로 압축했을 때의 개수를 각각 세어 보고 차이를 한 줄로 적어라.** 세 번째 단계에서 실패하면 그것이 이 과제의 진짜 수확이다.
:::
