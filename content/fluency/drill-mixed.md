# 11.12 드릴 IV — 종합 응용

::: lead
앞의 세 드릴은 유형을 미리 알려 주고 시작했다. 문자열([11.9](#/drill-string)), 격자([11.10](#/drill-grid)), 해시([11.11](#/drill-hash)) — 제목만 봐도 무엇을 꺼낼지 절반은 정해져 있었다. 실전은 그렇지 않다. 지문은 열람실과 짐칸과 세차기 이야기를 하고, **어떤 자료구조도 이름으로 등장하지 않는다.** 이 절의 일곱 문제는 전부 그렇게 쓰여 있다. 훈련하는 것은 새 알고리즘이 아니라 한 가지 동작이다 — **물리적 서술을 걷어내고 그 아래의 유형을 보는 것.** 그래서 문제마다 코드보다 먼저 **왜 이 유형이라고 판단했는가**를 적었다. 그 판단이 이 절의 전부다.
:::

## 유형을 부르는 문장들

유형이 안 보인다는 말은 정확히 이 뜻이다 — **지문에 자료구조 이름이 없다.** 대신 그 자리에 물리적 제약이나 수치 조건이 들어가 있다. 그것들이 신호다.

| 지문이 하는 말 | 이게 가리키는 유형 | 문제 |
| --- | --- | --- |
| "들어온 기록과 나간 기록이 섞여 있다" | 짝 맞추기 (`dict`) | 1 |
| "마지막에 넣은 것만 꺼낼 수 있다" | 스택 | 2 |
| "질의가 Q개 들어온다" | 전처리 (누적합) | 3 |
| "겹치지 않게 최대 몇 건" | 정렬 + 그리디 | 4 |
| "n이 10억이다", "최소 시간" | 답을 이분 탐색 | 5 |
| "버튼은 두 개뿐", "최소 횟수" | BFS | 6 |
| "지금의 선택이 뒤에까지 남는다" | DP | 7 |

표를 외우라는 게 아니다. **문제를 읽고 나서 스스로에게 던질 질문 네 개**를 고정하라는 것이다.

```text nolines
  Q1. 입력을 그대로 따라 하면 몇 번 도는가?
      -> 통하면 그냥 구현한다. 안 통하면 Q2 로 간다.

  Q2. 답의 후보 하나를 찍어 주면 채점이 쉬운가?
      -> 쉽고 단조롭다면 답 자체를 이분 탐색한다.

  Q3. 지금의 선택이 강제되는가, 뒤에 영향을 남기는가?
      -> 강제된다면 스택이나 그리디, 남는다면 DP 다.

  Q4. 같은 질문을 여러 번 묻는가?
      -> 전처리 한 번으로 비용을 앞에 몰아 넣는다.
```

규칙은 앞 드릴과 같다. **문제 설명까지만 읽고 멈추고, 타이머를 켜고 직접 짜라.** 못 풀었으면 코드보다 `어떻게 생각하는가` 를 먼저 읽고 **어느 문장에서 판단이 갈렸는지** 찾아라.

## 몸풀기 — easy 세 문제

### 문제 1 — 열람실 좌석 이용 시간

도서관 열람실 입퇴실 로그가 **시각 순으로** 주어진다. 각 줄은 `"HH:MM IN 좌석"` 또는 `"HH:MM OUT 좌석"` 이다.

- 좌석별 **총 이용 시간(분)** 을 구해 `(좌석, 분)` 리스트로 반환한다. **많은 순, 같으면 좌석코드 사전순.**
- 한 좌석은 동시에 한 명만 쓴다. 같은 좌석을 **하루에 여러 번** 쓸 수 있다.
- `OUT` 기록 없이 남은 좌석은 폐관 시각 `close` 까지 쓴 것으로 본다.

```python
LOG1 = ["09:00 IN S1", "09:10 IN S2", "09:40 OUT S1",
        "10:00 IN S1", "10:30 OUT S2", "11:00 OUT S1"]
seat_usage(LOG1, "12:00")   # -> [('S1', 100), ('S2', 80)]

LOG2 = ["10:00 IN S3", "10:00 IN S1", "11:30 OUT S1"]
seat_usage(LOG2, "12:00")   # -> [('S3', 120), ('S1', 90)]

seat_usage([], "12:00")     # -> []
```

제한 시간 8분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.

**어떻게 생각하는가**

- **유형 판정.** 표면은 시간표다. 손이 먼저 "9시부터 12시까지 1분씩 돌면서 누가 앉아 있는지 세자"로 간다. 그건 Q1에 걸린다 — 하루 720분 × 좌석 수만큼 돌게 되고, 좌석이 만 개면 720만 번이다. **입력이 로그 몇 줄인데 시간축을 다 도는 건 낭비다.**
- 실제 유형은 이 문장이 정한다. **"IN 이 있고 OUT 이 있다."** 짝이 있는 기록이다. 짝 맞추기는 시간축이 아니라 **열려 있는 것만 담아 두는 자료구조** 하나로 끝난다. 여는 기록에서 넣고, 닫는 기록에서 꺼내 차이를 더한다.
- 그 자료구조가 스택이 아니라 `dict` 인 이유는 **"한 좌석은 동시에 한 명"** 이라는 문장이다. 좌석마다 열린 기록이 최대 하나니까 `{좌석: 입실시각}` 으로 충분하다. 괄호 짝 맞추기처럼 중첩이 허용되면 그때 스택이 된다.
- "여러 번 쓸 수 있다"는 문장이 **누적**을 요구한다. 대입이 아니라 덧셈이다. `LOG1` 의 `S1` 이 정확히 이걸 확인하려고 들어간 데이터다(40분 + 60분).
- `"HH:MM"` 은 문자열 비교로도 정렬되지만 **뺄셈이 필요하면 분으로 바꿔야 한다**([11.3](#/string-toolkit)). 변환은 한 곳에서만 한다.

**코드**

```python title="reading_room.py"
def to_min(hhmm):
    h, m = hhmm.split(":")
    return int(h) * 60 + int(m)


def seat_usage(log, close):
    opened = {}                    # 좌석 -> 입실 시각. 열려 있는 기록만 남는다
    total = {}
    for line in log:
        t, kind, seat = line.split()
        if kind == "IN":
            opened[seat] = to_min(t)
        else:
            total[seat] = total.get(seat, 0) + to_min(t) - opened.pop(seat)
    for seat, start in opened.items():          # 폐관까지 안 나간 좌석
        total[seat] = total.get(seat, 0) + to_min(close) - start
    return sorted(total.items(), key=lambda p: (-p[1], p[0]))


LOG1 = ["09:00 IN S1", "09:10 IN S2", "09:40 OUT S1",
        "10:00 IN S1", "10:30 OUT S2", "11:00 OUT S1"]
LOG2 = ["10:00 IN S3", "10:00 IN S1", "11:30 OUT S1"]

for log in (LOG1, LOG2, []):
    print(seat_usage(log, "12:00"))
```

**실행 결과**

```text nolines
[('S1', 100), ('S2', 80)]
[('S3', 120), ('S1', 90)]
[]
```

::: danger 흔한 실수
**하나. 누적을 대입으로 쓴다.** 같은 좌석의 두 번째 이용이 첫 번째를 지운다.

```python
total = {}
total["S1"] = 40          # 1차 이용
total["S1"] = 60          # ❌ 2차 이용을 그냥 덮어썼다
print(total)              # -> {'S1': 60}
```

예외도 경고도 없다. `LOG1` 에서 `S1` 이 `60` 으로 나오는데 **그게 그럴듯한 숫자라서** 틀린 줄도 모른다. 로그 문제에서 "같은 대상이 여러 번 등장할 수 있는가"는 코드를 쓰기 전에 확인할 첫 항목이다.

**둘. `opened` 에서 꺼내지 않는다.** `opened.pop(seat)` 대신 `opened[seat]` 로 읽고 두면 마지막에 "안 나간 좌석" 보정에서 **이미 나간 좌석까지 폐관 시각까지 쓴 것으로 한 번 더 더한다.** 짝 맞추기에서 `pop` 은 값을 읽는 동작이 아니라 **"이 짝은 닫혔다"는 상태 갱신**이다.
:::

::: tip 변형 문제
- **좌석 지정이 없고 "동시에 최대 몇 명이 있었는가"** 를 물으면 유형이 바뀐다. 짝이 아니라 **경계 이벤트**가 되고, `+1/-1` 을 시각 순으로 훑는 스위핑이 된다.
- **로그가 시각 순이 아니면** 먼저 정렬해야 한다. 이때 같은 시각의 `OUT` 과 `IN` 중 어느 쪽을 먼저 처리하느냐가 답을 바꾼다 — 정렬 키의 두 번째 칸에 못 박아라([11.6](#/sorting-as-tool)).
- **`IN` 없이 `OUT` 이 오는 오작동 기록**이 섞이면 `opened.pop(seat)` 이 `KeyError` 다. 무시할지 예외로 알릴지는 요구사항이 정한다. 조용히 `pop(seat, None)` 으로 덮는 것이 가장 나쁜 선택이다.
:::

### 문제 2 — 좁은 짐칸 하차 순서

상자가 `1, 2, …, n` 번 순서로 컨베이어에서 나온다. 순서를 바꿀 수도, 건너뛸 수도 없다. 각 상자는 나오는 즉시 트럭 짐칸에 싣거나, 짐칸에 이미 실린 것들을 내린 뒤에 실을 수 있다. 짐칸이 좁아서 **가장 마지막에 실은 상자만 꺼낼 수 있다.**

배송 기사가 원하는 하차 순서 `order`(1~n의 순열)가 주어진다. 그 순서로 내릴 수 있으면 `True`, 불가능하면 `False` 를 반환해라.

```python
can_unload([1, 2, 3])      # -> True
can_unload([3, 2, 1])      # -> True
can_unload([2, 3, 1])      # -> True
can_unload([3, 1, 2])      # -> False
can_unload([4, 1, 3, 2])   # -> False
```

::: quiz 먼저 직접 풀어라
제한 시간 10분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.
:::

**어떻게 생각하는가**

- **유형 판정.** 첫 문장이 유형이다. **"마지막에 실은 것만 꺼낼 수 있다" = LIFO = 스택**([7.7](#/stack-queue)). 지문에 스택이라는 말은 없고 짐칸 이야기만 있지만, 제약의 모양이 곧 자료구조다.
- 진짜 함정은 여기다. 매 순간 "실을까 내릴까" 두 갈래로 보이니 **전탐색을 짜려는 손**이 나온다. Q3을 던져라 — **선택이 강제되는가?** 강제된다. 지금 내려야 하는 상자가 짐칸 맨 위에 있으면 **내리는 것 말고 할 게 없다.** 없으면 **싣는 것 말고 할 게 없다.** 갈림길이 아니라 외길이다. 그래서 백트래킹이 아니라 한 번의 순회로 끝난다.
- 손으로 굴려라. `[3, 1, 2]` — 3을 내리려면 1, 2, 3을 싣는다. 3을 내린다. 이제 위는 2인데 1이 필요하다. 더 실을 상자도 없다. **끝.** 이 굴림이 종료 조건 두 개를 그대로 준다.
- 실패 조건을 한 문장으로 못 박아라. **"더 실을 상자가 없는데 맨 위가 원하는 것이 아니다."** 이 문장이 `if` 하나가 된다.

**코드**

```python title="unload_order.py"
def can_unload(order):
    n = len(order)
    hold = []                       # 짐칸. 맨 뒤가 문 쪽
    nxt = 1                         # 다음에 실을 상자 번호
    for want in order:
        while nxt <= n and (not hold or hold[-1] != want):
            hold.append(nxt)        # 원하는 상자가 문 쪽에 없으면 계속 싣는다
            nxt += 1
        if not hold or hold[-1] != want:
            return False            # 더 실을 상자도 없는데 문 쪽이 다르다
        hold.pop()
    return True


for order in ([1, 2, 3], [3, 2, 1], [2, 3, 1], [3, 1, 2], [4, 1, 3, 2], [1]):
    print(f"{str(order):12} -> {can_unload(order)}")
```

**실행 결과**

```text nolines
[1, 2, 3]    -> True
[3, 2, 1]    -> True
[2, 3, 1]    -> True
[3, 1, 2]    -> False
[4, 1, 3, 2] -> False
[1]          -> True
```

이 코드는 `n ≤ 7` 의 **모든 순열**을 전탐색 풀이와 대조해서 일치를 확인했다. 결정론적 그리디가 맞는지 의심될 때 가장 값싼 검증법은 작은 입력 전수 대조다([11.7](#/blank-page-routine)).

::: danger 흔한 실수
**하나. `while` 을 `if` 로 쓴다.** "위에 없으면 하나 싣는다"로 짜면 `[3, 2, 1]` 에서 3을 내리기까지 세 개를 실어야 하는데 하나만 싣고 `False` 를 낸다. **한 번 내리기 위해 여러 번 실어야 한다** — 이걸 손으로 굴려 보지 않으면 안 보인다.

**둘. 빈 스택 확인을 뒤에 붙인다.** `hold[-1] != want` 를 `not hold` 보다 먼저 쓰면 빈 짐칸에서 `IndexError` 다. 파이썬의 `or`/`and` 는 왼쪽부터 평가하고 결과가 정해지면 멈추므로([1.8](#/control-flow)), **빈 검사를 반드시 왼쪽에** 둬라. 스택을 쓰는 코드에서 가장 흔한 예외 한 줄이다.
:::

::: tip 변형 문제
- **하차 순서 대신 "동작 기록"을 반환**하라고 하면 `append` 자리에 `"실음"`, `pop` 자리에 `"내림"` 을 리스트에 쌓으면 된다. 골격은 한 글자도 안 바뀐다.
- **짐칸 용량이 k로 제한**되면 `while` 조건에 `len(hold) < k` 가 붙는다. 이때는 "실을 수 없어서 실패"라는 세 번째 종료 조건이 생긴다.
- **꺼내는 곳이 양쪽**이면 스택이 아니라 `deque` 다. 그리고 선택이 강제되지 않으므로 **외길이 갈림길이 된다** — 이 문제가 갑자기 탐색 문제로 바뀐다. 제약 한 줄이 유형을 통째로 옮긴다.
:::

### 문제 3 — 전력 사용량 구간 질의

건물의 시간대별 전력 사용량이 `usage` 리스트로 주어진다. 질의 `(l, r)` 는 **l번째부터 r번째까지(양끝 포함)** 의 합을 묻는다. 인덱스는 0부터 센다. 질의는 리스트로 한꺼번에 주어지고 **최대 20만 개**다. `usage` 도 최대 20만 개다.

```python
USAGE = [3, 1, 4, 1, 5, 9, 2]
range_sums(USAGE, [(0, 2), (2, 5), (6, 6), (0, 6)])   # -> [8, 19, 2, 25]
range_sums([10], [(0, 0), (0, 0)])                    # -> [10, 10]
range_sums([3, 1, 4], [])                             # -> []
```

::: quiz 먼저 직접 풀어라
제한 시간 6분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.
:::

**어떻게 생각하는가**

- **유형 판정.** `sum(usage[l:r+1])` 로 한 줄이면 끝난다. 그런데 지문이 **"질의가 최대 20만 개"** 라고 굳이 말한다. 이 문장은 장식이 아니라 **유형 지정**이다. 구간 길이가 평균 5만이면 20만 × 5만 = 100억 번의 덧셈이다.
- Q4를 던져라 — **같은 질문을 반복해서 묻는가.** 그렇다면 답은 항상 같은 모양이다. **한 번 전처리하고, 질의는 상수 시간에 답한다.** 여기서의 전처리가 누적합이다.
- 왜 누적합인가. `l..r` 의 합은 `(0..r의 합) − (0..l−1의 합)` 이다. 뺄셈으로 표현되는 순간 미리 계산해 둘 것이 정해진다. **앞에서부터의 합 하나만 들고 있으면 모든 구간이 뺄셈 한 번**이다.
- 관용구는 `pre = [0, *accumulate(usage)]` 다. **맨 앞에 0을 넣는 것이 핵심**이고, 그러면 `l = 0` 을 특별 취급하지 않아도 된다. `pre[i]` 를 "앞 i개의 합"으로 정의하면 답은 `pre[r+1] - pre[l]` 이다.

```pyrepl
>>> from itertools import accumulate
>>> [0, *accumulate([3, 1, 4, 1, 5, 9, 2])]
[0, 3, 4, 8, 9, 14, 23, 25]
```

**코드**

```python title="power_query.py"
from itertools import accumulate


def range_sums(usage, queries):
    pre = [0, *accumulate(usage)]                      # pre[i] = 앞 i개의 합
    return [pre[r + 1] - pre[l] for l, r in queries]


USAGE = [3, 1, 4, 1, 5, 9, 2]
print(range_sums(USAGE, [(0, 2), (2, 5), (6, 6), (0, 6)]))
print(range_sums([10], [(0, 0), (0, 0)]))
print(range_sums([3, 1, 4], []))
```

**실행 결과**

```text nolines
[8, 19, 2, 25]
[10, 10]
[]
```

::: perf 전처리 한 줄이 두 자릿수를 지운다
0~999 균등 난수 정수 20만 개에, 시작·끝을 무작위로 뽑은 질의 2,000개(평균 구간 길이 약 5만 600)를 던졌다.

| 방법 | 2,000회 질의 |
| --- | --- |
| 누적합 전처리 + 뺄셈 | 11.3 ~ 15.7 ms |
| `sum(usage[l:r+1])` | 1.96 ~ 2.20 s |

(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다.)

**두 자릿수 차이다.** 그런데 질의가 **한 개**뿐이면 순위가 뒤집힌다 — 누적합은 20만 개를 먼저 훑어야 하고, `sum` 은 그 구간만 훑으면 된다. 전처리는 **비용을 앞으로 몰아 두는 거래**다. 거래가 이득이 되는 조건은 항상 "질의가 여러 번"이라는 문장 하나다([8.3](#/tle)).
:::

::: danger 흔한 실수
**하나. `pre[r] - pre[l]` 로 쓴다.** 양끝 포함이면 `pre[r+1]` 이다. 이 off-by-one은 **첫 예시에서도 8 대신 4가 나와** 금방 잡히지만, `l = r` 인 질의만 테스트하면 우연히 0이 나오면서 통과한 듯 보인다. 길이 1 구간과 길이 2 구간을 **둘 다** 넣어 봐라([11.14](#/exam-debug)).

**둘. 앞에 0을 안 넣는다.** `pre = list(accumulate(usage))` 로 두면 `l = 0` 일 때 `pre[-1]` 을 참조해 **리스트의 마지막 값**을 빼 버린다. 예외 없이 틀린 답이 나오고, 하필 전체 합이라서 결과가 큰 음수가 된다.
:::

::: tip 변형 문제
- **"구간 평균"** 이면 `(pre[r+1] - pre[l]) / (r - l + 1)` 이다. 길이는 인덱스로 계산되니 새로 셀 필요가 없다.
- **중간에 값이 바뀐다**(갱신 질의가 섞인다)면 누적합은 무너진다. 갱신마다 전처리를 다시 해야 하기 때문이다. 그 자리가 펜윅 트리·세그먼트 트리다([7.25](#/segment-tree)). **"갱신이 있는가"** 를 확인하고 나서 누적합을 골라라.
- **2차원**이면 같은 아이디어가 그대로 확장된다. 사각형 구간 합은 네 개의 누적값의 덧셈·뺄셈이다([11.4](#/array-grid)).
:::

## 본 드릴 — medium 네 문제

### 문제 4 — 회의실 예약 최대 수용

회의실이 하나 있고 예약 요청이 `(시작, 종료)` 정수 시각 리스트로 주어진다. 요청은 **통째로 받거나 통째로 거절**한다(시간 조정 불가). 한 예약의 종료 시각과 다음 예약의 시작 시각이 **같으면 연속 사용 가능**하다.

받을 수 있는 최대 건수와 그 예약 목록(시작 시각 순)을 반환해라.

```python
max_bookings([(9, 10), (9, 12), (10, 11), (11, 13), (12, 14)])
# -> (3, [(9, 10), (10, 11), (11, 13)])

max_bookings([(13, 15), (9, 11)])          # -> (2, [(9, 11), (13, 15)])
max_bookings([(9, 18), (10, 11), (11, 12)])  # -> (2, [(10, 11), (11, 12)])
max_bookings([])                           # -> (0, [])
```

::: quiz 먼저 직접 풀어라
제한 시간 12분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.
:::

**어떻게 생각하는가**

- **유형 판정.** "겹치지 않게 **최대 몇 건**"은 최적화 문제다. 후보가 부분집합이니 전탐색은 $2^n$ — Q1에서 탈락한다. 남는 것은 DP와 그리디인데, **구간을 고르는 문제에서 그리디가 최적을 보장하는 고전 유형**이 정확히 이것이다([7.19](#/greedy)).
- 문제는 **무엇으로 정렬하는가**다. 이걸 못 정하면 그리디는 그냥 틀린 코드다. 세 후보를 놓고 반례를 찾아라. 시작 시각 순? 짧은 순? 종료 시각 순?
- 손으로 굴려라. `[(9, 18), (10, 11), (11, 12)]` 에서 시작 시각 순으로 고르면 `(9, 18)` 하나를 잡고 하루가 끝난다. **정답은 2건이다.**

```pyrepl
>>> reqs = [(9, 18), (10, 11), (11, 12)]
>>> sorted(reqs)
[(9, 18), (10, 11), (11, 12)]
>>> sorted(reqs, key=lambda r: r[1])
[(10, 11), (11, 12), (9, 18)]
```

- 왜 종료 시각인가. **"빨리 끝나는 것을 잡을수록 남는 시간이 많다."** 남는 시간이 많으면 그 뒤의 선택지가 줄지 않는다. 이 한 문장이 그리디의 정당성이고, 시험장에서 확신을 주는 근거다.
- 마지막 디테일. `s >= last_end` 인가 `s > last_end` 인가는 **지문이 정한다.** "종료와 시작이 같으면 연속 사용 가능"이라고 써 있으니 `>=` 다. 이 부등호 하나가 예약 하나를 만든다.

**코드**

```python title="meeting_room.py"
def max_bookings(reqs):
    picked, last_end = [], None
    for s, e in sorted(reqs, key=lambda r: (r[1], r[0])):   # 끝나는 시각 순
        if last_end is None or s >= last_end:
            picked.append((s, e))
            last_end = e
    return len(picked), picked


for reqs in ([(9, 10), (9, 12), (10, 11), (11, 13), (12, 14)],
             [(13, 15), (9, 11)],
             [(9, 18), (10, 11), (11, 12)],
             []):
    print(f"{str(reqs):48} -> {max_bookings(reqs)}")
```

**실행 결과**

```text nolines
[(9, 10), (9, 12), (10, 11), (11, 13), (12, 14)] -> (3, [(9, 10), (10, 11), (11, 13)])
[(13, 15), (9, 11)]                              -> (2, [(9, 11), (13, 15)])
[(9, 18), (10, 11), (11, 12)]                    -> (2, [(10, 11), (11, 12)])
[]                                               -> (0, [])
```

종료 시각 순으로 골랐는데 결과가 시작 시각 순으로도 정렬돼 있다. 겹치지 않는 구간들이라 두 순서가 같아지기 때문이다 — 따로 정렬할 필요가 없다.

::: danger 흔한 실수
**하나. 짧은 것부터 고른다.** 직관적으로 그럴듯하고 실제로 틀린다. `[(9, 12), (11, 13), (12, 15)]` 에서 가장 짧은 `(11, 13)` 을 먼저 잡으면 나머지 둘이 다 겹쳐 **1건**이다. 정답은 `(9, 12)` 와 `(12, 15)` 로 **2건**이다.

**둘. 정렬 없이 그리디를 쓴다.** 입력이 우연히 시각 순으로 들어오는 예제에서는 통과하고 채점 데이터에서만 틀린다. 그리디의 정확성은 **정렬 순서에 전부 걸려 있다.** 정렬 키를 못 정했으면 그건 그리디를 고른 게 아니라 아무 코드나 쓴 것이다.
:::

::: tip 변형 문제
- **회의실이 k개**면 유형이 바뀐다. "빨리 끝나는 방"을 계속 꺼내야 하므로 종료 시각 힙이 된다([11.2](#/stdlib-arsenal)). "매번 극값 하나"라는 신호가 새로 생기는 것이다.
- **예약마다 가치가 있고 가치 합을 최대화**하면 그리디가 무너진다. 종료 시각 정렬 + 이분 탐색 + DP다([7.20](#/dp-basics)). **"최대 개수"가 "최대 가치"로 바뀌는 순간 유형이 이동한다** — 지문에서 이 단어를 놓치지 마라.
- **"최소 몇 개의 회의실이 필요한가"** 면 고르는 문제가 아니라 겹침의 최댓값을 세는 문제다. 그때는 정렬 + 스위핑이다.
:::

### 문제 5 — 무인 세차장 대기 시간

세차기가 `k` 대 있고, `i` 번 기계는 차 한 대를 세차하는 데 `times[i]` 분 걸린다. 기계들은 동시에 돌아가고, 한 기계는 한 대씩 쉬지 않고 처리한다. 대기 차량은 비어 있는 기계 아무 곳으로나 들어간다.

차량 `n` 대가 처음부터 줄 서 있을 때, **마지막 차량의 세차가 끝나는 가장 빠른 시각**(0분 시작)을 구해라. 제약: `k ≤ 100`, `times[i] ≤ 60`, **`n ≤ 10억`**.

```python
min_finish([7, 10], 6)     # -> 28
min_finish([4, 6, 9], 10)  # -> 20
min_finish([3], 1)         # -> 3
min_finish([1, 1], 5)      # -> 3
min_finish([7, 10], 0)     # -> 0
```

::: quiz 먼저 직접 풀어라
제한 시간 15분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.
:::

**어떻게 생각하는가**

- **유형 판정.** 시뮬레이션이 먼저 떠오른다. "가장 빨리 비는 기계에 다음 차를 넣는다" — 힙으로 $O(n \log k)$ 다. 맞는 답이지만 Q1에 걸린다. **`n ≤ 10억`.** 지문이 알려 준 숫자가 시뮬레이션을 금지한 것이다.
- 그럼 Q2를 던져라. **답의 후보 T를 하나 찍어 주면 채점이 쉬운가?** 쉽다. `T` 분 안에 `i` 번 기계는 `T // times[i]` 대를 처리한다. 전부 더해서 `n` 이상이면 T는 충분하다. `k ≤ 100` 이니 채점 한 번이 100번의 나눗셈이다.
- 그리고 **단조롭다.** T가 커지면 처리 대수는 절대 줄지 않는다. **"채점이 쉽다 + 단조롭다" = 답을 이분 탐색**([7.5](#/binary-search)). 이게 이 문제의 유형이다. 구하려는 것이 배열의 인덱스가 아니라 **답 자체**라는 점이 낯설 뿐, 이분 탐색의 조건은 그대로다.

```pyrepl
>>> times = [7, 10]
>>> [(T, sum(T // t for t in times)) for T in (20, 27, 28)]
[(20, 4), (27, 5), (28, 6)]
```

- 27분에 5대, 28분에 6대. `n = 6` 의 답이 28인 이유가 이 출력에 다 있다. **경계에서 값이 튀는 지점을 찾는 것**이 이분 탐색이 하는 일이다.
- 상한을 정해라. 가장 빠른 기계 **하나만** 써도 `min(times) * n` 분이면 끝난다. 그러니 그게 안전한 상한이다. `max(times) * n` 도 틀리진 않지만 크게 잡을 이유가 없다.
- `n = 0` 은 별도 처리다. 이분 탐색 하한을 1로 두면 0을 답으로 낼 수 없다.

**코드**

```python title="car_wash.py"
def min_finish(times, n):
    if n == 0:
        return 0
    lo, hi = 1, min(times) * n            # 가장 빠른 기계 하나로 다 하는 시간 = 안전한 상한
    while lo < hi:
        mid = (lo + hi) // 2
        if sum(mid // t for t in times) >= n:   # mid분 안에 n대를 넘기는가
            hi = mid
        else:
            lo = mid + 1
    return lo


for times, n in (([7, 10], 6), ([4, 6, 9], 10), ([3], 1), ([1, 1], 5), ([7, 10], 0)):
    print(f"times={str(times):11} n={n:<3} -> {min_finish(times, n)}")
```

**실행 결과**

```text nolines
times=[7, 10]     n=6   -> 28
times=[4, 6, 9]   n=10  -> 20
times=[3]         n=1   -> 3
times=[1, 1]      n=5   -> 3
times=[7, 10]     n=0   -> 0
```

무작위 입력 5,000건을 힙 시뮬레이션과 대조해 전부 일치를 확인했다(`k ≤ 5`, `n ≤ 40`). **이분 탐색 풀이를 짤 때는 느린 시뮬레이션을 정답의 기준으로 함께 짜라.** 버릴 코드가 아니라 채점기다.

::: perf 유형을 바꾸면 규모가 바뀐다
`k = 100`(각 1~60분), `n = 10억` 에서 이분 탐색 풀이가 **0.15 ~ 0.26 ms** 였다. 같은 기계 구성으로 힙 시뮬레이션은 `n = 10만` 에서 **43 ~ 48 ms** 다(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다).

시뮬레이션은 차량 한 대마다 `pop`/`push` 를 하니 `n = 10억` 이면 그 연산이 10억 번이다 — 재 볼 필요도 없다. 이분 탐색은 `n` 이 커져도 반복 횟수가 $\log$ 로만 늘고, 한 번의 채점 비용은 `k` 에만 달려 있다. **입력 크기가 알고리즘을 고르는 게 아니라, 지문의 제약이 유형을 지목한다.**
:::

::: danger 흔한 실수
**하나. 상한을 `min(times) * n` 이 아니라 `max(times)` 나 `n` 같은 값으로 잡는다.** 상한이 답보다 작으면 이분 탐색은 **예외 없이** 그 상한을 답으로 낸다. 상한은 "확실히 충분한 값"을 **말로 증명해서** 정해라 — "가장 빠른 기계 하나로 전부 처리하는 시간"처럼.

**둘. `while lo <= hi` 와 `hi = mid - 1` 을 섞어 쓴다.** 최솟값을 찾는 이분 탐색은 `while lo < hi` + `hi = mid` + `lo = mid + 1` 이 짝이다. 이걸 섞으면 무한 루프나 1 차이 오답이 된다. **경계 관용구는 하나만 골라서 손에 붙여라**([7.5](#/binary-search)).
:::

::: tip 변형 문제
- **차량이 시각마다 도착**하면 단조성이 유지되는지 다시 확인해야 한다. 도착 시각이 있으면 `T // t` 계산이 깨지고, 유형이 시뮬레이션이나 스위핑으로 돌아온다.
- **"n대를 처리하는 데 최소 기계 몇 대가 필요한가"** 로 바뀌면 이분 탐색의 대상이 시간에서 기계 수로 옮겨 간다. 채점 함수만 갈아 끼우면 골격은 그대로다.
- **각 차량이 특정 기계만 쓸 수 있으면** 나눗셈으로 셀 수 없다. 이분 탐색은 남지만 채점이 이분 매칭이 되고, 유형은 그래프로 넘어간다.
:::

### 문제 6 — 버튼이 두 개인 엘리베이터

`1` 층부터 `n` 층까지 있는 건물의 엘리베이터에 버튼이 딱 두 개다. 하나는 **`u` 층 위로**, 하나는 **`d` 층 아래로** 움직인다. 층 범위를 벗어나는 이동은 아예 동작하지 않는다.

`s` 층에서 `g` 층으로 가는 데 필요한 **최소 버튼 누름 횟수**를 반환해라. 갈 수 없으면 `-1`.

```python
min_press(10, 1, 10, 2, 1)   # -> 6
min_press(10, 1, 10, 3, 2)   # -> 3
min_press(5, 1, 4, 4, 4)     # -> -1
min_press(10, 7, 7, 3, 2)    # -> 0
```

::: quiz 먼저 직접 풀어라
제한 시간 12분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.
:::

**어떻게 생각하는가**

- **유형 판정.** 지문에 그래프도 노드도 없다. 그런데 **"최소 횟수"** 이고, **한 상태에서 갈 수 있는 다음 상태가 두 개뿐**이다. 이 두 조건이 만나면 유형은 하나다 — **가중치 없는 최단 경로 = BFS**([7.14](#/bfs-dfs)).
- 그래프를 만들어야 한다는 생각을 버려라. **노드는 층 번호 하나**고, 간선은 `+u`, `-d` 두 개다. 인접 리스트를 미리 짜는 게 아니라 **필요할 때 계산한다.** 격자 문제의 `dx/dy` 와 같은 구조다([11.4](#/array-grid)) — 격자가 1차원으로 납작해진 것뿐이다.
- 왜 그리디가 안 되는가. 손으로 굴려라. `n=10, s=1, g=10, u=2, d=1` 에서 목표에 가까워지는 방향만 누르면 1→3→5→7→9 로 가고, 9층에서 `+2` 는 11층이라 동작하지 않는다. **거기서 한 번 내려가야 한다.** 정답 경로는 1→3→5→7→9→8→10 으로 6번이다. **"뒤로 가야 앞으로 갈 수 있다" — 그리디가 죽는 전형적인 모양이고, 그게 BFS를 부른다.**
- 왜 DFS가 아닌가. 최소 횟수를 물었다. BFS는 **처음 도달한 순간이 최단**이다. DFS로 풀면 모든 경로를 다 봐야 한다.
- 방문 표시를 **큐에 넣을 때** 한다. 꺼낼 때 표시하면 같은 층이 큐에 여러 번 들어가 최악의 경우 지수로 부푼다. `dist` 딕셔너리 하나가 방문 표시와 거리를 겸한다.

**코드**

```python title="two_button_lift.py"
from collections import deque


def min_press(n, s, g, u, d):
    if s == g:
        return 0
    dist = {s: 0}                        # 방문 표시와 거리를 한 자료구조로
    q = deque([s])
    while q:
        cur = q.popleft()
        for nxt in (cur + u, cur - d):
            if 1 <= nxt <= n and nxt not in dist:
                if nxt == g:
                    return dist[cur] + 1
                dist[nxt] = dist[cur] + 1
                q.append(nxt)            # 넣을 때 표시한다. 꺼낼 때가 아니다
    return -1


for args in ((10, 1, 10, 2, 1), (10, 1, 10, 3, 2), (5, 1, 4, 4, 4), (10, 7, 7, 3, 2)):
    print(f"n={args[0]} {args[1]}층 -> {args[2]}층 (+{args[3]}/-{args[4]}) : {min_press(*args)}")
```

**실행 결과**

```text nolines
n=10 1층 -> 10층 (+2/-1) : 6
n=10 1층 -> 10층 (+3/-2) : 3
n=5 1층 -> 4층 (+4/-4) : -1
n=10 7층 -> 7층 (+3/-2) : 0
```

무작위 입력 4,000건(`n ≤ 30`)을 거리 배열을 반복 갱신하는 무식한 방법과 대조해 전부 일치했다.

::: danger 흔한 실수
**하나. `s == g` 를 처리하지 않는다.** 목표에 도착한 판정을 "큐에서 꺼낼 때"가 아니라 "넣을 때"만 하는 구조에서는 출발 = 목표인 경우가 통째로 빠진다. `-1` 이 나오고, 예시에 그 입력이 없으면 못 잡는다. **입력과 출력이 같은 퇴화 케이스를 항상 먼저 던져 봐라**([11.8](#/function-completion)).

**둘. `list` 를 큐로 쓴다.** `q.pop(0)` 은 원소 전체를 앞으로 당기므로 $O(n)$ 이고, BFS 전체가 $O(n^2)$ 이 된다. `n` 이 10만이면 여기서 시간 초과가 난다. **BFS는 `deque` 다** — 예외 없다([7.2](#/py-ds-cost)).
:::

::: tip 변형 문제
- **버튼이 세 개 이상**이어도 코드는 안 바뀐다. `for nxt in (...)` 안의 후보만 늘어난다. **BFS 골격이 좋은 이유는 상태 전이가 늘어도 구조가 그대로**라는 점이다.
- **버튼마다 비용이 다르면** BFS가 무너진다. 가중치가 생기는 순간 다익스트라다([7.15](#/shortest-path)). "누름 횟수"가 "소요 시간"으로 바뀌는 단어 하나가 유형을 옮긴다.
- **경로까지 반환**하려면 `dist` 를 `{층: (거리, 이전 층)}` 으로 바꾸고 목표에서 거꾸로 따라 올라간다. 거리만 필요할 때 이걸 미리 만들지는 마라.
:::

### 문제 7 — 공유 자전거 이용권 최소 요금

공유 자전거를 탈 예정인 날짜가 `days` 로 **오름차순** 주어진다(1~365의 정수). 이용권은 세 가지다.

- **1일권** `one` 원 — 그날 하루만
- **7일권** `week` 원 — 산 날부터 **연속 7일**
- **30일권** `month` 원 — 산 날부터 **연속 30일**

이용권은 아무 날에나 살 수 있고, 예정된 모든 날에 탈 수 있어야 한다. 최소 요금을 구해라. 아래 예시는 모두 `one=200, week=700, month=2000` 이다.

```python
min_fee([1, 4, 6, 7, 8, 20], 200, 700, 2000)         # -> 1100
min_fee([1, 2, 3, 4, 5, 6, 7, 8], 200, 700, 2000)    # -> 900
min_fee([8, 12, 13, 14, 15, 16, 29], 200, 700, 2000) # -> 1100
min_fee([1, 31, 61], 200, 700, 2000)                 # -> 600
min_fee([], 200, 700, 2000)                          # -> 0
```

::: quiz 먼저 직접 풀어라
제한 시간 15분. 아래 접근 과정을 보기 전에 반드시 손으로 짜 볼 것.
:::

**어떻게 생각하는가**

- **유형 판정.** Q3을 던져라. **선택의 결과가 뒤에 남는가?** 7일권을 사면 **그 뒤 6일에 영향이 남는다.** 남으면 그리디가 아니다. 그리고 매 지점의 선택지가 세 개뿐이고, 각 선택이 "더 작은 같은 문제"로 이어진다. **선택 + 뒤에 남는 영향 + 겹치는 부분 문제 = DP**([7.20](#/dp-basics)).
- 상태를 정해라. 여기서 헤매는 이유는 대개 **"이용권"을 상태로 잡으려 해서**다. 상태는 **날짜**다. `dp[d]` = **d일까지의 모든 예정일을 커버하는 최소 요금.** 이 한 문장을 못 쓰면 코드를 쓰지 마라.
- 전이는 지문을 그대로 옮긴다. `d` 가 예정일이 아니면 비용이 늘 이유가 없으니 `dp[d] = dp[d-1]`. 예정일이면 그날을 커버하는 방법이 셋이다 — 1일권이면 `dp[d-1] + one`, 7일권이면 그 권이 `d-6`부터 `d`까지 덮으니 `dp[d-7] + week`, 30일권이면 `dp[d-30] + month`.
- **왜 "d에서 시작하는 권"이 아니라 "d에서 끝나는 권"으로 세는가.** 뒤에서 앞을 참조해야 이미 계산된 값을 쓸 수 있기 때문이다. 7일권을 `d`일에 사서 미래를 덮는 것으로 세면 아직 계산되지 않은 칸을 봐야 한다. **DP의 방향은 "이미 아는 것에서 온다"로 정해진다.**
- 손으로 굴려라. `[1, 2, …, 8]` — 7일권 하나(700)로 1~7일을 덮고 8일에 1일권(200) = 900. 8장 사면 1,600이다. 확인 끝.

**코드**

```python title="bike_pass.py"
def min_fee(days, one, week, month):
    if not days:
        return 0
    need, last = set(days), days[-1]
    dp = [0] * (last + 1)
    for d in range(1, last + 1):
        if d not in need:
            dp[d] = dp[d - 1]            # 안 타는 날은 비용이 늘지 않는다
        else:
            dp[d] = min(dp[d - 1] + one,
                        dp[max(0, d - 7)] + week,
                        dp[max(0, d - 30)] + month)
    return dp[last]


for days in ([1, 4, 6, 7, 8, 20], [1, 2, 3, 4, 5, 6, 7, 8],
             [8, 12, 13, 14, 15, 16, 29], [1, 31, 61], [5], []):
    print(f"{str(days):32} -> {min_fee(days, 200, 700, 2000)}")
```

**실행 결과**

```text nolines
[1, 4, 6, 7, 8, 20]              -> 1100
[1, 2, 3, 4, 5, 6, 7, 8]         -> 900
[8, 12, 13, 14, 15, 16, 29]      -> 1100
[1, 31, 61]                      -> 600
[5]                              -> 200
[]                               -> 0
```

무작위 입력 2,000건을 **메모 없는 전탐색 재귀**와 대조해 전부 일치했다. DP를 짤 때 정답의 기준은 항상 전탐색이다 — 먼저 전탐색을 짜고, 그것이 같은 인자로 반복 호출되는 것을 확인한 다음 DP로 옮기는 순서가 안전하다.

::: danger 흔한 실수
**하나. `max(0, d - 7)` 을 빼먹는다.** `dp[d - 7]` 은 `d < 7` 에서 **음수 인덱스**가 된다. 파이썬은 음수 인덱스를 뒤에서 세는 유효한 접근으로 처리하므로 **예외가 안 날 수도 있다.**

```pyrepl
>>> dp = list(range(29))
>>> dp[5 - 30]
4
```

`dp[-25]` 가 조용히 `dp[4]` 를 준다. 실제로 `days=[5, 13, 15, 21, 28]`, `one=500, week=1800, month=2400` 에서 이 버그는 정답 `2400` 대신 `2500` 을 낸다. 리스트가 짧으면 `IndexError` 로 터져서 오히려 다행이지만, 길면 **예외 없이 틀린다.** 음수 인덱스가 유효 문법인 언어에서 DP를 짤 때 가장 많이 나오는 버그다([11.14](#/exam-debug)).

**둘. 그리디로 푼다.** "지금부터 7일 안에 탈 날이 4일 이상이면 7일권"류의 규칙은 반례가 있다. `[8, 12, 13, 14, 15, 16, 29]` 에서 8일에 7일권을 사면(8~14일 커버) 총 1,300원이지만, **12일에 사면**(12~18일 커버) 8일과 29일만 1일권으로 처리해 1,100원이다. **권을 어디서 시작하는지가 선택지고, 선택지가 있으면 DP다.**
:::

::: tip 변형 문제
- **"어떤 권을 언제 샀는지"** 까지 반환하려면 `dp` 와 나란히 선택을 기록하는 배열을 두고 끝에서 거꾸로 따라간다. 값만 필요할 때 미리 만들지 마라.
- **예정일이 365일에 흩어져 있고 날짜 범위가 아주 크면** 날짜 축이 아니라 **예정일 인덱스 축**으로 DP를 짠다. 커버 범위 끝을 `bisect` 로 찾는다([11.2](#/stdlib-arsenal)). 상태 축을 바꾸는 것이 DP 최적화의 기본이다.
- **권 종류가 입력으로 주어지면**(기간·가격 목록) `min()` 안의 세 줄이 루프 한 줄이 된다. 하드코딩된 선택지를 데이터로 바꾸는 연습을 해 둬라 — 과제형에서 그대로 요구된다([12.2](#/requirements-to-model)).
:::

## 복기표 — 표면과 실제

풀고 나서 이 표를 덮고 스스로 채워 봐라. **채울 수 있으면 유형 판별이 손에 붙은 것이다.**

| 문제 | 표면이 유혹하는 풀이 | 실제 유형 | 유형을 정한 문장 |
| --- | --- | --- | --- |
| 1 | 시간축 1분씩 순회 | 짝 맞추기(`dict`) | "한 좌석은 동시에 한 명" |
| 2 | 싣고 내리기 전탐색 | 스택 | "마지막에 실은 것만 꺼낸다" |
| 3 | 질의마다 구간 합 | 누적합 전처리 | "질의가 20만 개" |
| 4 | 부분집합 전탐색 | 정렬 + 그리디 | "겹치지 않게 최대 몇 건" |
| 5 | 힙 시뮬레이션 | 답을 이분 탐색 | "n ≤ 10억" |
| 6 | 가까워지는 방향 그리디 | BFS | "최소 누름 횟수" + 전이 두 개 |
| 7 | 연속일수 기반 그리디 | DP | "권을 아무 날에나 살 수 있다" |

## 요약

- **유형이 안 보이는 문제는 자료구조 이름이 지워진 문제다.** 그 자리에 물리적 제약("마지막에 넣은 것만")과 수치 조건("n ≤ 10억")이 들어가 있다. 그것들이 유형을 지목한다.
- **네 질문을 순서대로 던져라.** ① 그대로 따라 하면 몇 번 도는가 ② 답 후보를 찍어 주면 채점이 쉬운가 ③ 선택이 강제되는가 남는가 ④ 같은 질문을 반복하는가.
- **제약 조건은 장식이 아니다.** "질의가 20만 개"는 전처리를 요구하고, "n ≤ 10억"은 시뮬레이션을 금지하고 답을 이분 탐색하라고 말한다. 지문의 숫자를 읽고 나서 도구를 골라라.
- **그리디와 DP를 가르는 질문은 하나다.** "지금의 선택이 뒤에 영향을 남기는가." 안 남으면(문제 2, 4) 한 번의 순회로 끝나고, 남으면(문제 7) 상태를 정의해야 한다.
- **그리디를 고르면 정렬 키를 말로 정당화해라.** "빨리 끝나는 것을 잡을수록 남는 시간이 많다"까지 못 말하면 그건 그리디가 아니라 운이다. 짧은 순·시작 순은 실제로 반례가 있다.
- **"뒤로 가야 앞으로 갈 수 있다"가 보이면 BFS다.** 노드가 정수 하나여도 그래프이고, 상태 전이가 두 개뿐이어도 최단 경로다.
- **조용히 틀리는 것들을 외워라.** 누적을 대입으로 쓰기, `pre[r]` 과 `pre[r+1]` 혼동, 음수 DP 인덱스, 잘못 잡은 이분 탐색 상한. 넷 다 예외가 나지 않는다.
- **모든 문제에 느린 정답을 함께 짰다.** 전수 순열 대조(문제 2), 힙 시뮬레이션(문제 5), 무식한 거리 갱신(문제 6), 메모 없는 재귀(문제 7). **빠른 풀이의 정당성은 느린 풀이와의 일치로 확인한다.**
