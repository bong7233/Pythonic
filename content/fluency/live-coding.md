# 11.13 라이브 코딩 — 생각을 말하며 푸는 법

::: lead
앞의 열두 절은 혼자 푸는 훈련이었다. 라이브 코딩에는 조건이 하나 더 붙는다. **누가 옆에서 보고 있고, 당신의 머릿속은 그 사람에게 보이지 않는다.** 그래서 여기서 떨어지는 사람은 대개 못 풀어서 떨어지지 않는다. 푸는 과정이 관측되지 않아서 떨어진다. 이 절은 발화 대본을 그대로 싣는다. 되묻는 문장, 무식한 방법을 먼저 꺼내는 문장, 막혔을 때 침묵을 대신하는 문장, 다 짠 코드를 스스로 검증하며 설명하는 문장. 문제를 푸는 절차 자체는 [11.7](#/blank-page-routine)에 있다. 여기서 다루는 것은 그 절차를 **소리 내어** 돌리는 법이다.
:::

## 같은 코드를 낸 두 사람이 갈린다

25분 세션에서 두 지원자가 똑같은 12줄 함수를 완성했다. 한 명은 통과하고 한 명은 떨어졌다. 세션 기록을 나란히 놓으면 이유가 보인다.

```text nolines
  A                                  B
  0:00  read                         0:00  read
  0:01  (silence)                    0:01  ask 4 questions
  0:04  type ..................      0:03  "brute force first: O(n^2)"
  0:20  "done"                       0:06  "bottleneck is the inner loop"
  0:21  Q: empty list?               0:09  type + narrate ..........
  0:22  "ah... let me fix"           0:18  walk one example by hand
  0:24  fix                          0:21  check 3 edge cases
                                     0:23  discuss trade-off
```

두 사람의 최종 화면은 같다. 그런데 A의 기록에서 면접관이 확인할 수 있는 것은 **결과 하나**뿐이다. 요구사항을 확인했는지, 복잡도를 아는지, 경계를 스스로 찾는지 — 전부 관측되지 않았다. 관측되지 않은 능력은 없는 것으로 채점된다.

> 라이브 코딩은 코드를 채점하지 않는다. **관측 가능한 사고 과정**을 채점한다.

이 문장을 받아들이면 전략이 바뀐다. 정답에 도달하는 것보다 **지금 어디까지 갔는지 상대가 알게 하는 것**이 먼저다. 완성하지 못했는데 통과하는 경우가 실제로 있고, 완성했는데 떨어지는 경우도 있다.

::: note 채점표는 대개 다섯 칸이다
| 칸 | 면접관이 확인하는 것 | 침묵하면 |
| --- | --- | --- |
| 문제 이해 | 애매한 자리를 스스로 찾아 되묻는가 | 확인 못 함 → 0점 |
| 접근 설계 | 후보를 두 개 이상 놓고 이유로 고르는가 | 우연히 맞춘 것과 구별 안 됨 |
| 구현 | 코드가 의도와 일치하는가, 이름이 말을 하는가 | 화면으로 보이는 유일한 칸 |
| 검증 | 시키지 않아도 경계를 돌려 보는가 | 면접관이 대신 찾아 준다 → 감점 |
| 협업 | 힌트를 받아들이는가, 모르는 것을 모른다고 하는가 | 확인 못 함 → 0점 |

다섯 칸 중 **화면만으로 채점되는 칸은 하나**다. 나머지 넷은 말로만 전달된다. 과제형에서 같은 항목을 코드와 README로 전달하는 것이 [12.1](#/takehome-eval)과 [12.8](#/readme-submit)이다.
:::

## 25분 세션 하나를 통째로

시간 배분을 고정해 두면 세션 중에 "지금 뭘 해야 하지"를 생각하지 않아도 된다.

```text nolines
  0:00 ─┬─ CLARIFY    되묻기. 질문 3~4개. 코드는 한 줄도 안 쓴다
  0:03 ─┼─ BRUTE      무식한 방법을 말로만. 복잡도까지 붙인다
  0:06 ─┼─ IMPROVE    병목을 지목하고 개선안을 고른다
  0:09 ─┼─ CODE       짜면서 말한다. 한 줄에 한 문장
  0:18 ─┼─ VERIFY     예시를 손으로 통과시킨다. 경계 세 개
  0:23 ─┴─ EXTEND     확장 질문. 트레이드오프로 답한다
```

면접관이 화면에 붙인 문제는 이것이다.

> 도서관 대출 로그가 `(대출일, 회원, 도서)` 튜플 리스트로 주어진다. 같은 회원이 같은 책을 두 번 이상 빌린 경우들 중, **다시 빌리기까지 걸린 간격이 가장 짧은 것의 일수**를 반환하라. 그런 경우가 없으면 `-1`.
>
> ```text nolines
> LOG = [(1, "kim", "A"), (3, "lee", "A"), (5, "kim", "B"),
>        (9, "kim", "A"), (11, "kim", "B"), (12, "lee", "A")]
>
> shortest_regap(LOG) -> 6        # kim 이 B 를 5일과 11일에 빌렸다
> ```

### 0:00–0:03 되묻기

첫 3분에 코드를 쓰지 않는 것이 이 세션의 가장 큰 투자다. 발화는 이렇게 나간다.

> **나** — "먼저 지문을 제 말로 확인하겠습니다. `(회원, 도서)` 쌍이 같은 두 기록의 날짜 차이 중 최솟값을 구하는 문제로 읽었습니다. 맞습니까?"
> **면접관** — "맞습니다."
> **나** — "네 가지만 확인하겠습니다. 첫째, 로그가 대출일 오름차순으로 정렬돼 있다고 가정해도 됩니까?"
> **면접관** — "아니요. 순서는 보장되지 않습니다."
> **나** — "알겠습니다. 그러면 정렬 비용이 붙습니다. 둘째, 같은 회원이 같은 책을 **같은 날** 두 번 빌린 기록이 있을 수 있습니까? 있다면 간격 0이 정답이 되는데요."
> **면접관** — "있을 수 있습니다. 0으로 처리해 주세요."
> **나** — "셋째, 세 번 이상 빌린 경우 모든 쌍을 봐야 합니까, 아니면 인접한 두 번만 봐도 됩니까? 최솟값만 필요하니 정렬 후 인접 쌍만 보면 충분하다고 생각하는데 확인하고 싶습니다."
> **면접관** — "그 판단이 맞습니다."
> **나** — "마지막으로 로그 크기 상한이 있습니까?"
> **면접관** — "20만 건 정도로 보세요."

질문 네 개가 각각 다른 일을 했다. 첫 번째는 **알고리즘을 바꿨다**(정렬이 필요해졌다). 두 번째는 **반환값 규약을 정했다**(0이 유효한 답). 세 번째는 **복잡도를 $O(n^2)$ 에서 내렸다**. 네 번째는 **어디까지 최적화할지**를 정했다. 3분에 네 가지를 얻었다.

::: danger 되묻지 않으면 조용히 다른 문제를 푼다
"정렬돼 있다"를 묻지 않고 가정하면 어떻게 되는지 보자. 지문 예시는 우연히 정렬돼 있어서 통과한다.

```pyrepl
>>> def regap_naive(log):
...     last, best = {}, -1
...     for day, member, book in log:          # 정렬을 안 했다
...         key = (member, book)
...         if key in last and (best == -1 or day - last[key] < best):
...             best = day - last[key]
...         last[key] = day
...     return best
...
>>> regap_naive([(1, "kim", "A"), (9, "kim", "A")])
8
>>> regap_naive([(9, "kim", "A"), (1, "kim", "A")])
-8
```

같은 두 기록을 순서만 바꿨는데 **음수 간격**이 나왔다. 더 나쁜 것은 이 값이 "없음"을 뜻하는 `-1` 과 같은 자리로 흘러든다는 점이다. 예외도 경고도 없다.

이건 코딩 실수가 아니다. **묻지 않은 가정**이다. 그리고 라이브 코딩에서 면접관이 가장 정확하게 관찰하는 것이 이것이다 — 지문에 안 적힌 것을 스스로 발견하는가. 애매한 자리가 어디에 생기는지는 [11.7](#/blank-page-routine)의 표에 있다.
:::

::: tip 되묻기는 "질문"이 아니라 "가정 선언"이어도 된다
면접관이 답을 안 주는 경우가 있다. "당신이 정하세요"가 온다. 그때 침묵하지 말고 **가정을 선언하고 진행한다.**

> "정해지지 않았다면 간격 0을 유효한 답으로 처리하겠습니다. 그렇게 가정한 이유는 같은 날 재대출이 데이터상 가능하고, 0을 제외하면 그 정보가 사라지기 때문입니다. 다른 규칙이 필요하면 말씀해 주세요."

이 한 문단이 채점표의 두 칸(문제 이해, 협업)을 동시에 채운다. **"모르겠습니다"와 "이렇게 가정하겠습니다"는 완전히 다른 점수를 받는다.** 자동 채점 시험에서는 물어볼 사람이 없으니 같은 문장을 주석으로 남긴다.
:::

::: warn 되묻기도 과하면 감점이다
질문은 **셋에서 넷**이다. 열 개를 던지면 그건 요구사항 확인이 아니라 시간 소진이고, 면접관은 "혼자 판단할 수 없는 사람"으로 읽는다.

걸러야 할 질문은 두 종류다. **지문에 이미 답이 있는 질문**("입력이 리스트입니까?")과 **답이 코드를 안 바꾸는 질문**("회원 이름에 공백이 있을 수 있습니까?"). 남길 질문의 기준은 하나다 — **답에 따라 내가 쓸 코드가 달라지는가.** 위 네 질문은 전부 그 기준을 통과했다.
:::

### 0:03–0:06 무식한 방법을 먼저 말한다 — 짜지는 않는다

> **나** — "가장 무식한 방법부터 말씀드리겠습니다. 모든 두 기록 쌍을 보고, 회원과 도서가 같으면 날짜 차의 절댓값을 후보에 넣습니다. 쌍이 $n(n-1)/2$ 개라 $O(n^2)$ 이고, 20만 건이면 200억 번이라 파이썬에서는 확실히 안 됩니다. 다만 이 버전은 **정렬이 필요 없고 틀릴 여지가 거의 없어서** 나중에 빠른 버전과 대조할 기준으로 남겨 두겠습니다."

여기서 한 일은 세 가지다. 하한선을 확보했고(최소한 이건 짤 수 있다), 개선의 방향을 정의했고(줄일 대상은 안쪽 루프), 대조 기준을 예고했다. 그리고 셋 다 **1분 안에 말로** 끝났다.

::: warn 무식한 방법을 "말하는" 것과 "짜기 시작하는" 것은 다르다
초보가 가장 자주 하는 실수가 무식한 방법을 말없이 짜기 시작하는 것이다. 그러면 면접관은 그게 당신의 최종 답인지 중간 단계인지 알 수 없다. 15분 뒤에 지우게 되면 그 15분은 아무 칸도 채우지 못한다.

순서는 **말 → 개선 → 코드**다. 말로 끝난 무식한 방법은 **채점된다.** 아직 안 짰어도 "$O(n^2)$ 로 풀 수 있음을 안다"는 정보는 이미 전달됐다.

예외는 하나다. 개선안이 3분 안에 안 나오면 무식한 방법을 **실제로 짠다.** 동작하는 $O(n^2)$ 가 동작하지 않는 $O(n)$ 보다 언제나 높은 점수다([11.7](#/blank-page-routine)).
:::

### 0:06–0:09 병목을 지목하고 개선안을 고른다

> **나** — "안쪽 루프가 하는 일은 '이 `(회원, 도서)` 를 전에 본 적 있나'입니다. 그건 딕셔너리 조회로 $O(1)$ 이 됩니다. 그리고 최솟값만 필요하니 각 키에서 **직전 대출일 하나만** 기억하면 됩니다. 단 이건 날짜 오름차순을 전제로 하니, 정렬되지 않는다고 하셨으므로 정렬을 먼저 붙입니다.
>
> 여기서 두 가지 방법이 갈립니다. **A**는 전체를 날짜순으로 한 번 정렬한 뒤 한 번 훑는 것이고, **B**는 `(회원, 도서)` 별로 날짜를 모은 다음 각 리스트를 따로 정렬해 인접 쌍만 보는 것입니다. 둘 다 $O(n \log n)$ 입니다. A는 세 줄 더 짧고 B는 정렬 대상이 작게 쪼개져서 실제로는 더 빠를 것 같습니다. **저는 A로 가겠습니다** — 25분 안에 정확하게 짜는 게 우선이고, 성능이 문제가 되면 B로 바꾸면 됩니다. 괜찮습니까?"
> **면접관** — "진행하세요."

이 발화의 마지막 문장이 핵심이다. **두 안을 놓고, 기준을 밝히고, 하나를 고르고, 동의를 구한다.** 여기서 면접관이 "B로 해 보세요"라고 하면 그건 힌트다. 무료로 방향을 얻은 것이니 감사하고 따라가면 된다.

::: tip 힌트를 받아들이는 문장 — 그리고 거절하는 문장
협업 칸이 가장 크게 움직이는 순간이 면접관이 개입할 때다. 받아들일 때는 **무엇을 이해했는지 되풀어서** 말해라. 그냥 "네"는 이해했는지 알 수 없다.

> "정렬 대상을 쪼개라는 말씀으로 이해했습니다. 키별로 리스트를 모으고 각각 정렬하겠습니다."

거절해야 할 때도 있다. 힌트가 지금 상황에 안 맞을 수도 있고, 잘못 알아들었을 수도 있다. 그때는 **이유를 붙여 거절**하고 동의를 구한다.

> "그렇게 하면 정확해지긴 하는데 남은 12분에 다 못 짤 것 같습니다. 지금 버전을 끝내고 시간이 남으면 바꾸는 쪽이 어떻습니까?"

말없이 무시하는 것이 최악이다. 면접관은 자기 힌트가 전달됐는지를 보고 있다.
:::

### 0:09–0:18 짜면서 말한다

내레이션에는 층이 셋 있다. **무엇을 쓰는지**는 말하지 마라 — 화면에 보인다. 말할 것은 나머지 둘이다.

| 층 | 말할 것 | 실제 발화 |
| --- | --- | --- |
| ❌ 무엇 | 화면에 이미 있다 | "for 문을 돌립니다" |
| ✅ 왜 | 그 줄을 쓴 이유 | "키를 튜플로 잡는 이유는 회원과 도서를 함께 봐야 하기 때문입니다" |
| ✅ 무엇을 안 하는지 | 버린 선택지 | "여기서 리스트에 다 모으지 않는 이유는 최솟값만 필요해서입니다" |

```python title="live.py — 0:18 시점의 화면"
def shortest_regap(log):
    """같은 회원이 같은 책을 다시 빌리기까지 걸린 최단 간격(일). 없으면 -1."""
    last = {}                              # (회원, 책) -> 직전 대출일
    best = -1
    for day, member, book in sorted(log):  # 날짜 오름차순이 이 루프의 전제다
        key = (member, book)
        if key in last:
            gap = day - last[key]
            if best == -1 or gap < best:
                best = gap
        last[key] = day
    return best
```

> **나** — "`sorted(log)` 만 쓴 이유는 튜플의 첫 원소가 이미 날짜라서 `key=` 가 필요 없기 때문입니다. 회원 이름이 두 번째 정렬 기준으로 붙지만 답에는 영향이 없습니다. `best` 를 `-1` 로 시작한 게 조금 위험해서 조건을 `best == -1 or gap < best` 로 썼습니다. `float('inf')` 로 시작해서 마지막에 `-1` 로 바꾸는 방법도 있는데, 간격 0이 유효한 답이라 부등호 하나에 실수가 생기지 않는 쪽을 골랐습니다."

**주석 두 줄이 전부다.** 하나는 딕셔너리가 무엇을 담는지, 하나는 정렬이 왜 필요한지. 나머지는 말로 나갔다. 라이브 코딩에서 주석을 많이 쓰면 타이핑 시간만 먹는다. 남길 주석은 **읽어서 안 보이는 것**뿐이다.

::: warn 내레이션을 멈춰야 하는 순간이 있다
루프 조건이나 인덱스 계산처럼 **정신을 다 써야 하는 세 줄**을 쓰는 동안에는 말을 멈춰도 된다. 대신 멈추기 전에 예고해라.

> "여기 경계 계산이 있어서 30초만 조용히 쓰겠습니다."

예고 없는 침묵과 예고된 침묵은 완전히 다르게 읽힌다. 전자는 막힌 것으로 보이고 후자는 집중으로 보인다.
:::

### 0:18–0:23 코드를 설명하며 검증한다

**"다 됐습니다"로 끝내지 마라.** 그 문장은 검증 칸을 통째로 면접관에게 넘긴다. 검증은 세 가지를 순서대로 한다.

**① 예시 하나를 실제로 통과시킨다.** 눈으로 읽지 말고 상태를 찍어라. 공유 에디터에서 실행이 되면 `print` 를, 안 되면 화면에 표를 손으로 적는다.

```pyrepl
>>> LOG = [(1, "kim", "A"), (3, "lee", "A"), (5, "kim", "B"),
...        (9, "kim", "A"), (11, "kim", "B"), (12, "lee", "A")]
>>> last, best = {}, -1
>>> for day, member, book in sorted(LOG):
...     key = (member, book)
...     seen = last.get(key)
...     if seen is not None and (best == -1 or day - seen < best):
...         best = day - seen
...     last[key] = day
...     print(f"day={day:3} key={key} 직전={seen} best={best}")
...
day=  1 key=('kim', 'A') 직전=None best=-1
day=  3 key=('lee', 'A') 직전=None best=-1
day=  5 key=('kim', 'B') 직전=None best=-1
day=  9 key=('kim', 'A') 직전=1 best=8
day= 11 key=('kim', 'B') 직전=5 best=6
day= 12 key=('lee', 'A') 직전=3 best=6
>>> best
6
```

> **나** — "9일에 kim 의 A 가 처음 갱신돼서 8이 됐고, 11일에 kim 의 B 가 6으로 줄였습니다. 12일 lee 는 9라서 갱신하지 않습니다. `best` 가 한 번 줄어든 뒤 다시 커지지 않는 것까지 확인했습니다."

**② 경계를 세 개 돌린다.** 감으로 고르지 말고 [11.8](#/function-completion)의 체크리스트를 소리 내어 훑어라. 이 문제에서 걸리는 것은 빈 입력, 재대출이 없는 경우, 그리고 되묻기에서 얻은 같은 날 재대출이다.

```python title="live.py — 이어서 붙인 검증"
assert shortest_regap(LOG) == 6                                    # 지문 예시
assert shortest_regap([]) == -1                                    # 빈 입력
assert shortest_regap([(1, "kim", "A")]) == -1                     # 한 건
assert shortest_regap([(1, "kim", "A"), (2, "kim", "B")]) == -1    # 재대출 없음
assert shortest_regap([(4, "kim", "A"), (4, "kim", "A")]) == 0     # 같은 날 두 번
assert shortest_regap([(9, "kim", "A"), (1, "kim", "A")]) == 8     # 역순 입력
assert shortest_regap([(1, "k", "A"), (2, "k", "A"), (9, "k", "A")]) == 1  # 3회 대출
print("경계 7건 통과")
```

```text nolines
경계 7건 통과
```

마지막 두 줄이 되묻기의 결과물이다. 역순 입력은 첫 번째 질문에서, 3회 대출은 세 번째 질문에서 나왔다. **되묻기를 안 하면 테스트할 것도 모른다.**

**③ 복잡도를 한 문장으로 말한다.** 시간과 공간을 둘 다.

> **나** — "정렬이 $O(n \log n)$, 훑는 것이 $O(n)$ 이라 전체 $O(n \log n)$ 입니다. 공간은 서로 다른 `(회원, 도서)` 쌍의 개수만큼이라 최악 $O(n)$ 입니다. 20만 건이면 정렬 비용과 훑는 비용이 비슷한 규모일 텐데, 정렬은 C에서 도니까 둘 다 합쳐 1초 안에는 끝날 겁니다."

::: tip 검증 중에 버그를 찾으면 그게 감점이 아니라 가점이다
스스로 찾은 버그는 **검증 칸을 채운다.** 면접관이 찾아 준 버그는 검증 칸을 비운다. 그러니 발견했을 때 당황하지 말고 그대로 소리 내라.

> "역순 입력에서 음수가 나옵니다. 원인은 `sorted` 를 빼먹은 것이고, 위치는 `for` 줄입니다. 지금 붙이겠습니다."

**원인 → 수정 위치 → 수정 방법** 순서로 말해라. "어? 왜 안 되지"를 반복하는 것과는 다르게 읽힌다. 디버깅을 말로 하는 절차는 [11.14](#/exam-debug)에 더 있다.
:::

### 0:23–0:25 확장 질문에 답한다

> **면접관** — "아까 B가 더 빠를 것 같다고 했는데, 실제로 그럴까요?"
> **나** — "정렬 비용이 $O(n \log n)$ 인데 B는 그것을 여러 개의 작은 정렬로 쪼갭니다. 키가 $k$ 개면 대략 $O(n \log(n/k))$ 이라 키가 많을수록 유리합니다. 로그 항의 차이라 자릿수는 안 바뀔 거고, 몇 배 정도라고 예상합니다. 실제로는 측정해 봐야 합니다."

이 답의 마지막 문장이 중요하다. **"측정해 봐야 한다"는 회피가 아니라 정답이다**([5.1](#/profiling)). 그리고 실제로 재면 이렇게 나온다.

::: perf 방향은 맞았고 이유는 틀렸다
로그 20만 건, 대출일은 `0 ~ 10^9` 범위의 난수다. 회원·도서는 `m0`, `b0` 같은 짧은 문자열 이름을 균등 무작위로 뽑았다 — 원소가 문자열이냐 정수냐에 따라 `sorted` 와 튜플 해싱의 절대값이 달라지니 재현할 때 맞춰라. 회원 수 × 도서 수를 바꿔 서로 다른 `(회원, 도서)` 키 개수를 두 종류로 만들었고, 키당 평균 기록 수는 각각 3.5건과 200건이다.

| 측정 대상 | 키 57,904개 (회원 300 × 도서 200) | 키 1,000개 (회원 50 × 도서 20) |
| --- | --- | --- |
| **A 전체** — 한 번 정렬 후 한 번 훑기 | 330 ~ 449 ms | 274 ~ 337 ms |
| **B 전체** — 키별로 모아 각각 정렬 | 140 ~ 181 ms | 59 ~ 86 ms |
| A 중 `sorted(log)` 만 | 167 ~ 222 ms | 169 ~ 217 ms |
| B 중 키별 리스트로 모으기만 | 95 ~ 200 ms | 29 ~ 39 ms |
| B 중 모으기 + 그룹별 `sort()` | 112 ~ 210 ms | 46 ~ 65 ms |

(Python 3.14.0rc2 / Linux 기준 실측. `timeit.repeat(repeat=10)` 을 네 번 반복해 얻은 최솟값과 최댓값의 범위다. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다.)

읽을 것이 셋이다.

1. **B가 두 모양 모두 빠르다.** 예측한 방향은 맞았다. 그리고 배수는 2~5배로 **자릿수는 안 바뀐다** — 로그 항의 차이라는 예측도 맞았다.
2. **그런데 키가 적은 쪽에서 B가 더 유리하다.** "키가 많을수록 유리"라던 예측과 반대다.
3. 아래 세 줄이 이유를 말한다. A의 `sorted(log)` 는 **키 개수와 무관**하다(167~222 대 169~217). 반면 B의 비용은 큰 몫이 **모으는 단계**다 — 한 회차 안에서 나란히 재면 키가 많은 쪽은 B 전체 135밀리초 중 97밀리초(3분의 2 이상), 키가 적은 쪽은 60밀리초 중 30밀리초(절반)가 이 단계다. 다만 이 단계가 키 개수에 **비례하지는 않는다.** 바닥값은 20만 번의 `append` 라 키 개수와 무관하고(키가 4개뿐인 로그로 재면 이 단계만 23밀리초다), 키가 늘면 그 위에 리스트 객체를 만드는 몫이 얹힌다 — 키를 58배 늘려도 3~4배만 는다(29~39 대 95~200). 키마다 리스트 객체를 하나씩 만들기 때문이다. 정작 **정렬 자체는 두 모양 모두 20밀리초 안쪽**이다.

즉 $O(n \log(n/k))$ 라는 예측은 맞았지만, 그 절약분보다 **키당 리스트 객체 생성 비용**이 컸다. 이런 상수는 예측으로 안 나온다([7.2](#/py-ds-cost)).

세션에서 얻어야 할 결론은 배수가 아니다. **25분 안에 A를 고른 판단이 옳았다**는 것이다. 200밀리초 차이는 정확성 리스크를 감수할 값이 아니다. 시간 초과가 실제로 걸렸을 때의 대응은 [8.3](#/tle)에 있다.
:::

## 막혔을 때 — 침묵을 대신하는 문장들

막히는 것은 감점이 아니다. **막힌 채 조용한 것**이 감점이다. 상황별로 쓸 문장을 외워 두면 사고가 멈춘 동안에도 입이 움직인다.

| 상황 | 침묵 대신 말할 것 |
| --- | --- |
| 접근이 아예 안 떠오른다 | "제일 무식한 방법부터 말씀드리고 거기서 줄여 보겠습니다." |
| 두 방법 중 못 고르겠다 | "A는 짧고 B는 빠릅니다. 저는 정확성이 우선이라 A로 가겠습니다." |
| 자료구조 이름이 안 떠오른다 | "제가 필요한 건 '넣을 때마다 최솟값이 유지되는 것'입니다. 이름이 지금 안 떠오르니 동작만 먼저 쓰고 넘어가겠습니다." |
| 틀린 건 알겠는데 어딘지 모른다 | "예시를 세 번째 원소까지 손으로 굴려 보겠습니다." |
| 문법이나 인자 이름이 기억 안 난다 | "정확한 시그니처가 기억나지 않아서 의사코드로 쓰고 넘어가겠습니다. 표준 라이브러리에 있는 함수입니다." |
| 복잡도 계산에 자신이 없다 | "루프가 두 겹이라 최악은 $n^2$ 인데, 안쪽이 조기 종료되니 실제로는 더 작을 겁니다. 정확한 상한은 다시 세어 보겠습니다." |
| 시간이 부족하다 | "남은 5분은 검증에 쓰겠습니다. 지금 코드는 정상 경로까지 동작하고 빈 입력은 미구현입니다." |

세 번째 문장이 특히 값어치가 있다. `heapq` 라는 단어가 안 떠올라도 **필요한 동작을 정확히 서술하면 그 칸은 채워진다.** 도구 이름을 못 대는 것과 필요한 성질을 모르는 것은 완전히 다른 실패다([11.2](#/stdlib-arsenal)).

마지막 문장은 미완성을 선언하는 문장이다. 미완성 자체보다 **미완성을 정확히 아는 것**이 높게 평가된다. 과제형에서 정직한 TODO가 높은 점수를 받는 것과 같은 이유다([12.1](#/takehome-eval)).

::: danger 아는 척은 다른 모든 칸의 점수를 무효로 만든다
모르는 것을 아는 것처럼 말하면 면접관은 **당신이 확실히 말한 다른 모든 것**을 의심하기 시작한다. 채점표 다섯 칸이 전부 깎인다. 되돌릴 방법이 없다.

모른다고 말하는 정확한 형태는 셋으로 나뉜다.

- **모르지만 추론할 수 있다** — "정확히는 모르지만, `dict` 가 해시 테이블이니 최악에는 충돌로 $O(n)$ 이 될 겁니다. 확인해 봐야 합니다."
- **모르고 추론도 안 된다** — "그건 모릅니다. 찾아본 적이 없습니다."
- **틀렸다는 것을 방금 알았다** — "제가 방금 말한 게 틀렸습니다. `deque` 의 중간 인덱싱은 $O(1)$ 이 아니라 $O(n)$ 입니다."

세 번째가 가장 높은 점수를 받는다. 자기 발화를 정정하는 사람은 리뷰에서도 정정한다. 그게 협업 칸이 재는 것이다([12.11](#/self-review)).
:::

## 그 외에 하지 말아야 할 것

- **통째로 지우기.** <kbd>Ctrl</kbd>+<kbd>A</kbd> 후 삭제는 면접관이 방금까지 읽던 문맥을 지운다. 지울 거면 먼저 말해라. "이 접근은 버리겠습니다. 이유는 …입니다." 그리고 지우지 말고 **아래에 새로 써라.** 시간이 남으면 지운다.
- **면접관의 질문을 답만 하고 넘기기.** 면접관이 특정 줄을 가리키며 질문하면 그건 **버그 신호**다. 대개 진짜로 버그가 있다. "왜 여기서 `-1` 인가요?" 는 궁금해서 묻는 게 아니다.
- **사과 반복.** "죄송합니다"를 세 번 하면 남은 시간이 사과로 채워진다. 한 번이면 충분하고, 그 자리에 다음 행동을 넣어라.
- **문제를 다시 읽으며 시간 보내기.** 세 번째 읽기부터는 새 정보가 안 나온다. 그때는 [11.7](#/blank-page-routine)의 탈출 절차로 내려가라 — 입력을 최소로 줄이고 손으로 굴린다.
- **완성 후 침묵.** 남은 시간에 아무것도 안 하면 검증 칸이 빈다. 할 게 없으면 확장 질문을 스스로 던져라. "입력이 스트리밍으로 들어온다면 이 코드에서 정렬을 뺄 수 있는지 생각해 보고 있습니다."

## 공유 에디터라는 물리적 조건

원격 라이브 코딩은 대개 브라우저 편집기에서 진행된다. 여기서 잃는 것이 세 가지다.

첫째, **자동완성과 시그니처 힌트가 없다.** `heapq.nlargest(n, iterable, key=...)` 의 인자 순서를 손으로 기억해야 한다. 둘째, **실행이 안 되거나 매우 느리다.** 셋째, **되돌리기 이력이 짧다.**

여기에 맞춘 습관은 셋이다.

1. **실행 없이 읽히는 코드를 써라.** 한 줄에 두 가지를 하지 말고, 중간 결과를 변수에 담아 이름을 붙여라. `print` 대신 사람이 읽고 판정하게 만드는 것이 목적이다.
2. **`assert` 를 코드 아래에 쌓아라.** 실행이 되면 그게 테스트고, 안 되면 그게 명세다. 어느 쪽이든 검증 칸을 채운다([12.6](#/test-strategy)).
3. **기억이 흐린 API는 쓰지 마라.** `bisect.insort_right` 의 인자 순서가 헷갈리면 `sort()` 를 써라. 라이브 코딩에서 화려한 한 줄은 이득이 없고, 틀린 한 줄은 손해가 크다.

::: cote 자동 채점 시험에도 라이브 코딩 습관이 이득이다
사람이 안 보는 시험에서도 셋은 그대로 남는다.

- **되묻기 → 가정 주석.** 물어볼 사람이 없으면 `# 가정:` 으로 남긴다. 나중에 오답을 되짚을 때 이 줄이 범위를 절반으로 줄인다.
- **무식한 방법 → 대조 기준.** 지우지 말고 남겨 무작위 교차 검증에 써라([11.7](#/blank-page-routine)).
- **검증 3종 → 제출 전 루틴.** 예시 통과, 경계 세 개, 복잡도 확인. [11.8](#/function-completion)의 6분 루틴이 이것의 확장판이다.

라이브 코딩과 자동 채점의 차이는 **말로 하는가 주석으로 남기는가**뿐이다. 절차는 같다.
:::

## 이 능력은 혼자서 훈련할 수 있다

면접관이 없어도 훈련은 된다. 조건은 하나다. **소리를 내야 한다.** 머릿속으로 하는 리허설은 침묵 연습이다.

1. **녹음하며 푼다.** 타이머 25분, 화면 녹화나 음성 녹음. 문제는 [11.12](#/drill-mixed)나 [11.9](#/drill-string)에서 아직 안 본 것을 고른다.
2. **다시 들으며 침묵 구간을 잰다.** 30초 넘는 침묵이 몇 번 있었는지, 그 순간에 무엇을 하고 있었는지 적는다.
3. **침묵 하나마다 문장 하나를 붙인다.** 위 표에서 골라도 되고 직접 만들어도 된다. 다음 회차에 그 문장을 실제로 말한다.

3주면 침묵 구간이 눈에 띄게 줄어든다. 이건 성격의 문제가 아니라 **문장 재고**의 문제다. 말할 문장이 있으면 말한다.

## 요약

- 라이브 코딩은 코드가 아니라 **관측 가능한 사고 과정**을 채점한다. 채점표 다섯 칸 중 화면만으로 채워지는 것은 **구현 한 칸**뿐이고, 나머지 넷(문제 이해·접근 설계·검증·협업)은 말로만 전달된다.
- 25분을 고정 배분해라. **되묻기 3분 → 무식한 방법 3분 → 개선 3분 → 코딩 9분 → 검증 5분 → 확장 2분.** 첫 3분에 코드를 쓰지 않는 것이 가장 큰 투자다.
- 되묻기의 대가는 즉시 돌아온다. "정렬돼 있습니까"를 안 물으면 같은 두 기록의 순서만 바뀌어도 **음수 간격이 `-1` 자리로 조용히 흘러든다.** 면접관이 답을 안 주면 **가정을 선언하고 진행해라** — "모르겠습니다"와는 다른 점수를 받는다.
- 무식한 방법은 **말로만** 먼저 꺼낸다. 하한선·개선 방향·대조 기준 세 가지가 1분에 확보된다. 개선안이 3분 안에 안 나오면 그때는 실제로 짜라 — 동작하는 $O(n^2)$ 가 동작하지 않는 $O(n)$ 보다 높다.
- 내레이션에서 **무엇을 쓰는지는 말하지 마라.** 화면에 있다. 말할 것은 **왜 그 줄인지**와 **무엇을 안 하는지**다. 집중이 필요한 세 줄 앞에서는 침묵을 예고해라.
- "다 됐습니다"로 끝내면 검증 칸을 면접관에게 넘긴다. **예시 하나를 상태까지 찍어 통과 → 경계 세 개 → 복잡도 한 문장**까지가 한 세트다. 스스로 찾은 버그는 가점이다.
- 막힘은 감점이 아니고 **막힌 채 조용한 것**이 감점이다. 상황별 문장을 재고로 들고 있어라. 도구 이름이 안 떠올라도 **필요한 동작을 정확히 서술하면 그 칸은 채워진다.**
- **아는 척은 다른 모든 칸을 무효로 만든다.** 자기 발화를 정정하는 것이 가장 높은 점수를 받는다.

::: quiz 실습 과제 — 타이머를 켜고 소리 내어 풀어라
전부 **25분 타이머 + 녹음**으로 진행한다. 그리고 각 과제의 산출물에 **되묻기 질문 목록**과 **가정 주석**이 반드시 들어가야 한다. 코드만 있는 답은 이 절의 과제를 안 한 것이다.

**1. 되묻기가 답을 바꾸는 것을 직접 확인하라 (25분)**

> 엘리베이터 호출 로그가 `(초, 층, "UP"|"DOWN")` 리스트로 주어진다. 같은 층·같은 방향 호출이 **`w` 초 이내에** 다시 들어오면 중복 누름으로 보고 무시한다. 실제로 처리된 호출만 입력 순서대로 반환하라.
>
> ```python
> C = [(0, 3, "UP"), (1, 3, "UP"), (5, 3, "UP"), (5, 3, "DOWN"), (12, 3, "UP")]
> dedupe_calls(C, 4)   # -> [(0, 3, 'UP'), (5, 3, 'UP'), (5, 3, 'DOWN'), (12, 3, 'UP')]
> dedupe_calls(C, 0)   # -> C 그대로
> dedupe_calls([(7, 1, "DOWN"), (7, 1, "DOWN")], 0)  # -> [(7, 1, 'DOWN')]
> ```

이 지문에는 **정해지지 않은 것이 최소 셋** 있다. 찾아서 질문 문장으로 적어라. 그중 하나는 "`w` 초 이내의 기준이 **직전에 처리한 호출**인가 **직전 입력**인가"다. 위 예시는 전자 기준이다. **후자로 가정한 함수도 짜서 같은 입력에 대해 결과가 달라지는 것을 출력으로 보여라.** 어느 쪽이 옳은지가 아니라, 가정이 답을 바꾼다는 사실이 이 과제의 답이다.

**2. 무식한 방법을 말로 먼저 꺼내라 (25분)**

> 초 단위 이벤트 시각 리스트가 주어진다(정렬 보장 없음). 길이 `w` 초의 닫힌 창 `[t, t+w]` 안에 들어오는 이벤트가 가장 많을 때 그 개수를 반환하라.
>
> ```python
> busiest_window([1, 2, 3, 9, 10], 2)   # -> 3
> busiest_window([4, 4, 4], 0)          # -> 3
> busiest_window([1, 4, 7], 2)          # -> 1
> busiest_window([10, 1, 2, 11], 1)     # -> 2
> busiest_window([], 5)                 # -> 0
> ```

순서를 지켜라. ① 무식한 $O(n^2)$ 버전을 **먼저 녹음으로 말하고** 짠다. ② 그다음 개선판을 짠다. ③ 두 구현을 무작위 입력 20,000건으로 대조한다. 녹음에서 ①과 ② 사이에 **"병목은 …이고 그것을 …로 바꿉니다"** 라는 문장이 실제로 들려야 한다.

**3. 확장 질문을 스스로 던져라 (15분)**

2번 함수가 **개수 대신 `(개수, 창 시작 시각)`** 을 반환하도록 고쳐라. 동점이면 가장 빠른 시작 시각을 고르고, 빈 입력은 `(0, None)` 이다.

```python
busiest_window_at([1, 2, 3, 9, 10], 2)   # -> (3, 1)
busiest_window_at([10, 1, 2, 11], 1)     # -> (2, 1)
busiest_window_at([], 5)                 # -> (0, None)
```

고치기 전에 **"어디가 바뀌고 어디는 안 바뀌는지"를 먼저 소리 내어 말하고** 녹음하라. 그 예측과 실제 diff를 비교해라. 예측이 틀린 자리가 당신이 자기 코드를 덜 이해한 자리다.

**4. 침묵을 계량하라 (녹음 재생)**

1~3번 녹음을 다시 듣고 표를 채워라. 열은 **침묵 시작 시각 / 길이(초) / 그때 하던 일 / 다음에 쓸 문장** 넷이다. 30초 넘는 침묵이 세 번 이상이면, 다음 회차에는 그 세 자리에 넣을 문장을 미리 적어 두고 시작해라.

**5. 검증을 코드로 남겨라**

1~3번 전부에 `assert` 를 최소 다섯 개 붙여라. 그중 셋은 **경계**여야 한다(빈 입력 / 원소 한 개 / 전부 같은 값). 그리고 각 함수 아래에 시간·공간 복잡도를 **한 줄 주석**으로 적어라. 말로 못 하는 복잡도는 아직 모르는 복잡도다.
