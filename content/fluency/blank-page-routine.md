# 11.7 백지에서 시작하는 5단계 루틴

::: lead
앞의 다섯 절에서 무기를 채웠다. 그런데 무기고가 가득해도 백지 앞에서는 여전히 첫 줄이 안 나온다. 무엇을 꺼낼지 정하는 **순서**가 없기 때문이다. 이 절은 그 순서를 고정한다. 문제를 읽은 순간부터 통과하는 함수가 나올 때까지 매번 똑같이 밟는 다섯 단계다. 영감은 필요 없다. 각 단계는 **다음 단계가 쓸 산출물**을 하나씩 남기고, 마지막 단계는 스스로 채점된다. 실제 문제 두 개에 이 루틴을 끝까지 시연하고, 막혔을 때의 탈출 절차까지 붙인다.
:::

## 숙련자는 매번 다르게 시작하지 않는다

초보와 숙련자의 차이는 아이디어의 질이 아니다. **시작 방식이 일정한가**다.

초보의 화면은 이렇게 흘러간다. 문제를 읽는다 → 머릿속에서 완성된 풀이를 찾는다 → 안 나온다 → 문제를 다시 읽는다. 이 순환에는 **출력이 없다.** 20분이 지나도 파일은 비어 있다. 반면 숙련자의 화면에는 20분 뒤 무언가가 남아 있다. 완성된 풀이가 아니어도 자기 말로 옮긴 한 문장, 손으로 굴린 표, 함수 이름 하나는 남는다. **그게 다음 20분의 재료다.**

그래서 이 루틴의 설계 원칙은 하나다.

> **모든 단계는 눈에 보이는 산출물을 하나 남긴다. 산출물이 없으면 그 단계를 안 한 것이다.**

```text nolines
  ┌──────────────────────┐
  │ (1) RESTATE          │   문제를 내 말로 다시 쓴다
  └───────────┬──────────┘   남는 것: 한 문장 + 입력/출력 타입
              │
              ▼
  ┌──────────────────────┐
  │ (2) ROLL             │   예시를 손으로 굴린다
  └───────────┬──────────┘   남는 것: 상태 변화 표 한 개
              │
              ▼
  ┌──────────────────────┐
  │ (3) PICK             │   굴린 흔적에서 자료구조를 고른다
  └───────────┬──────────┘   남는 것: 도구 이름 한두 개
              │
              ▼
  ┌──────────────────────┐
  │ (4) SKELETON         │   시그니처와 검증문을 먼저 쓴다
  └───────────┬──────────┘   남는 것: 실행되는(그리고 실패하는) 파일
              │
              ▼
  ┌──────────────────────┐
  │ (5) FILL             │   안을 채워 검증문을 통과시킨다
  └───────────┬──────────┘   남는 것: 통과하는 함수
              │
              └──────▶ 막히면 (2)로 돌아간다. 앞으로 밀지 마라.
```

::: note 11.1의 네 지점과 이 다섯 단계는 다른 물건이다
[11.1](#/fluency-gap)에서 손이 멈추는 지점을 넷으로 나눴다(번역 / 도구 선택 / 골격 / 검증). 그건 "나는 어디서 막히는가"를 기록하는 **진단 좌표**다. 이 절의 다섯 단계는 **실행 절차**다.

차이는 ② ROLL 하나다. 진단할 때는 잘 안 보이는 단계인데, 코드를 만들어 내는 힘의 대부분이 여기서 나온다. 손으로 굴리지 않고 고른 도구는 추측이다.
:::

## 단계 ① 문제를 내 말로 다시 쓴다

문제 문장을 그대로 다시 읽는 것은 이 단계가 아니다. **원문을 보지 않고** 다음 세 줄을 쓸 수 있어야 이 단계가 끝난다.

```text nolines
입력:  무엇이 몇 개, 각각 어떤 타입
출력:  어떤 타입, 없을 때는 무엇을 반환
규칙:  한 줄에 하나씩. 번호를 붙인다
```

세 줄 중 가장 값어치 있는 것은 **출력** 줄이다. 반환 타입을 정하면 함수 이름이 따라 나오고, 이름이 정해지면 본문이 따라 나온다. 반대 순서는 성립하지 않는다.

::: warn 내 말로 못 쓰면 아직 읽은 게 아니다
규칙을 옮겨 쓰다 보면 원문에서 지나쳤던 문장이 하나씩 튀어나온다. "같은 회원은 한 번만", "동점이면 사전순", "출력은 정수" 같은 것들이다. **못 옮겨 쓴 규칙은 안 읽은 규칙이고, 안 읽은 규칙은 채점에서 발견된다.**

이 단계를 건너뛴 대가는 5분이 아니다. 규칙 하나를 빠뜨린 채 20분짜리 코드를 다 짜면, 그 규칙을 넣기 위해 구조를 다시 짜야 한다.
:::

### 애매한 문장은 질문 목록으로 남긴다

문제 문장은 자주 불완전하다. 자주 비어 있는 자리는 정해져 있다.

| 비어 있는 자리 | 물어볼 것 |
| --- | --- |
| 동점 | 같은 값일 때 순서는 무엇으로 정하는가 |
| 빈 입력 | 입력이 비면 무엇을 반환하는가 (예외인가 기본값인가) |
| 범위 밖 | 0이나 음수가 들어올 수 있는가 |
| 중복 | 같은 항목이 두 번 나올 수 있는가, 그럼 한 번으로 세는가 |

과제형이나 면접이라면 **되묻는다.** 되묻는 것 자체가 평가 항목이다([11.13](#/live-coding), [12.2](#/requirements-to-model)). 자동 채점 시험이라면 물어볼 사람이 없으니 **가정을 코드에 명시로 남긴다.**

```python
# 가정: n >= 1. n == 0 은 문제에 정의가 없어 예외로 막는다.
if n <= 0:
    raise ValueError("n은 1 이상이어야 한다")
```

::: danger 정의되지 않은 입력에서 두 구현은 서로 다른 답을 낸다
아래에서 시연할 좌석 문제를 두 가지 방식으로 짜고, 가드 없이 `n = 0` 으로 불러 보면 이렇게 된다. 같은 문제를 푼 두 구현이 **조용히 다른 값**을 낸다.

```text nolines
find_block(["OOXOOO"], 0)   -> (0, 3)   /  (0, 0)
find_block(["XX"], 0)       -> (0, 1)   /  (0, 0)
                               세는 방식    문자열 검색 방식
```

검색 쪽이 `(0, 0)` 을 내는 이유는 `"O" * 0` 이 빈 문자열이고, 빈 문자열은 어디서나 발견되기 때문이다.

```pyrepl
>>> "OOXOOO".find("")
0
>>> "XX".find("")
0
```

어느 쪽도 틀리지 않았다. **문제가 정하지 않은 것을 구현이 각자 정한 것**이다. ① 단계에서 이 자리를 찾으면 `raise` 한 줄로 닫히고, 못 찾으면 원인 불명의 오답으로 돌아온다.
:::

## 단계 ② 예시를 손으로 굴린다

이 단계가 루틴의 심장이고, 가장 많이 생략된다. "예시 보니까 알겠네"에서 멈추기 때문이다.

굴린다는 것은 **입력의 원소를 하나씩 처리하면서, 그 순간 내가 무엇을 알고 있는지 적는 것**이다. 종이든 주석이든 좋다. 다만 **적어야** 한다. 머릿속으로 굴리면 세 번째 원소에서 앞의 두 개를 잊는다.

좌석 배치 `"OOXOOO"` 에서 연속 3석을 찾는 과정을 굴리면 이렇게 된다.

```text nolines
seat:    O   O   X   O   O   O
c:       0   1   2   3   4   5
run:     1   2   0   1   2   3
                             ^ 여기서 run == 3 이 됐다
                               시작 열 = 5 - 3 + 1 = 3
```

이 표 하나가 세 가지를 동시에 결정한다.

1. **무엇을 기억해야 하는가** — `run` 하나뿐이다. 리스트도 딕셔너리도 필요 없다.
2. **언제 답이 나오는가** — `run` 이 `n` 에 도달하는 순간. 즉 조기 반환이다.
3. **답을 어떻게 계산하는가** — 끝 열에서 `n - 1` 을 뺀다. 이 뺄셈이 나중에 off-by-one이 되는 자리다.

세 줄을 코드로 옮기면 그게 본문이다. **손으로 굴린 절차가 곧 알고리즘이다.**

::: tip 예시는 세 개를 굴린다 — 정상, 경계, 반례
문제에 붙은 예시는 대개 정상 케이스뿐이다. 나머지 둘은 직접 만든다.

- **경계**: 빈 입력, 원소 한 개, 전부 같은 값, 답이 맨 앞이나 맨 끝인 것.
- **반례**: 답이 없어야 하는 입력. 반환값이 `None` 인지 `-1` 인지 `[]` 인지가 여기서 정해진다.

세 개를 굴리는 5분이 ⑤ 단계의 디버깅 20분을 없앤다. 경계 케이스 목록은 [11.8](#/function-completion)에 체크리스트로 있다.
:::

## 단계 ③ 굴린 흔적에서 자료구조를 고른다

여기서 하는 일은 도구를 **떠올리는** 것이 아니라 **읽어내는** 것이다. ② 에서 적은 표를 보고 질문 하나만 던진다.

> **굴리는 동안 내가 계속 들고 있던 것은 무엇인가?**

그 답이 자료구조다.

::: note 굴린 흔적 → 도구 변환표
| 굴리는 동안 한 일 | 자료구조 |
| --- | --- |
| 숫자 하나만 갱신했다 (개수, 최댓값, 누적) | 지역 변수 하나 |
| 앞에서 본 값을 나중에 다시 찾았다 | `dict` (값 → 위치나 개수) |
| "이 값을 본 적 있나"만 물었다 | `set` |
| 방금 넣은 것을 먼저 꺼냈다 | 리스트를 스택으로 |
| 앞에서 꺼내고 뒤에 넣었다 | `deque` |
| 항목마다 여러 개를 모아 뒀다 | `defaultdict(list)` |
| 매번 가장 작은 것 하나만 꺼냈다 | `heapq` |
| 표를 다 채운 뒤 순서대로 다시 봤다 | `sorted` |

각 도구를 언제 쓰고 언제 안 쓰는지는 [11.2](#/stdlib-arsenal), [11.5](#/dict-set-patterns), [11.6](#/sorting-as-tool)에 있다. 이 절의 주장은 하나다. **표를 먼저 그리면 이 변환은 기계적이다.** 표가 없으면 도구 목록을 처음부터 훑는 수밖에 없고, 그게 5분씩 잡아먹는다.
:::

::: danger 도구를 먼저 정하고 문제를 거기 맞추지 마라
최근에 힙을 공부했으면 힙으로 풀고 싶어진다. 이건 실력이 아니라 편향이다. 증상은 분명하다. **"이 문제는 무엇으로 푸는 문제인가"를 먼저 묻고 있다면 방향이 거꾸로다.** 물어야 할 것은 "굴릴 때 내가 무엇을 들고 있었나"다.

위 좌석 문제는 슬라이딩 윈도우로도, 행을 `X` 로 잘라 조각 길이를 재는 방식으로도 풀린다. 다 맞는 풀이다. 그런데 굴린 표에 남은 것은 `run` 이라는 정수 하나뿐이었다. **표가 가리키는 가장 싼 도구를 집어라.** 정수 하나로 되는 문제에 자료구조를 얹으면 실수할 자리만 늘어난다.
:::

## 단계 ④ 함수 골격과 검증문을 먼저 쓴다

여기서 처음 편집기에 코드를 쓴다. 그런데 **본문은 쓰지 않는다.** 쓰는 것은 넷이다.

```python title="seat_block.py — 골격. 이 상태로 한 번 실행한다"
SEATS = ["OOXOOO", "XOOXXO", "OOOOOX"]


def find_block(rows, n):
    """연속된 빈 좌석 n칸의 시작 위치 (행, 열). 없으면 None."""
    return None                       # 아직 안 채웠다


assert find_block(SEATS, 3) == (0, 3)
assert find_block(SEATS, 2) == (0, 0)
assert find_block(SEATS, 4) == (2, 0)
assert find_block(SEATS, 7) is None
assert find_block([], 1) is None
assert find_block(["XXX"], 1) is None
print("전부 통과")
```

1. **이름** — 값을 반환하면 명사·형용사형, 상태를 바꾸면 동사형([1.1](#/objects-names)).
2. **시그니처** — 인자 이름과 개수, 그리고 순서.
3. **한 줄 docstring** — ① 의 출력 줄을 그대로 옮긴다. 반환 타입과 "없을 때"를 명시한다.
4. **검증문** — ② 에서 굴린 예시를 `assert` 로 박는다.

::: tip 골격을 실행해서 실패를 먼저 확인해라
위 파일을 지금 실행하면 이렇게 끝난다.

```text nolines
Traceback (most recent call last):
  File ".../seat_block.py", line 9, in <module>
    assert find_block(SEATS, 3) == (0, 3)
           ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
AssertionError
```

이 실패는 좋은 소식이다. **검증문이 실제로 작동한다는 증거**다. 이걸 확인해 두지 않으면 ⑤ 를 다 채운 뒤의 "통과했다"가 사실은 검증문이 비어 있었던 것일 수도 있다.

`assert` 로 충분하다. 코딩테스트 환경에는 pytest가 없다. 과제형이라면 이 `assert` 들이 그대로 테스트 파일의 초안이 된다([6.1](#/pytest), [12.6](#/test-strategy)).
:::

이 단계의 진짜 효과는 심리적이다. 골격까지 오면 **화면에 빈 곳이 한 군데밖에 없다.** 백지가 사라지고 빈칸 채우기가 된다.

## 단계 ⑤ 안을 채우고 검증문을 통과시킨다

채우는 순서도 정해져 있다. **확실한 줄부터** 쓴다.

```text nolines
1. 정규화       입력을 다루기 쉬운 형태로 (분 단위로, 소문자로, 정수로)
2. 준비         ③ 에서 고른 자료구조를 만든다
3. 순회         하나씩 처리한다. ② 의 표가 그대로 루프 본문이다
4. 반환         답을 만든다. 못 찾은 경우도 반드시 처리한다
```

막히면 4번부터 거꾸로 쓴다. "답의 형태"를 먼저 적으면 그 앞이 무엇이어야 하는지 좁혀진다.

::: warn ⑤ 단계에서는 최적화하지 않는다
통과하지 않는 코드를 빠르게 만드는 것은 의미가 없다. 순서는 **통과 → 측정 → 개선**이다. 이 순서를 뒤집는 것이 파이썬에서 가장 흔한 시간 낭비다([5.1](#/profiling)).

시간 초과가 실제로 나면 그때 바꾼다. 무엇을 바꿀지는 [8.3](#/tle)과 [7.2](#/py-ds-cost)에 있다.
:::

## 시연 I — 좌석 배치도에서 연속 좌석 찾기

지금까지의 다섯 단계를 실제로 밟는다. 문제는 이것이다.

> 공연장 좌석 배치도가 문자열 리스트로 주어진다. `'O'` 는 빈 좌석, `'X'` 는 예약된 좌석이다. **같은 행에서 연속된 `n`석**을 찾아 시작 위치를 `(행, 열)` 로 반환하라. 가능한 자리가 여러 개면 위쪽 행이 먼저, 같은 행이면 왼쪽이 먼저다. 없으면 `None`.
>
> ```text nolines
> rows = ["OOXOOO",
>         "XOOXXO",
>         "OOOOOX"]
>
> find_block(rows, 3) -> (0, 3)
> find_block(rows, 2) -> (0, 0)
> find_block(rows, 4) -> (2, 0)
> find_block(rows, 7) -> None
> ```

### ① 내 말로

```text nolines
입력:  문자열 리스트 rows ('O'/'X' 로만 구성), 정수 n
출력:  (행, 열) 정수 튜플. 없으면 None
규칙:  1. 연속은 한 행 안에서만. 행을 넘어가지 않는다
       2. 위 행 우선, 같은 행이면 작은 열 우선
       3. 행마다 길이가 다를 수 있다고 가정한다 (문제에 언급 없음)
       4. n <= 0 은 정의가 없다 -> 예외로 막는다
```

규칙 3과 4가 원문에 없다. 이게 ① 단계의 수확이다. 규칙 3을 명시했으니 열 개수를 미리 하나로 정해 두는 코드는 쓰지 않는다.

### ② 손으로 굴리기

첫 행을 `n = 3` 으로 굴린 표는 앞에서 이미 봤다. 그 표를 얻는 과정을 REPL에서도 그대로 재현할 수 있다.

```pyrepl
>>> row = "OOXOOO"
>>> runs = []
>>> run = 0
>>> for seat in row:
...     run = run + 1 if seat == "O" else 0
...     runs.append(run)
...
>>> runs
[1, 2, 0, 1, 2, 3]
```

경계 예시도 굴린다. `rows = []` 이면 루프가 안 돌아 `None`, `rows = ["XXX"], n = 1` 이면 `run` 이 1이 되는 순간이 없어 `None` 이다. **두 경계가 "루프를 다 돌고 나서 `None`" 이라는 같은 출구로 나간다.** 출구가 하나면 구조가 단순해진다.

### ③ 도구

굴리는 동안 들고 있던 것은 `run` 정수 하나. 컨테이너 없음. 발견 즉시 반환.

후보가 하나 더 있다. 각 행을 문자열로 보고 `"O" * n` 을 찾는 것이다.

```pyrepl
>>> "OOXOOO".find("OOO")
3
>>> "OOXOOO".find("OOOO")
-1
```

한 줄로 끝난다. 둘 다 맞는 풀이지만 **세는 쪽**을 본문으로 고른다. 변형에 강하기 때문이다. 빈 좌석 표시가 두 종류로 늘거나 "가장 긴 구간"을 물으면 `find` 는 못 쓰고, 세는 쪽은 조건 한 줄만 바뀐다([11.3](#/string-toolkit)).

### ④ 골격

앞의 골격 그대로다. 예시 네 개와 경계 두 개를 `assert` 로 박는다.

### ⑤ 채우기

```python title="seat_block.py"
SEATS = ["OOXOOO", "XOOXXO", "OOOOOX"]


def find_block(rows, n):
    """연속된 빈 좌석 n칸의 시작 위치 (행, 열). 없으면 None."""
    if n <= 0:
        raise ValueError("n은 1 이상이어야 한다")
    for r, row in enumerate(rows):
        run = 0                                   # 지금까지 이어진 'O' 개수
        for c, seat in enumerate(row):
            run = run + 1 if seat == "O" else 0
            if run == n:                          # 방금 n칸이 됐다
                return (r, c - n + 1)             # 시작 열은 n-1칸 앞
    return None


assert find_block(SEATS, 3) == (0, 3)
assert find_block(SEATS, 2) == (0, 0)
assert find_block(SEATS, 4) == (2, 0)
assert find_block(SEATS, 7) is None
assert find_block([], 1) is None
assert find_block(["XXX"], 1) is None
print("전부 통과")
```

```text nolines
전부 통과
```

본문 9줄이다. 새로운 개념은 하나도 없다. `enumerate` 와 정수 하나뿐이다. **이 문제가 어려웠던 이유는 도구를 몰랐기 때문이 아니라 순서가 없었기 때문이다.**

::: danger 이 문제에서 실제로 틀리는 두 곳
**1. 시작 열 대신 끝 열을 반환한다.** `return (r, c)` 로 쓰면 이렇게 된다.

```text nolines
n=3 -> (0, 5)     정답은 (0, 3)
n=2 -> (0, 1)     정답은 (0, 0)
```

②의 표에 `시작 열 = 5 - 3 + 1` 을 적어 뒀다면 이 실수는 나오지 않는다. 굴린 표가 off-by-one을 막는 방식이 이것이다.

**2. `run = 0` 을 행 루프 밖에 둔다.** 그러면 앞 행의 연속이 다음 행으로 새어 나간다.

```text nolines
find_block(["OOO", "OOO"], 4)  -> (1, -3)     정답은 None
find_block(SEATS, 6)           -> (2, -1)     정답은 None
```

**음수 열이 나왔다.** 채점기에서는 `IndexError` 나 조용한 오답으로 나타난다. 가드를 걸 거면 **반환할 값에** 걸어라. `assert 0 <= c` 는 아무것도 못 잡는다 — `c` 는 루프 변수, 즉 끝 열이라 언제나 0 이상이고, 새어 나가는 값은 `c - n + 1` 이다. `start = c - n + 1` 로 한 번 뽑아 두고 `assert 0 <= start` 를 걸면 위 두 호출이 반환 전에 터진다([11.14](#/exam-debug)).
:::

::: tip 조건이 바뀌면 무엇이 바뀌는가
- **"가장 긴 연속 구간의 길이"** 로 바뀌면 → 조기 반환을 없애고 `best = max(best, run)` 로. 루프 구조는 그대로다.
- **행을 넘어 이어져도 된다면** → `run = 0` 을 행 루프 밖으로 옮긴다. 단 그것만으로는 **세는 규칙만** 그 문제의 정답이 되고 반환값은 여전히 깨진다 — 방금 본 음수 열이 바로 그것이다. 시작 위치가 행 경계를 넘으니 좌표를 1차원으로 펴서 계산하고 되돌려야 한다. 행 길이가 모두 같다면 `idx = r * len(row) + c - n + 1` 을 구해 `divmod(idx, len(row))` 를 반환하면 되고, 그러면 `["OOO", "OOO"]`, `n=4` 가 `(0, 0)`, `SEATS`, `n=6` 이 `(1, 5)` 를 낸다. **부등호와 초기화 위치가 곧 요구사항이다.**
- **열 방향(같은 열의 연속)이면** → `zip(*rows)` 로 전치한 뒤 같은 함수를 쓴다([11.4](#/array-grid)). 다만 반환값의 행·열을 되돌리는 것을 잊지 마라. 그리고 `zip` 은 **가장 짧은 행에서 잘린다.** `["OOO", "OO", "OOO"]` 를 전치하면 3열이 아니라 2열만 남고, 잃은 열은 조용히 사라진다. ① 의 규칙 3처럼 행 길이가 다를 수 있으면 `itertools.zip_longest(*rows, fillvalue="X")` 로 빈자리를 예약석으로 메운 뒤 전치해라.
:::

## 시연 II — 유형이 안 보이는 문제

두 번째는 한 단계 어렵다. 읽어도 무슨 유형인지 안 보이는 종류다.

> 창고의 하루치 재고 변화가 정수 리스트로 주어진다. 양수는 입고, 음수는 출고다. **재고가 기간 시작 직전과 정확히 같아지는 가장 긴 연속 기간의 길이**를 반환하라. 그런 기간이 없으면 0.
>
> ```text nolines
> longest_flat([1, -1, 3, -3])       -> 4
> longest_flat([2, -1, -1, 5])       -> 3
> longest_flat([5, -5, 2, 1, -3, 4]) -> 5
> longest_flat([1, 2, 3])            -> 0
> longest_flat([0])                  -> 1
> longest_flat([])                   -> 0
> ```

### ① 내 말로

```text nolines
입력:  정수 리스트 deltas (양수 입고, 음수 출고). 빈 리스트 가능
출력:  정수 길이. 없으면 0 (None 이 아니다)
규칙:  1. "시작 직전과 같아진다" = 그 구간의 변화량 합이 0
       2. 연속 구간이다. 건너뛸 수 없다
       3. 가장 긴 것 하나의 길이만 답한다. 위치는 안 묻는다
       4. 초기 재고는 주어지지 않는다 -> 답에 영향이 없다는 뜻이다
```

규칙 1이 이 문제의 절반이다. **"같아진다"를 "합이 0"으로 바꾸는 것**이 번역이다. 규칙 4도 값어치가 있다. 초기 재고 없이 답이 정해진다는 것을 확인하면, 그 값을 어디에 넣을지 고민하지 않는다.

### ② 손으로 굴리기

`[2, -1, -1, 5]` 를 굴린다. 날짜 경계마다 **그때까지의 누적 재고**를 적는다.

```text nolines
day:      0    1    2    3    4
delta:         +2   -1   -1   +5
stock:    0    2    1    0    5
          ^______________^
          같은 값 0 이 두 번 나왔다 -> 그 사이 3일이 답
```

여기서 아이디어가 튀어나온다. **누적값이 같은 두 지점 사이의 합은 0이다.** 찾을 것은 "합이 0인 구간"이 아니라 **"같은 누적값이 두 번 나오는 자리"** 다.

`day 0` 칸을 적은 것이 결정적이다. 아무것도 처리하지 않은 상태의 0을 안 적으면 `[1, -1, 3, -3]` 의 답 4를 못 얻는다.

```pyrepl
>>> from itertools import accumulate
>>> list(accumulate([1, -1, 3, -3], initial=0))
[0, 1, 0, 3, 0]
```

0이 세 번(`day 0`, `2`, `4`) 나오고 가장 먼 쌍이 답 4다. `initial=0` 이 표의 맨 왼쪽 칸이다([3.2](#/itertools)).

### ③ 도구

굴릴 때 한 일은 둘이다. **누적값을 하나씩 갱신했고, 그 값을 전에 본 적 있는지 확인했다.** 변환표를 그대로 읽으면 정수 하나 + `dict`(값 → 처음 나온 위치)다.

`set` 이 아니라 `dict` 인 이유는 "본 적 있나"로는 부족하고 **어디서 봤는지**가 필요하기 때문이다. 저장하는 것은 **처음 나온 위치**다. 가장 긴 구간을 원하므로 왼쪽 경계는 최대한 왼쪽이어야 한다.

### ④ 골격과 ⑤ 채우기 — 그런데 여기서 막혔다고 하자

②의 아이디어가 안 떠올랐다고 하자. 이때 하는 일은 정해져 있다. **무식한 방법으로 먼저 정답을 만든다.**

```python title="stock_flat.py — 1단계: 무식하게"
def longest_flat_slow(deltas):
    """모든 구간을 다 본다. 느리지만 틀릴 여지가 거의 없다."""
    best = 0
    for i in range(len(deltas)):
        total = 0
        for j in range(i, len(deltas)):
            total += deltas[j]
            if total == 0:
                best = max(best, j - i + 1)
    return best
```

두 겹 루프에 조기 종료도 없다. 그래도 **예시 여섯 개를 전부 통과한다.** 이제 정답 생성기가 손에 있다. 쓰임은 둘이다. 시간이 다 됐을 때 그대로 제출할 답, 그리고 빠른 버전을 대조할 기준.

```python title="stock_flat.py — 2단계: 표가 가리킨 대로"
def longest_flat(deltas):
    """누적 재고가 같은 두 날짜 경계를 찾는다. 한 번만 훑는다."""
    first = {0: 0}                       # 누적 재고 -> 그 값이 처음 나온 날짜 경계
    total = 0
    best = 0
    for day, d in enumerate(deltas, start=1):
        total += d
        if total in first:
            best = max(best, day - first[total])
        else:
            first[total] = day           # 처음 본 값만 기록한다 (왼쪽 경계 보존)
    return best
```

`start=1` 이 표의 `day` 축과 맞는다. `day` 는 "이 날까지 처리한 뒤의 경계", `first[total]` 은 "같은 누적값이었던 이전 경계"다. 두 경계의 차가 곧 기간 길이다.

돌아가는 모습을 눈으로 보려면 `print` 한 줄이면 된다.

```pyrepl
>>> deltas = [2, -1, -1, 5]
>>> total, best, first = 0, 0, {0: 0}
>>> for day, d in enumerate(deltas, start=1):
...     total += d
...     if total in first:
...         best = max(best, day - first[total])
...     else:
...         first[total] = day
...     print(day, total, best, first)
...
1 2 0 {0: 0, 2: 1}
2 1 0 {0: 0, 2: 1, 1: 2}
3 0 3 {0: 0, 2: 1, 1: 2}
4 5 3 {0: 0, 2: 1, 1: 2, 5: 4}
>>> best
3
```

출력의 두 번째 열 `2 1 0 5` 가 ②에서 손으로 적은 `stock` 줄에서 `day 0` 칸을 뗀 것과 정확히 같다. **손으로 굴린 표가 곧 실행 로그다.** 이 대조가 맞으면 그 함수는 거의 확실히 맞다.

### 두 구현을 무작위 입력으로 대조한다

이게 ⑤ 단계의 마지막 동작이다. 예시 통과는 필요조건일 뿐이다.

```python title="stock_flat.py — 3단계: 교차 검증"
import random

CASES = [([1, -1, 3, -3], 4), ([2, -1, -1, 5], 3), ([5, -5, 2, 1, -3, 4], 5),
         ([1, 2, 3], 0), ([0], 1), ([], 0)]

for deltas, want in CASES:
    assert longest_flat_slow(deltas) == want, deltas
print("느린 버전: 예시 전부 통과")

for deltas, want in CASES:
    assert longest_flat(deltas) == want, deltas
print("빠른 버전: 예시 전부 통과")

random.seed(1)
for _ in range(30_000):
    deltas = [random.randint(-3, 3) for _ in range(random.randint(0, 12))]
    slow, fast = longest_flat_slow(deltas), longest_flat(deltas)
    assert slow == fast, (deltas, slow, fast)
print("무작위 30,000건 일치")
```

```text nolines
느린 버전: 예시 전부 통과
빠른 버전: 예시 전부 통과
무작위 30,000건 일치
```

입력을 짧게(0~12개) 잡는 것이 요령이다. 짧으면 느린 버전도 빨라서 3만 건이 순식간이고, **경계 상황이 훨씬 자주 나온다.** 빈 리스트도, 원소 한 개도, 전부 0인 입력도 저절로 들어 있다. 이 방식을 도구로 만든 것이 [6.3 속성 기반 테스트](#/hypothesis)다.

::: danger 이 문제에서 실제로 틀리는 세 곳
**1. `first[total] = day` 를 무조건 실행한다.** `if/else` 없이 매번 갱신하면 왼쪽 경계가 오른쪽으로 밀려 **가장 긴 것 대신 가장 짧은 것**을 재게 된다.

```text nolines
잘못된 버전([1, -1, 1, -1])   -> 2      정답은 4
```

**2. `first = {0: 0}` 대신 `first = {}` 로 시작한다.** 처리 전 상태를 표에 안 적은 것과 같다.

```text nolines
잘못된 버전([1, -1, 3, -3])   -> 2      정답은 4
잘못된 버전([2, -1, -1, 5])   -> 0      정답은 3
잘못된 버전([0])              -> 0      정답은 1
```

**3. `max` 를 빼먹는다.** `best = max(best, day - first[total])` 를 `best = day - first[total]` 로 쓰면, 나중에 찾은 짧은 구간이 앞서 찾은 긴 구간을 덮어쓴다. 셋 중 이게 가장 위험하다. **예시 여섯 개를 전부 통과하기 때문이다.**

```text nolines
잘못된 버전([1, -1, 1, -1, 3, 9, -9])  -> 2      정답은 4
```

앞의 두 실수는 예시 여섯 개 중 각각 네 개, 두 개만 통과한다. 즉 **예시를 전부 돌리기만 하면 첫 예시 `[1, -1, 3, -3]` 에서 바로 걸린다.** 위험한 것은 예시 하나만 눈으로 확인하고 넘어가는 습관이다. 반면 세 번째 실수는 예시로는 절대 안 잡히고 **무작위 대조에서만** 잡힌다. 위 하네스(`random.seed(1)`, 길이 0~12, 값 -3~3) 기준으로 세 버그가 걸린 반복 번호는 각각 2번째, 3번째, 2번째다. 시드나 생성기를 바꾸면 이 숫자는 달라지지만(`seed(7)` 이면 세 번째 버그가 14번째) 수십 건 안에 걸린다는 것은 변하지 않는다.
:::

::: perf 무식한 방법의 값을 알고 결정해라
같은 답을 내는 두 구현의 실행 시간이다.

| 입력 길이 | `longest_flat_slow` | `longest_flat` |
| --- | --- | --- |
| 100 | 0.17~0.24 ms | 0.010~0.014 ms |
| 2,000 | 72~83 ms | 0.24~0.30 ms |
| 5,000 | 452~536 ms | 0.60~0.82 ms |

(Python 3.14.0rc2 / Linux 기준 실측. `timeit.repeat(repeat=7)` 최솟값을 반복 횟수로 나눈 값이고, 입력은 `random.randint(-3, 3)` 리스트다. 시드와 반복 횟수를 바꿔 여러 번 돌린 범위를 적었다. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다.)

읽어야 할 것은 배수가 아니라 **절대 시간**이다. 일지가 100일치면 무식한 방법도 0.2밀리초다. 그럴 때 두 겹 루프는 정답이고 최적화는 시간 낭비다. 5,000일치면 0.5초가 되고, 이게 케이스마다 반복되면 시간 초과다.

그래서 **입력 크기 제한을 먼저 읽고**, 작으면 무식하게 완성부터, 크면 처음부터 ②의 표를 신뢰한다. 누적합 관용구는 [7.3](#/two-pointers), 딕셔너리 조회 비용은 [7.6](#/hashing)에 있다.
:::

## 막혔을 때 — 순서가 정해진 탈출 절차

막히는 것은 정상이다. 문제는 막힌 상태로 **같은 화면을 계속 보는 것**이다. 규칙을 정해라. **같은 화면을 30초 이상 멍하게 보고 있으면 아래로 내려간다.** 위에서부터 순서대로, 하나에 3분씩만.

| 순서 | 무엇을 하는가 | 왜 듣는가 |
| --- | --- | --- |
| 1 | 입력을 **최소로 줄인다.** 원소 한 개, 그다음 두 개 | 손으로 낸 절차가 곧 코드다 |
| 2 | **무식하게 완성한다.** 지우지 말고 남긴다 | 정답 생성기 겸 대조 기준이 생긴다 |
| 3 | ②의 표를 **다시 그린다** | 대개 표에 안 적은 칸에 답이 있다 |
| 4 | **출력에서 거꾸로** 쓴다. 반환문을 먼저 적는다 | 답의 형태가 앞을 좁힌다 |
| 5 | 문제를 **쪼갠다.** 보조 함수 이름만 먼저 적는다 | `to_minutes` 하나가 문제를 반으로 줄인다 |
| 6 | 다른 문제로 **넘어간다** | 한 문제에 매달리는 것이 가장 비싼 실수다 |

::: cote 시험장 축약판 — 30분 문제의 시간 배분
```text nolines
(1) RESTATE    2분   한 문장 + 입출력 타입
(2) ROLL       5분   표 한 개. 경계 예시 두 개 추가
(3) PICK       2분   도구 이름 한두 개
(4) SKELETON   3분   시그니처 + assert. 실패를 눈으로 확인
(5) FILL      15분   통과시킨다
    여유       3분   경계 재확인, 반환 타입 재확인
```

대부분은 ①②③④에 **0분**을 쓰고 ⑤에 30분을 쓴다. 그리고 그 30분 중 20분을 "무엇을 쓸지 정하는 데" 보낸다. 앞의 12분은 뒤의 20분을 사는 값이다.

끝났을 때의 규칙도 미리 정해 둬라. **⑤에서 절반이라도 채웠으면 그대로 제출한다.** 부분 점수가 있는 채점기가 많고, 없더라도 미완성 파일보다 동작하는 무식한 풀이가 낫다([11.14](#/exam-debug)).
:::

## 이 루틴을 어떻게 몸에 붙이는가

읽어서는 안 붙는다. 다음 열 문제를 **산출물을 주석으로 남기면서** 풀어라. 그리고 못 푼 문제마다 **어느 단계까지 갔는지** [11.1](#/fluency-gap)의 복기 노트에 단계 번호로 적어라. "③에서 도구가 안 나왔다"의 처방은 [11.2](#/stdlib-arsenal) 재독이고, "⑤에서 인덱스가 틀렸다"의 처방은 드릴([11.9](#/drill-string))이다. 완전히 다른 병이다.

숙련자가 문제를 보고 바로 코드를 쓰는 것처럼 보이는 것은 단계를 생략한 게 아니라 **①②③이 몇 초로 압축된 것**이다. 압축은 반복에서만 나온다.

## 요약

- 백지 문제의 원인은 아이디어 부족이 아니라 **순서 없음**이다. 이 루틴의 유일한 규칙은 **모든 단계가 눈에 보이는 산출물을 하나 남긴다**는 것이다. 다섯 단계는 **① 내 말로 다시 쓰기 ② 손으로 굴리기 ③ 흔적에서 도구 읽기 ④ 골격과 검증문 ⑤ 채우기**이고, 막히면 앞으로 밀지 말고 ②로 돌아간다.
- ① 의 산출물은 **입력·출력·규칙 세 줄**이다. 원문에 없는 규칙(빈 입력, 동점, 범위 밖)이 여기서 드러난다. 정의되지 않은 입력은 `raise` 한 줄로 닫아라 — `n=0` 에서 두 구현이 `(0, 3)` 과 `(0, 0)` 으로 갈린다.
- ② 는 루틴의 심장이다. **적지 않으면 굴린 게 아니다.** 굴린 표가 (1) 무엇을 기억할지 (2) 언제 답이 나오는지 (3) 인덱스 계산을 한꺼번에 결정하고, off-by-one을 미리 막는다.
- ③ 은 도구를 떠올리는 단계가 아니라 **표에서 읽어내는** 단계다. 질문은 "굴리는 동안 내가 들고 있던 것은 무엇인가" 하나뿐이다. 정수 하나로 되는 문제에 자료구조를 얹지 마라.
- ④ 에서 시그니처와 `assert` 를 먼저 쓰면 백지가 **빈칸 채우기**로 바뀐다. 골격을 실행해 **실패를 눈으로 확인**하는 것까지가 이 단계다. ⑤ 에서는 최적화하지 않는다 — **통과 → 측정 → 개선** 순서다.
- 무식한 방법은 버리지 말고 남겨 **무작위 교차 검증의 기준**으로 쓴다. 예시 여섯 개를 전부 통과하는 오답(`max` 누락)은 이 대조에서만 잡힌다. 입력 100개면 두 겹 루프도 0.2밀리초, 5,000개면 0.5초다(실측) — **크기 제한을 먼저 읽고** 정해라.
- 막히면 순서대로: **입력 줄이기 → 무식하게 완성 → 표 다시 그리기 → 출력에서 거꾸로 → 쪼개기 → 넘어가기.** 30초 규칙을 지켜라.

::: quiz 코드 과제 — 다섯 단계의 산출물을 파일에 남겨라
**각 문제마다 파일 하나를 만들고, 맨 위에 ①의 세 줄과 ②의 표를 주석으로 적은 뒤** 코드를 써라. 산출물이 없는 답은 이 절의 과제를 안 한 것이다.

1. **`count_blocks(rows, n)`** — 시연 I의 좌석 배치도에서, 각 행에 있는 **길이 `n` 이상인 빈 좌석 덩어리의 개수**를 모두 합해 반환하라.

   ```python
   SEATS = ["OOXOOO", "XOOXXO", "OOOOOX"]
   count_blocks(SEATS, 2)   # 4
   count_blocks(SEATS, 3)   # 2
   count_blocks(SEATS, 5)   # 1
   count_blocks(SEATS, 1)   # 5
   count_blocks([], 2)      # 0
   ```

   조기 반환만 없애면 되는 문제가 아니다. **② 에서 `run` 이 끊기는 순간에 무엇을 해야 하는지**를 표에 적고 시작해라. 문자열을 `X` 로 잘라 푸는 두 번째 풀이도 짜서 두 결과를 무작위 입력 1,000건으로 대조하라.

2. **`min_initial(deltas)`** — 시연 II와 같은 재고 변화 리스트를 받아, **재고가 한 번도 음수가 되지 않게 하려면 초기 재고가 최소 얼마여야 하는지**를 반환하라.

   ```python
   min_initial([-2, 3, -4])            # 3
   min_initial([1, 2])                 # 0
   min_initial([-1])                   # 1
   min_initial([3, -1, -1, -1, -1])    # 1
   min_initial([0, -5, 5])             # 5
   min_initial([])                     # 0
   ```

   ② 에서 누적 재고 표를 그리면 답이 표의 어느 칸에 있는지 바로 보인다. **표를 먼저 그려라.** 그린 뒤에는 루프로 다섯 줄이고, `itertools.accumulate` 를 쓰면 한 줄이다. 두 버전을 다 짜서 여섯 예시가 같은지 확인하라.

3. **탈출 절차 2번을 연습하라.** 2번 문제를 **무식한 방법으로도** 짜라. 초기 재고를 0부터 하나씩 올려 통과하는 첫 값을 찾는 방식이다. 그리고 두 구현을 무작위 입력 20,000건으로 대조하는 하네스를 시연 II의 3단계 형태로 작성해 통과시켜라. **탐색 상한을 어디로 잡을지**가 함정이다 — 상한 없는 `while` 과 상한 있는 `range` 중 무엇을 고를지 정하고 이유를 주석으로 남겨라.

4. **일부러 애매한 문제를 처리하라.** 다음 문장에는 정해지지 않은 것이 최소 세 개 있다.

   > 창고 이동 기록이 `"출발창고>도착창고:수량"` 형태의 문자열 리스트로 주어진다. 가장 활발한 창고를 반환하라.

   **비어 있는 자리 세 개를 질문 문장으로 적고**, 각각에 대해 택한 가정을 주석으로 명시한 뒤 `busiest(records) -> str` 을 완성하라. **가정을 하나 바꾸면 어느 줄이 바뀌는지**도 주석으로 표시하라. 정답은 하나가 아니다. 평가되는 것은 가정이 코드에 드러나 있는지다.

5. **루틴 자체를 측정하라.** [11.9 드릴 I](#/drill-string)에서 아직 안 본 문제 세 개를 골라 이 루틴대로 풀며 **단계별 소요 시간을 초 단위로 기록**하라. 자기 기록을 위 `::: cote` 상자의 배분과 비교해라. ⑤에 90퍼센트를 쓰고 있다면 그게 다음 2주 동안 고칠 것이다.
:::
