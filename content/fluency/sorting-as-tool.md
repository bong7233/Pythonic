# 11.6 정렬을 무기로 쓰기

::: lead
정렬은 "순서대로 늘어놓으라"는 요구가 있을 때만 쓰는 도구가 아니다. 실전에서 정렬이 진짜로 하는 일은 **문제를 다른 문제로 바꾸는 것**이다. 모든 쌍을 봐야 하던 문제가 이웃만 보면 되는 문제가 되고, 언제 겹치는지 모르던 구간이 앞의 것 하나만 기억하면 되는 구간이 된다. 이 절은 Timsort가 어떻게 동작하는지를 다시 설명하지 않는다([7.4 정렬](#/sorting)에 있다). **문제를 읽고 "여기서 정렬하면 뭐가 사라지는가"를 3초 안에 판단하는 손**을 만든다.
:::

## 정렬은 답이 아니라 전처리다

문제 하나로 시작한다. 읽고 30초 안에 접근을 정해라.

> 창고에 상자 $n$ 개가 있다. 무게 목록이 주어질 때, **무게 차이가 가장 작은 두 상자**의 차이를 구하라.

정직한 답은 모든 쌍을 보는 것이다.

```python title="이중 루프 — 정직하지만 O(n²)"
import itertools

def closest_pair(weights):
    return min(abs(a - b) for a, b in itertools.combinations(weights, 2))
```

여기서 멈추면 안 된다. **"차이가 가장 작은 두 개"는 정렬하면 반드시 이웃이 된다.** 정렬된 배열에서 서로 이웃이 아닌 두 값 사이에는 반드시 다른 값이 끼어 있고, 그러면 그 값과의 차이가 더 작기 때문이다. 그러니 이웃만 보면 된다.

```pyrepl
>>> sizes = [143, 87, 205, 90, 178, 146]
>>> sizes.sort()
>>> sizes
[87, 90, 143, 146, 178, 205]
>>> min(b - a for a, b in zip(sizes, sizes[1:]))
3
```

`zip(s, s[1:])` 은 이웃 쌍을 만드는 관용구다([11.4](#/array-grid)). 정렬 덕분에 `abs` 도 필요 없어졌다 — 뒤가 항상 크다.

::: perf 정렬 한 번이 자릿수를 바꾼다
`random.seed(3)` 으로 만든 0~999,999 범위 무작위 정수 5,000개로 두 방법을 재 봤다.

```text nolines
n=5000  이중 루프  1050 ~ 1121 ms      정렬 후 인접  0.95 ~ 1.07 ms
```

(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 자릿수 차이는 어디서나 같다.)

세 자릿수 차이다. $O(n^2)$ 의 1,250만 번 비교가 $O(n \log n)$ 정렬 한 번 + $O(n)$ 스캔으로 줄었다. 여기서 기억할 것은 배수가 아니라 **구조**다. 정렬은 $O(n \log n)$ 을 **선불로 내고** 그 뒤의 작업을 한 단계 싼 문제로 바꾼다. $n \log n$ 은 사실상 공짜에 가깝다 — 100만 개도 파이썬에서 1초 이내다([7.4](#/sorting)의 스케일링 실측).
:::

이게 이 절 전체의 사고 틀이다.

> **정렬은 비용이 아니라 투자다.** 낼 값은 $O(n \log n)$ 하나로 고정돼 있고, 돌려받는 것은 "이웃만 보면 된다", "앞의 것 하나만 기억하면 된다", "양 끝에서 만나면 된다" 같은 **구조적 단순화**다.

## 조건 문장을 키로 번역한다

정렬을 쓰기로 정했으면 다음 관문은 `key=` 다. 여기서 손이 멈추는 이유는 문법을 몰라서가 아니라 **문제 문장을 키로 옮기는 절차가 없어서**다. 절차는 세 단계다.

1. 조건 문장을 **"먼저 A, 같으면 B, 그래도 같으면 C"** 형태로 쪼갠다.
2. 각 조각을 **(무엇을, 어느 방향으로)** 로 적는다.
3. 그 순서 그대로 **튜플**에 담는다. 내림차순인 숫자 조각에는 `-` 를 붙인다.

장비 대여 기록에서 *"사용 시간이 많은 순, 같으면 이름 가나다순"* 은 이렇게 옮겨진다.

```text nolines
  sorted(rows, key=lambda r: (-r[1], r[0]))
                               │     │
                               │     └── 2순위: 이름 오름차순
                               └─────── 1순위: 사용 시간 내림차순 (부호를 뒤집었다)
```

```pyrepl
>>> rows = [("cam-2", 3), ("drone-1", 5), ("tripod-3", 3)]
>>> sorted(rows, key=lambda r: (-r[1], r[0]))
[('drone-1', 5), ('cam-2', 3), ('tripod-3', 3)]
```

튜플이 사전식으로 비교되는 원리와 음수 트릭의 한계(문자열에는 안 통한다)는 [7.4](#/sorting)에 있다. 여기서 훈련할 것은 **문장에서 키까지 3초**다. 아래 표를 덮고 왼쪽만 보면서 오른쪽을 직접 써 봐라.

| 문제 문장 | 키 |
| --- | --- |
| "점수가 높은 순, 동점이면 이름순" | `key=lambda r: (-r.score, r.name)` |
| "짧은 것부터, 길이가 같으면 사전순" | `key=lambda w: (len(w), w)` |
| "끝나는 시각이 빠른 순" | `key=lambda x: x[1]` |
| "대소문자 무시하고 사전순" | `key=str.lower` |
| "0에 가까운 순" | `key=abs` |
| "마지막 두 자리 숫자 기준" | `key=lambda n: n % 100` |
| "슬롯 번호 순 (`slot-9`, `slot-10`)" | `key=lambda s: int(s.split("-")[1])` |
| "값이 큰 순으로 딕셔너리 키 나열" | `key=d.get, reverse=True` |

마지막 두 개가 실전에서 특히 자주 나온다.

```pyrepl
>>> labels = ["slot-10", "slot-9", "slot-100"]
>>> sorted(labels)
['slot-10', 'slot-100', 'slot-9']
>>> sorted(labels, key=lambda s: int(s.split("-")[1]))
['slot-9', 'slot-10', 'slot-100']
```

```pyrepl
>>> stock = {"bolt": 12, "nut": 40, "washer": 12}
>>> sorted(stock)
['bolt', 'nut', 'washer']
>>> sorted(stock, key=stock.get, reverse=True)
['nut', 'bolt', 'washer']
>>> sorted(stock.items(), key=lambda kv: (-kv[1], kv[0]))
[('nut', 40), ('bolt', 12), ('washer', 12)]
```

세 줄이 전부 다른 것을 준다. `sorted(딕셔너리)` 는 **키만** 정렬해서 리스트로 준다 — 값은 사라진다. 값 기준으로 키를 세우려면 `key=stock.get`, 키와 값을 같이 들고 가려면 `.items()` 를 정렬한다. 시험장에서 "값 기준으로 정렬했는데 값이 안 나온다"고 당황하는 지점이 여기다.

::: warn `reverse=True` 는 튜플 전체에 걸린다
방향이 섞인 조건에서 `reverse=True` 를 쓰면 **2순위 키까지 같이 뒤집힌다.**

```pyrepl
>>> rows = [("cam-2", 3), ("drone-1", 5), ("tripod-3", 3)]
>>> sorted(rows, key=lambda r: (-r[1], r[0]))
[('drone-1', 5), ('cam-2', 3), ('tripod-3', 3)]
>>> sorted(rows, key=lambda r: (r[1], r[0]), reverse=True)
[('drone-1', 5), ('tripod-3', 3), ('cam-2', 3)]
```

동점인 `cam-2` 와 `tripod-3` 의 순서가 정반대다. 두 번째 줄은 이름까지 내림차순이 됐다. **`reverse=True` 는 모든 키의 방향이 같을 때만 써라.** 방향이 섞이면 숫자 키에 `-` 를 붙이는 쪽이 안전하다. 문자열처럼 부호를 못 붙이는 키가 내림차순이어야 하면 두 번에 나눠 정렬하거나 정수로 매핑한다 — 세 가지 우회로가 [7.4](#/sorting)에 정리돼 있다.
:::

::: danger 튜플 키는 동점이 생기는 순간 터질 수 있다
2순위 키를 안 쓰고 **원소 자체**를 튜플에 넣는 코드를 자주 본다. 정렬은 1순위가 같을 때만 2순위를 비교하므로, **동점이 없는 예제 입력에서는 멀쩡히 통과한다.**

```pyrepl
>>> jobs = [(2, {"id": "A"}), (1, {"id": "B"})]
>>> sorted(jobs)
[(1, {'id': 'B'}), (2, {'id': 'A'})]
>>> jobs.append((1, {"id": "C"}))
>>> sorted(jobs)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: '<' not supported between instances of 'dict' and 'dict'
```

`dict` 는 대소 비교가 정의돼 있지 않다. 순서 비교가 없는 사용자 정의 클래스도 마찬가지다([1.14 특수 메서드](#/dunder)). 예제 데이터에는 동점이 없고 채점 데이터에는 있는, 정확히 그런 종류의 사고다.

**규칙: 튜플 키의 원소는 전부 서로 대소 비교가 되는 값이어야 한다** — 수, 문자열, 그리고 그런 값들로만 이뤄진 튜플. 원본 객체를 같이 들고 가고 싶으면 키가 아니라 정렬 결과에서 꺼내라.

`heapq` 에 `(우선순위, 객체)` 를 넣을 때도 정확히 같은 사고가 난다. 우선순위가 겹치는 원소가 들어오면 두 번째 필드끼리 비교가 시작된다. 다만 **터지는 시점은 예측할 수 없다.** `heappush` 는 sift 경로의 조상하고만 비교하므로, 넣는 순서에 따라 push 에서 바로 터지기도 하고 **push 는 전부 통과하고 `heappop` 에서 터지기도 한다.**

```pyrepl
>>> import heapq
>>> h = []
>>> heapq.heappush(h, (1, {"id": "A"}))
>>> heapq.heappush(h, (2, {"id": "B"}))
>>> heapq.heappush(h, (2, {"id": "C"}))
>>> [p for p, _ in h]
[1, 2, 2]
>>> heapq.heappop(h)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
TypeError: '<' not supported between instances of 'dict' and 'dict'
```

세 번의 `heappush` 가 전부 조용히 통과했다. `(2, C)` 의 조상은 `(1, A)` 하나뿐이고 우선순위가 달라서 딕셔너리까지 내려가지 않았기 때문이다. 힙 안에는 이미 비교할 수 없는 쌍이 나란히 들어앉아 있고, 터지는 것은 나중에 꺼낼 때다. 반대로 마지막을 `(1, {"id": "C"})` 로 넣으면 그 자리에서 `heappush` 가 터진다. **"넣는 데 성공했으니 안전하다"가 성립하지 않는다.**

해법은 `(우선순위, 순번, 객체)` 처럼 **절대 겹치지 않는 정수 순번**을 2순위 필드로 끼워 넣는 것이다. `itertools.count()` 로 그 순번을 만드는 관용구는 [7.8 힙과 우선순위 큐](#/heap)에 있다.
:::

### 키는 원소당 정확히 한 번 계산된다

`key=` 안에 무거운 계산을 넣어도 되는지 묻는 사람이 많다. 답은 **된다**이고, 근거는 호출 횟수다.

```pyrepl
>>> calls = 0
>>> def keyed(x):
...     global calls
...     calls += 1
...     return x % 7
...
>>> import random
>>> random.seed(0)
>>> data = [random.randrange(10**6) for _ in range(10_000)]
>>> _ = sorted(data, key=keyed)
>>> calls
10000
```

원소 1만 개에 호출 1만 번. **비교 횟수($\approx 12$만 번)가 아니라 원소 수만큼**이다. 그래서 `key=lambda s: tuple(map(int, s.split(".")))` 처럼 파싱이 들어간 키도 안심하고 쓸 수 있다. 반대로 비교할 때마다 파이썬 함수가 호출되는 `cmp_to_key` 는 이 성질이 없다 — 그 비교와 실측은 [7.4](#/sorting)에 있다.

::: perf 키를 좁히면 정렬이 두 배 빨라진다
"키를 만드는 비용이 추가된다"는 직관은 자주 틀린다. 20만 개의 `(int, int)` 튜플 리스트를 네 가지 방법으로 정렬해 봤다.

```python title="같은 데이터, 다른 키"
import random, timeit
from operator import itemgetter

random.seed(11)
data = [(random.randrange(10**6), random.randrange(10**6)) for _ in range(200_000)]
ints = [r[0] for r in data]

def ms(call):                     # 1회 소요를 밀리초로 — 최소~최대
    t = timeit.repeat(call, number=3, repeat=7)
    return f"{min(t) / 3 * 1000:.1f} ~ {max(t) / 3 * 1000:.1f} ms"

print("순수 int       ", ms(lambda: sorted(ints)))
print("itemgetter(0)  ", ms(lambda: sorted(data, key=itemgetter(0))))
print("튜플 통째로    ", ms(lambda: sorted(data)))
print("튜플 키 재생성 ", ms(lambda: sorted(data, key=lambda r: (r[0], r[1]))))
```

| 정렬 대상 | 1회 소요 |
| --- | --- |
| 순수 `int` 리스트 | 54.7 ~ 65.2 ms |
| `key=itemgetter(0)` (키가 `int`) | 70.4 ~ 77.9 ms |
| 튜플을 통째로 비교 | 170.7 ~ 196.6 ms |
| `key=lambda r: (r[0], r[1])` (튜플 키 생성) | 264.8 ~ 296.5 ms |

(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 네 방법의 순서는 어디서나 같다. 세 번 재실행해도 이 순서는 바뀌지 않았다.)

**키를 스칼라 하나로 좁히면 튜플 통째 정렬보다 두 배 이상 빠르고, 필요 없는 튜플 키를 만들면 오히려 1.5배 안팎으로 느려진다.** 튜플 비교는 튜플 객체를 따라가 원소를 하나씩 꺼내야 하고, 튜플 키 생성은 원소 수만큼 새 튜플을 할당한다.

실전 규칙: **2순위 키가 실제로 필요할 때만 튜플을 만들어라.** 1순위만으로 충분하면 `itemgetter(0)` 하나로 끝내라 — 동점의 상대 순서는 안정 정렬이 입력 순서 그대로 지켜 준다. 다만 `sorted(data)` 와 `sorted(data, key=itemgetter(0))` 은 **동점 순서가 다르다.** 속도 때문에 결과를 바꾸지는 마라.
:::

::: deep 리스트 원소의 타입이 섞이면 느려진다
CPython의 정렬은 시작 전에 키를 훑어서 **전부 같은 타입인지** 확인하고, 그렇다면 그 타입 전용 비교 함수로 갈아탄다. 일반 비교 경로를 건너뛰는 최적화다. 전용 경로가 있는 타입은 넷이다 — `float`, `int`, `str`, 그리고 **튜플**. 바로 앞 perf 상자의 "튜플 통째로"가 그래도 쓸 만했던 것이 이 때문이다.

조건은 "타입이 같다"보다 좁다. 정수는 **전부 한 자리(30비트) 안에 들어와야** 하고, 문자열은 **전부 latin-1** 이어야 한다. `2**30` 을 넘는 정수나 한글 문자열은 타입이 전부 같아도 이 경로를 못 탄다 — 20만 개 기준으로 각각 1.7~1.9배, 1.6배 느렸다. 선택 로직은 `Objects/listobject.c` 의 `ints_are_bounded` / `strings_are_latin` 검사와 `unsafe_long_compare` / `unsafe_latin_compare` / `unsafe_float_compare` / `unsafe_tuple_compare` 다.

그리고 이 최적화는 **한 개만 어긋나도** 꺼진다. `random.seed(5)` 로 만든 20만 개 정수 리스트에서 **가운데 원소 하나만** `float()` 로 감싸 봤다. 전부 `float` 인 리스트도 대조군으로 같이 쟀다.

```text nolines
all-int  48.6 ~ 53.9 ms     all-float  47.4 ~ 50.3 ms     하나만 float  82.8 ~ 95.3 ms
```

(Python 3.14.0rc2 / Linux 기준 실측. 절대값은 기기마다 다르지만 섞였을 때 느려진다는 방향은 같다.)

값도 순서도 그대로인데 1.7~1.8배 느려졌다. 재실행하면 배수가 흔들리지만 2배를 넘지는 않았다. 그리고 **`float` 가 느린 게 아니다** — 전부 `float` 면 `int` 만큼 빠르다. 느려지는 원인은 타입이 **섞였다**는 것 하나다. 실전에서 이걸 밟는 경로도 하나다 — **키 함수가 조건에 따라 다른 타입을 반환할 때.**

```python
# ❌ 대부분 int 인데 가끔 float 가 섞인다
key=lambda r: r.deadline if r.deadline else float("inf")

# ✅ 타입을 하나로 통일한다
key=lambda r: r.deadline if r.deadline else 10**18
```

`10**18` 은 30비트를 넘으니 정수 전용 비교까지 타지는 못한다. 그래도 타입이 하나라서 섞인 쪽보다는 빠르다 — 같은 데이터에서 59.5 ~ 61.6 ms 대 80.1 ~ 84.9 ms 다.

정확성에는 영향이 없다. 자릿수를 바꾸는 차이도 아니다. 하지만 **키 함수는 타입을 하나로 고정한다**는 습관은 공짜로 얻는 이득이다.
:::

::: cote 시험장에서 그대로 쓰는 키 모음
```python
sorted(pts)                                      # 좌표: x 오름, 같으면 y 오름 (튜플 비교가 이미 그렇다)
sorted(jobs, key=lambda j: j[1])                 # 끝나는 시각 순 (그리디 전처리)
sorted(words, key=lambda w: (len(w), w))         # 짧은 것부터, 같으면 사전순
sorted(cnt.items(), key=lambda kv: (-kv[1], kv[0]))   # 빈도 내림, 같으면 키 오름
sorted(rows, key=lambda r: (r[0], -r[1]))        # 그룹 오름 + 그룹 안에서 내림
sorted(enumerate(a), key=lambda p: -p[1])        # 값 기준 정렬 + 원래 인덱스 보존
```
`Counter.most_common()` 은 **동점 순서를 이름으로 정리해 주지 않는다.** 출력 순서가 채점에 걸리는 문제라면 네 번째 줄처럼 직접 정렬해라([11.2](#/stdlib-arsenal)).
:::

## 정렬이 문제를 지우는 다섯 가지 형태

여기가 이 절의 심장이다. 문제를 읽는 순간 이 다섯 중 어디에 해당하는지만 판단하면 된다.

### ① "가장 가까운/비슷한" — 인접 문제로 바뀐다

**신호**: "차이가 가장 작은", "가장 비슷한 두 개", "중복이 있는가".

정렬하면 **후보가 이웃뿐**이 된다. 앞에서 본 최소 차이 문제가 이 형태다. "중복 원소가 있는가"도 같은 구조인데, 이건 `set` 이 $O(n)$ 으로 이긴다([11.5](#/dict-set-patterns)) — **정렬이 이기는 경우는 "가장 가까운"처럼 값의 순서가 필요할 때**다. 같음 여부만 물으면 해시가 이긴다.

### ② 구간 겹침 — 앞의 것 하나만 기억하면 된다

**신호**: "예약이 겹치는가", "시간대를 합쳐라", "구간을 병합".

```text nolines
before                                   어느 둘이 겹치는지 보려면 모든 쌍을 봐야 한다
   A       |=========|
   B  |====|
   C           |==========|

after (start ascending)                  왼쪽부터 훑으며 "직전 끝"만 들고 가면 된다
   B  |====|
   A       |=========|
   C           |==========|
               ^ 여기서 직전 끝(A) > 내 시작(C) -> 겹침 확정
```

**시작 시각 오름차순**으로 정렬하면 "내 앞의 구간들 중 아직 안 끝난 게 있는가"가 "지금까지 본 끝 시각의 최댓값이 내 시작보다 큰가"로 줄어든다.

```python title="구간 병합"
def merge(slots):
    merged = []
    for start, end in sorted(slots):
        if merged and start <= merged[-1][1]:      # 직전 덩어리와 붙는다
            merged[-1][1] = max(merged[-1][1], end)
        else:
            merged.append([start, end])
    return [tuple(x) for x in merged]
```

```pyrepl
>>> merge([(9, 11), (13, 15), (10, 12), (15, 16)])
[(9, 12), (13, 16)]
>>> merge([(1, 10), (2, 3), (4, 5)])
[(1, 10)]
```

::: warn 구간 문제에서 정렬 기준을 틀리는 두 가지
**첫째, 병합을 끝 시각 기준으로 정렬하면 틀린다.**

```pyrepl
>>> sorted([(1, 10), (2, 3), (4, 5)], key=lambda x: x[1])
[(2, 3), (4, 5), (1, 10)]
```

`(1, 10)` 이 맨 뒤로 밀렸다. 이 순서로 병합하면 `[(2, 3), (4, 10)]` 이 나온다 — 정답은 `[(1, 10)]` 이다. **병합은 시작 기준, 그리디 선택은 끝 기준.** 둘을 섞지 마라.

**둘째, 정렬했다고 "직전 하나"만 보면 되는 것은 아니다.** 병합은 누적 덩어리의 끝을 갱신하니까 맞지만, *앞의 무언가와 겹치는 구간을 모두 찾는* 문제에서 바로 앞 원소하고만 비교하면 놓친다. `rows` 는 `(시작, 끝, 이름)` 3-튜플의 시작 시각 오름차순 리스트다.

```python
# ❌ 바로 앞 하나만 본다 — A(9~18) 다음에 B(10~11), C(12~13) 가 오면 C 를 놓친다
for prev, cur in zip(rows, rows[1:]):
    if cur[0] < prev[1]: ...

# ✅ 지금까지 본 끝 시각의 최댓값과 비교한다
max_end = 0
for start, end, who in rows:
    if start < max_end: ...
    max_end = max(max_end, end)
```

지금까지 본 끝 시각의 최댓값과 비교하면 **겹치는 구간을 빠뜨리지 않는다.** 다만 이건 "겹치는 상대가 하나라도 있다"까지다 — 겹치는 **모든 쌍**을 열거해야 하면 `max_end` 하나로는 부족하다. `[(9,18,'A'), (10,20,'B'), (12,13,'C')]` 에서 `max_end` 는 `(A,B)` 와 `(B,C)` 만 내놓고 `(A,C)` 를 놓친다. 최댓값 하나가 아니라 **아직 안 끝난 구간 목록**을 들고 가면서 끝난 것을 끝 시각 순으로 버려야 한다(끝 시각 최소 힙, [7.8](#/heap)).

정렬이 보장하는 것은 **시작 시각의 순서**뿐이다. 끝 시각은 여전히 뒤죽박죽이라는 것을 잊지 마라.
:::

### ③ "동시에 몇 개" — 이벤트로 쪼개서 정렬한다

**신호**: "가장 붐빈 시각", "최대 몇 대가 동시에", "필요한 최소 개수".

구간을 통째로 다루지 말고 **시작 이벤트 `+1`, 종료 이벤트 `-1` 로 쪼개서** 시각 순으로 정렬한다. 구간 문제가 1차원 스캔으로 납작해진다.

```python title="동시 사용 최댓값"
def peak(slots):
    events = []
    for start, end in slots:
        events.append((start, 1))
        events.append((end, -1))
    events.sort()                      # 같은 시각이면 -1 이 먼저 온다
    cur = best = 0
    for _, delta in events:
        cur += delta
        best = max(best, cur)
    return best
```

```pyrepl
>>> peak([(9, 11), (13, 15), (10, 12), (15, 16)])
2
>>> peak([(9, 12), (10, 13), (11, 14)])
3
```

::: tip 같은 시각의 순서가 정책이다
`events.sort()` 는 `(시각, 델타)` 튜플을 비교하므로 시각이 같으면 **`-1` 이 `+1` 보다 먼저** 온다. 즉 "11시에 반납하고 11시에 빌리는 것은 겹치지 않는다"고 판정한다. 위 예에서 `(13, 15)` 와 `(15, 16)` 이 겹치지 않는 이유가 이것이다.

문제가 "끝나는 시각과 시작하는 시각이 같으면 겹친 것으로 본다"고 하면 정반대여야 한다. 그때는 `(start, 0)`, `(end, 1)` 처럼 **델타가 아닌 별도의 순서 필드**를 두거나 종료 이벤트를 `(end, 2)` 로 밀어라. 이 한 줄이 문제 조건 전체를 뒤집는다. **경계에서 어느 쪽이 먼저인지는 반드시 문제 문장에서 확인해라.**
:::

### ④ 짝 맞추기 — 정렬하면 양 끝에서 만난다

**신호**: "둘씩 묶어서", "최대 무게를 넘지 않게", "최소 몇 번에".

```python title="짐 두 개씩, 카트 한 대의 한계는 limit"
def min_carts(weights, limit):
    w = sorted(weights)
    i, j, used = 0, len(w) - 1, 0
    while i <= j:
        if w[i] + w[j] <= limit:       # 가장 가벼운 것과 가장 무거운 것이 같이 갈 수 있으면 태운다
            i += 1
        j -= 1
        used += 1
    return used
```

```pyrepl
>>> min_carts([70, 50, 80, 50], 100)
3
>>> min_carts([40, 40, 40], 100)
2
```

정렬 없이는 어떤 둘을 묶을지 $2^n$ 가지를 따져야 한다. 정렬하고 나면 **"가장 무거운 것은 가장 가벼운 것과 짝이 되지 못하면 아무하고도 못 된다"** 는 사실이 성립해서 선택지가 하나로 줄어든다. 투 포인터 자체는 [7.3](#/two-pointers)에 있다. 여기서 기억할 것은 **투 포인터의 전제 조건이 대부분 "정렬돼 있음"이라는 것**이다.

### ⑤ 그리디 전처리 — 무엇으로 정렬하느냐가 알고리즘이다

**신호**: "최대 몇 개를 처리", "겹치지 않게 최대한", "마감이 있는 작업".

```python title="한 사람이 겹치지 않게 처리할 수 있는 최대 건수"
def max_jobs(slots):
    count, last = 0, float("-inf")
    for start, end in sorted(slots, key=lambda x: x[1]):   # 끝나는 시각 오름차순
        if start >= last:
            count += 1
            last = end
    return count
```

```pyrepl
>>> jobs = [(13, 16), (9, 12), (11, 14), (15, 18), (9, 10)]
>>> max_jobs(jobs)
3
```

정렬 기준을 시작 시각으로 바꾸면 **알고리즘이 통째로 틀린다.**

```pyrepl
>>> jobs = [(9, 18), (10, 11), (12, 13), (14, 15)]
>>> max_jobs(jobs)
3
>>> sorted(jobs, key=lambda x: x[1])
[(10, 11), (12, 13), (14, 15), (9, 18)]
```

시작 시각 순으로 골랐다면 `(9, 18)` 을 먼저 집어 답이 1이 된다. **그리디에서 정렬 기준은 취향이 아니라 증명의 일부다.** 왜 끝나는 시각인지(교환 논법)는 [7.19 그리디](#/greedy)에 있다. 이 절에서 가져갈 것은 판단 하나다 — **그리디가 떠오르면 "무엇으로 줄을 세울 것인가"를 먼저 정하고, 반례를 하나 만들어 확인해라.**

## 정렬하지 말아야 할 자리

무기를 아는 것만큼 **언제 칼집에서 안 빼는지**가 중요하다.

::: danger 정렬하는 순간 인덱스가 사라진다
"가장 점수가 높은 사람의 **번호**", "정렬 전 위치", "몇 번째로 들어왔는가" — 답이 값이 아니라 **위치**인 문제에서 그냥 정렬하면 정보가 날아간다.

```python
# ❌ 값은 정렬됐는데 누구 것이었는지 모른다
scores.sort(reverse=True)

# ✅ 인덱스를 같이 들고 간다
sorted(enumerate(scores), key=lambda p: -p[1])
```

```pyrepl
>>> scores = [88, 95, 88, 70]
>>> sorted(enumerate(scores), key=lambda p: -p[1])
[(1, 95), (0, 88), (2, 88), (3, 70)]
```

동점인 0번과 2번이 **원래 순서대로** 남아 있다. 안정 정렬이라 공짜로 얻는 성질이고, "동점이면 먼저 들어온 사람이 앞" 같은 요구사항은 **아무것도 안 해도 만족된다.**

여기서 한 걸음 더 나간 것이 등수 매기기다. 정렬된 순서를 **원래 자리로 되돌려 놓아야** 한다.

```python title="동점은 같은 등수, 출력은 입력 순서대로"
def rank_by_score(scores):
    order = sorted(range(len(scores)), key=lambda i: -scores[i])
    rank = [0] * len(scores)
    for place, i in enumerate(order, 1):
        prev = order[place - 2]
        if place > 1 and scores[i] == scores[prev]:
            rank[i] = rank[prev]                  # 동점자는 앞사람 등수를 그대로
        else:
            rank[i] = place
    return rank
```

```pyrepl
>>> rank_by_score([88, 95, 88, 70])
[2, 1, 2, 4]
>>> rank_by_score([50, 50, 50])
[1, 1, 1]
```

`sorted(range(len(x)), key=...)` 는 **값이 아니라 인덱스를 정렬하는** 관용구다. 등수·순위·"원래 자리에 답을 채워 넣기" 유형에서 반사적으로 나와야 한다.
:::

정렬이 필요 없는 나머지 경우들:

- **전체 순서가 필요 없다.** 최댓값 하나면 `max()`, 상위 $K$ 개면 `heapq.nlargest`. $K$ 가 상수면 힙이 이기고 $n$ 의 비율이면 정렬이 이긴다 — 실측은 [11.2](#/stdlib-arsenal)에 있다.
- **값의 순서가 아니라 존재만 물었다.** "중복이 있는가", "둘 다 나온 것은 무엇인가"는 `set` 이 $O(n)$ 으로 끝낸다([11.5](#/dict-set-patterns)). 정렬해서 이웃을 비교할 이유가 없다.
- **정렬된 상태에 질의만 반복한다.** 한 번 정렬해 두고 `bisect` 로 묻는다. 매번 다시 정렬하지 마라([7.5](#/binary-search)).
- **원본 순서가 출력 형식이다.** 중간 계산을 위해 정렬했다면 출력 전에 되돌릴 방법을 미리 정해 둬라.

::: warn 복잡도만 보고 정렬을 기각하지 마라
바로 위 규칙에는 예외가 있다. **정렬이 $O(n \log n)$ 이라서 $O(n)$ 짜리에 진다는 추론은 작은 $n$ 에서 자주 틀린다.**

두 문자열이 같은 글자로 이뤄졌는지 판정하는 두 방법을, **길이 10의 애너그램 쌍**(`"coordinate"` 와 `"decoration"` — 정답이 `True` 라서 두 방법 모두 끝까지 가는 최악의 경우)으로 10만 번씩 재 봤다.

```text nolines
sorted(a) == sorted(b)      80.6 ~  82.9 ms
Counter(a) == Counter(b)   414.7 ~ 442.2 ms
```

(Python 3.14.0rc2 / Linux 기준 실측. 절대값과 배수는 입력과 기기에 따라 달라지지만 `sorted` 가 이긴다는 방향은 같다.)

이론상 진 쪽이 5배 빠르다. `sorted` 는 전체가 C 안에서 끝나고 `Counter` 는 글자마다 파이썬 바이트코드와 딕셔너리 갱신을 밟기 때문이다. 배수는 입력에 따라 움직인다 — 애너그램이 아닌 쌍(`"decorative"`)으로 바꾸면 `Counter` 가 첫 불일치에서 일찍 끝나 3.5배로 줄어든다. 그래도 **$n$ 이 작으면 상수가 복잡도를 이긴다**는 결론은 그대로다. 길이별 교차점 실측은 [11.5](#/dict-set-patterns)에 있다.
:::

::: perf `.sort()` 와 `sorted()` 는 메모리가 다르다
반환값과 부작용의 차이는 [7.4](#/sorting)에 있다. 실전에서 하나 더 걸리는 것이 **메모리 제한**이다. `random.seed(1)` 로 만든 0~999,999,999 범위 정수 100만 개를 두 방식으로 정렬하며 `tracemalloc` 으로 봤다.

```text nolines
sorted() 피크  11.4 MB      .sort() 피크   3.8 MB
```

(Python 3.14.0rc2 / Linux 기준 실측. 세 번 반복해도 소수점 첫째 자리까지 같은 값이 나왔다.)

숫자가 정확히 맞아떨어진다. `sorted()` 는 **새 리스트(포인터 100만 개 = 7.6 MB)** 를 만들고 그 위에 병합용 임시 버퍼(3.8 MB = 포인터 50만 개)를 얹어 11.4 MB가 된다. `.sort()` 는 임시 버퍼만 쓴다. 원소 객체 자체는 양쪽 다 공유하므로 여기 안 잡힌다.

메모리 제한이 빡빡한 문제에서 **입력을 다시 안 쓸 거라면 `.sort()`** 다. 반대로 함수 인자로 받은 리스트라면 호출자의 데이터를 조용히 바꾸는 것이므로 `sorted()` 로 새 리스트를 만들어라([1.1](#/objects-names)).
:::

## 실전: 장비 대여소 정산 리포트

지금까지의 판단을 한 문제에 몰아 넣는다. 요구사항은 셋이다.

1. 같은 장비가 **시간이 겹치게** 대여된 기록을 찾아라.
2. 동시에 나가 있던 장비 수의 **최댓값**을 구하라.
3. 총 사용 시간 **상위 3명**을 구하라. 같으면 이름 가나다순.

세 요구사항이 각각 형태 ②, ③, 그리고 튜플 키에 대응한다. 정렬 기준을 먼저 정하고 코드를 쓴다.

```python title="rental_report.py"
from collections import defaultdict

# (사용자, 장비, 대여 시각, 반납 시각) — 시각은 그날의 시(hour)
LOGS = [
    ("hyeon", "drone-1", 9, 12),
    ("mina", "cam-2", 10, 11),
    ("hyeon", "cam-2", 13, 16),
    ("jaewon", "drone-1", 11, 15),
    ("mina", "tripod-3", 9, 18),
    ("jaewon", "cam-2", 15, 17),
    ("mina", "drone-1", 16, 18),
]


def conflicts(logs):
    """장비별로 시작 시각 순으로 세운 뒤, 지금까지의 최대 반납 시각과 비교한다."""
    by_gear = defaultdict(list)
    for user, gear, start, end in logs:
        by_gear[gear].append((start, end, user))

    found = []
    for gear, rows in sorted(by_gear.items()):     # 장비 이름 순으로 보고
        rows.sort()                                # 시작 시각 오름차순
        max_end, holder = 0, None
        for start, end, user in rows:
            if start < max_end:                    # 아직 반납 안 된 것이 있다
                found.append((gear, holder, user))
            if end > max_end:
                max_end, holder = end, user
    return found


def peak_in_use(logs):
    """시작 +1, 반납 -1 로 쪼개서 시각 순으로 훑는다."""
    events = []
    for _, _, start, end in logs:
        events.append((start, 1))
        events.append((end, -1))
    events.sort()                                  # 같은 시각이면 반납이 먼저
    cur = best = 0
    for _, delta in events:
        cur += delta
        best = max(best, cur)
    return best


def top_users(logs, k):
    """사용 시간 내림차순, 같으면 이름 오름차순."""
    hours = defaultdict(int)
    for user, _, start, end in logs:
        hours[user] += end - start
    return sorted(hours.items(), key=lambda r: (-r[1], r[0]))[:k]


print("겹침:", conflicts(LOGS))
print("동시 최대:", peak_in_use(LOGS))
print("상위 3명:", top_users(LOGS, 3))
```

```text nolines
겹침: [('cam-2', 'hyeon', 'jaewon'), ('drone-1', 'hyeon', 'jaewon')]
동시 최대: 3
상위 3명: [('mina', 12), ('hyeon', 6), ('jaewon', 6)]
```

세 함수 모두 **정렬 한 줄이 알고리즘 전체를 결정했다.** `peak_in_use` 에서 `events.sort()` 를 빼면 위 입력의 답이 3이 아니라 1이 된다. `top_users` 의 키에서 `-` 를 빼면 꼴찌 셋이 나온다.

`conflicts` 의 `rows.sort()` 는 더 고약하다. **이 입력에서는 지워도 답이 똑같이 나온다.**

```text nolines
rows.sort() 있음        [('cam-2', 'hyeon', 'jaewon'), ('drone-1', 'hyeon', 'jaewon')]
rows.sort() 없음        [('cam-2', 'hyeon', 'jaewon'), ('drone-1', 'hyeon', 'jaewon')]
rows.sort() 없음 + 입력을 역순으로
                        겹침 4건 (엉뚱한 쌍까지 섞여 나온다)
```

`LOGS` 가 장비별로 이미 대여 시각 순에 가깝게 들어와 있어서 우연히 맞은 것이다. 입력 순서를 뒤집으면 곧바로 무너진다. **"내 손에 있는 입력에서 맞았다"는 정렬을 지워도 된다는 근거가 못 된다.** 채점 데이터의 입력 순서는 당신이 정하지 않는다.

`hyeon` 과 `jaewon` 이 동점 6시간인데 이름순으로 정리된 것도 확인해라 — 이 한 글자가 채점에서 갈린다.

::: note 이 코드가 이미 답을 정한 것들
- `sorted(by_gear.items())` 는 **출력 순서를 고정**하기 위한 것이다. 딕셔너리 순회 순서에 의존한 출력은 입력 순서가 바뀌면 같이 바뀐다([11.5](#/dict-set-patterns)).
- `rows.sort()` 는 `by_gear` 안의 리스트를 제자리에서 바꾼다. 이 함수 안에서 만든 리스트라 안전하다. 남의 리스트였다면 `sorted()` 여야 한다.
- `start < max_end` 는 "반납과 대여가 같은 시각이면 겹치지 않는다"는 정책이다. `<=` 로 바꾸면 정반대가 된다. **부등호 하나가 요구사항이다.**
:::

## 요약

- 정렬은 "순서대로 출력하라"는 요구가 있을 때만 쓰는 게 아니다. **$O(n \log n)$ 을 선불로 내고 문제를 한 단계 싼 구조로 바꾸는 전처리**다.
- 조건 문장은 **"먼저 A, 같으면 B"** 로 쪼개서 그 순서 그대로 튜플 키에 담는다. 숫자 키의 내림차순은 부호를 뒤집고, `reverse=True` 는 **모든 키의 방향이 같을 때만** 쓴다.
- `key=` 는 **원소당 정확히 한 번** 호출된다. 파싱·정규화를 키에 넣어도 안전하다. 반면 **필요 없는 튜플 키는 정렬을 1.5배 느리게** 하고, 키를 스칼라로 좁히면 두 배 빨라진다.
- 튜플 키의 원소는 전부 비교 가능해야 한다. `dict` 나 순서 없는 객체를 넣으면 **동점이 처음 생기는 데이터에서** 터진다.
- 정렬이 문제를 지우는 다섯 형태: **① 가장 가까운 → 이웃만 ② 구간 겹침 → 앞의 끝 하나만 ③ 동시 개수 → 이벤트 +1/-1 ④ 짝 맞추기 → 양 끝에서 ⑤ 그리디 → 무엇으로 줄 세울지가 알고리즘.**
- 정렬하면 **인덱스가 사라진다.** 답이 위치라면 `enumerate` 또는 `sorted(range(n), key=...)` 로 인덱스를 들고 가라.
- 안 쓰는 판단도 무기다. 최댓값 하나면 `max`, 상위 K(K가 상수)면 `heapq`, 중복 여부만 물으면 `set`, 정렬된 상태에 질의만 반복하면 한 번 정렬한 뒤 `bisect`.

::: quiz 코드 과제
읽고 답하지 말고 **직접 짜라.** 각 문제마다 정렬 기준을 먼저 한 문장으로 적고 시작해라. 다 짠 뒤에는 "정렬을 빼면 무엇이 무너지는가"를 스스로 말해 봐라.

1. **`top_delays(records, k)`** — `(정류장, 지연 분)` 기록에서 정류장별 지연 합계를 구해 **큰 순으로 k개**를 돌려준다. 합계가 같으면 **정류장 이름 오름차순**.

   ```python
   R = [("songpa", 30), ("mapo", 30), ("gangnam", 12), ("gangnam", 18), ("mapo", 0)]
   top_delays(R, 2)   # [('gangnam', 30), ('mapo', 30)]
   top_delays(R, 3)   # [('gangnam', 30), ('mapo', 30), ('songpa', 30)]
   ```

   셋 다 30분 동점이다. `Counter.most_common(3)` 으로 짜면 왜 위험한지 함께 설명해라.

2. **`merge_windows(windows)`** — 설비 점검 시간대 목록을 겹치거나 맞닿은 것끼리 합쳐 **시작 시각 순**으로 돌려준다.

   ```python
   merge_windows([(3, 5), (1, 4), (9, 10)])    # [(1, 5), (9, 10)]
   merge_windows([(1, 2), (2, 3), (3, 4)])     # [(1, 4)]
   ```

   두 번째 예시가 `[(1, 2), (2, 3), (3, 4)]` 로 나왔다면 부등호가 `<` 다. **맞닿은 것을 합칠지 말지가 부등호 하나로 갈린다** — 두 버전을 다 짜 보고 차이를 눈으로 확인해라.

3. **`min_carts(weights, limit)`** — 짐을 한 카트에 **최대 두 개까지**, 무게 합이 `limit` 이하가 되게 실을 때 필요한 최소 카트 수. 어떤 짐도 혼자서는 `limit` 을 넘지 않는다고 가정한다.

   ```python
   min_carts([70, 50, 80, 50], 100)   # 3
   min_carts([40, 40, 40], 100)       # 2
   ```

   먼저 짜고 나서, **모든 짝짓기를 다 해 보는 무식한 함수**를 따로 만들어 무작위 입력 200개로 두 결과가 같은지 대조해라. 그리디가 맞는지 스스로 확인하는 훈련이다.

4. **`rank_by_score(scores)`** — 점수 리스트를 받아 **입력과 같은 순서로** 등수 리스트를 돌려준다. 동점은 같은 등수이고, 다음 등수는 인원수만큼 건너뛴다.

   ```python
   rank_by_score([88, 95, 88, 70])   # [2, 1, 2, 4]
   rank_by_score([50, 50, 50])       # [1, 1, 1]
   ```

   본문에 답이 있다. **보지 말고 짜라.** 다 짠 뒤 본문과 비교해라. 그다음 변형: 등수를 건너뛰지 않는 방식(`[2, 1, 2, 3]`)으로 고쳐라.

5. **`sort_labels(labels)`** — `"1.10.0"` 같은 점 구분 버전 문자열을 **버전 순서**로 정렬한다. 자리 수는 다를 수 있다.

   ```python
   sort_labels(["1.10.0", "1.9.3", "1.10", "2.0.0"])
   # ['1.9.3', '1.10', '1.10.0', '2.0.0']
   ```

   `"1.10"` 이 `"1.10.0"` 앞에 오는 이유를 튜플 비교로 설명할 수 있어야 한다. 그다음, `"1.10.0-rc1"` 처럼 뒤에 꼬리표가 붙는 경우를 어떻게 처리할지 **키 함수 설계를 말로 먼저** 정해라.
:::
