# 11.1 왜 손이 안 움직이는가

::: lead
당신은 스택이 무엇인지 안다. BFS가 무엇인지도 안다. 그런데 빈 편집기 앞에 "주차 요금을 계산하는 함수를 쓰라"는 한 줄을 놓으면 30분이 지나도 첫 줄이 안 나온다. 이건 알고리즘 지식의 문제가 아니다. **문제 문장을 파이썬 코드로 옮기는 손이 아직 안 만들어진 것**이다. 이 절은 그 진단을 정확히 내리고, 나머지 13개 절이 무엇을 고칠 것인지 지도를 그린다. 읽기만 해서는 아무것도 안 바뀌니, 중간에 반드시 멈추고 손으로 풀어야 한다.
:::

## 30분 동안 아무 줄도 못 쓰는 상태

익숙한 장면이 있다. 문제를 읽는다. 무슨 말인지 다 이해된다. 어렵지도 않다. 그런데 커서만 깜빡인다.

이때 머릿속에서 실제로 벌어지는 일은 이렇다.

- "이거 문자열 나누는 거네" → 그런데 `split` 인지 `partition` 인지 확신이 없다.
- "빈도를 세면 되겠다" → `Counter` 를 쓸까 `dict` 를 직접 만들까 고민하다 5분이 간다.
- "일단 함수 이름부터" → 인자를 몇 개 받아야 하는지 정하려다 다시 문제를 읽는다.
- 결국 파이썬을 잠깐 접고 **머릿속에서 알고리즘을 다 완성하려고 한다.** 그러다 30분이 간다.

마지막 항목이 핵심이다. **손이 안 움직이니까 머리로 다 끝내려 한다.** 그런데 머리로 다 끝내는 건 원래 불가능하다. 숙련자도 코드를 쓰면서 생각한다. 쓰면서 생각하려면 쓰는 행위 자체가 싸야 하고, 그게 유창함이다.

::: warn 이 절은 알고리즘을 가르치지 않는다
아래 자가 진단 3문제에는 **알고리즘이 하나도 없다.** 스택도, 그래프도, DP도 없다. 세는 것과 정렬하는 것 이상이 필요 없다. 그런데도 못 푼다면 [Part VII](#/complexity)을 다시 펴는 것은 답이 아니다. 고쳐야 할 것이 다른 곳에 있다.
:::

## 지금 멈추고 풀어라

여기서부터가 이 절의 본론이다. 아래 3문제를 **먼저 풀어야** 다음 문단이 의미가 있다.

::: quiz 자가 진단 — 편집기를 열고 15분
세 문제 전부 합쳐 15분. 검색 금지, 자동완성 끄기, 아래로 스크롤 금지.

**문제 1 — 좌석 코드 검증**

공연장 좌석 코드가 유효한지 판정하는 `is_valid_seat(code) -> bool` 을 쓰라. 규칙은 전부 만족해야 한다.

1. 길이는 2자 이상 4자 이하.
2. 첫 글자는 구역이고 `A`~`F` 대문자 중 하나.
3. 둘째 글자부터 끝까지는 전부 숫자.
4. 그 숫자 부분은 `0` 으로 시작하지 않는다.
5. 숫자로 읽은 좌석 번호는 1 이상 200 이하.

```text nolines
"A1"    -> True
"F200"  -> True
"B12"   -> True
"C07"   -> False   (0으로 시작)
"G5"    -> False   (구역이 A~F가 아님)
"B201"  -> False   (번호 범위 초과)
"a5"    -> False   (소문자)
"D"     -> False   (길이 부족)
```

**문제 2 — 주차 요금 정산**

같은 날 안에서의 입차·출차 시각이 `"HH:MM"` 두 개로 주어진다. 요금을 정수로 반환하는 `parking_fee(enter, leave) -> int` 를 쓰라.

- 최초 30분까지는 기본요금 1000원.
- 30분을 넘긴 시간은 **10분 단위로 500원**. 10분이 안 되는 나머지도 한 단위로 올린다.

```text nolines
("09:00", "09:25") -> 1000
("09:00", "09:30") -> 1000
("09:00", "09:31") -> 1500
("09:00", "09:41") -> 2000
("09:00", "10:00") -> 2500
("08:15", "11:47") -> 10500
```

**문제 3 — 대출 상위 도서**

도서관 대출 기록이 `"회원ID,도서코드"` 형태의 문자열 리스트로 주어진다. 대출 횟수가 많은 순으로 상위 `k`개 도서코드를 반환하는 `top_books(records, k) -> list[str]` 를 쓰라.

- **같은 회원이 같은 책을 여러 번 빌린 것은 1회로 센다.**
- 횟수가 같으면 도서코드 사전순.
- 도서가 `k`개보다 적으면 있는 만큼만 반환한다.

```text nolines
records = ["U01,B100", "U02,B100", "U01,B100",
           "U03,B200", "U02,B200", "U01,B300"]

top_books(records, 2)  -> ['B100', 'B200']
top_books(records, 3)  -> ['B100', 'B200', 'B300']
top_books(records, 10) -> ['B100', 'B200', 'B300']
top_books([], 3)       -> []
```
:::

## 채점 — 못 푼 이유를 유형으로 읽는다

각 문제의 기준 해답을 먼저 보고, 그 아래에서 **어디서 멈췄는가에 따라 무엇이 부족한지**를 해석한다. 맞혔더라도 걸린 시간을 보라. 이 셋은 각각 3~5분 안에 끝나야 하는 난이도다.

### 문제 1 — 규칙을 코드 순서로 옮기기

::: answer 문제 1 기준 해답
```python title="seat.py"
ZONES = "ABCDEF"


def is_valid_seat(code: str) -> bool:
    # 규칙 하나당 조기 반환 하나. 순서는 "싼 검사 먼저".
    if not 2 <= len(code) <= 4:
        return False
    if code[0] not in ZONES:
        return False
    number = code[1:]
    if not number.isdecimal():       # isdigit 이 아니다 — 아래 상자 참고
        return False
    if number[0] == "0":
        return False
    return 1 <= int(number) <= 200


for code in ["A1", "F200", "B12", "C07", "G5", "B201", "a5", "D"]:
    print(f"{code!r:8} {is_valid_seat(code)}")
```

```text nolines
'A1'     True
'F200'   True
'B12'    True
'C07'    False
'G5'     False
'B201'   False
'a5'     False
'D'      False
```

주석을 빼면 함수 본문은 10줄이다. 새로운 개념은 하나도 없다. `len`, `in`, 슬라이싱, `isdecimal`, `int` 뿐이다.
:::

여기서 멈췄다면 원인은 대개 셋 중 하나다.

| 멈춘 지점 | 진짜 원인 | 갈 곳 |
| --- | --- | --- |
| 규칙 5개를 한 줄 `if` 에 다 넣으려다 엉킴 | 조기 반환으로 규칙을 **분해**하는 습관이 없다 | [11.3 문자열 다루기](#/string-toolkit) |
| "숫자인지 확인"에서 손이 멈춤 | `str` 메서드가 머릿속 목록에 없다 | [11.3 문자열 다루기](#/string-toolkit) |
| 함수 시그니처를 못 정하고 헤맴 | 골격을 먼저 적는 절차가 없다 | [11.7 백지 루틴](#/blank-page-routine) |

**규칙이 여러 개인 검증 문제는 조건을 한 덩어리로 합치지 마라.** 규칙 하나에 `if ...: return False` 하나. 이러면 규칙이 하나 추가돼도 줄 하나만 늘어나고, 틀렸을 때 어느 규칙이 문제인지 즉시 보인다.

::: danger isdigit 은 이 문제에서 틀린 도구다
"숫자인가"를 묻는 `str` 메서드는 세 개고, 셋 다 다르다. 이 문제처럼 **`int()` 로 변환할 것**이라면 `isdecimal()` 을 써야 한다.

```pyrepl
>>> "12".isdigit()
True
>>> "1²".isdigit()
True
>>> "1²".isdecimal()
False
>>> int("1²")
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
    int("1²")
ValueError: invalid literal for int() with base 10: '1²'
```

`isdigit()` 은 위첨자 같은 문자에도 `True` 를 준다. 그 뒤에 `int()` 를 부르면 `ValueError` 로 죽는다. 코딩테스트 입력에는 이런 문자가 잘 안 나오지만, **과제형이나 실무 입력에는 나온다.** `isdigit()` 은 "사람이 숫자로 읽는가", `isdecimal()` 은 "`int()` 가 먹는가"로 기억해라. 셋의 차이는 [1.4 문자열과 유니코드](#/strings)에 있다.
:::

### 문제 2 — 단위를 하나로 정규화하기

::: answer 문제 2 기준 해답
```python title="parking.py"
BASE_MINUTES = 30
BASE_FEE = 1000
UNIT_MINUTES = 10
UNIT_FEE = 500


def to_minutes(hhmm: str) -> int:
    # 시각 비교·뺄셈을 전부 정수 하나로 만든다. 이 한 줄이 문제를 반으로 줄인다.
    hour, minute = hhmm.split(":")
    return int(hour) * 60 + int(minute)


def parking_fee(enter: str, leave: str) -> int:
    stayed = to_minutes(leave) - to_minutes(enter)
    if stayed <= BASE_MINUTES:
        return BASE_FEE
    over = stayed - BASE_MINUTES
    units = -(-over // UNIT_MINUTES)      # 올림 나눗셈
    return BASE_FEE + units * UNIT_FEE


for enter, leave in [("09:00", "09:25"), ("09:00", "09:30"), ("09:00", "09:31"),
                     ("09:00", "09:41"), ("09:00", "10:00"), ("08:15", "11:47")]:
    print(enter, leave, parking_fee(enter, leave))
```

```text nolines
09:00 09:25 1000
09:00 09:30 1000
09:00 09:31 1500
09:00 09:41 2000
09:00 10:00 2500
08:15 11:47 10500
```
:::

이 문제의 전부는 **보조 함수 `to_minutes` 를 만들 생각을 했는가**다. 시·분을 따로 들고 다니면 자정 근처 처리, 뺄셈, 비교가 전부 지저분해진다. 분 하나로 바꾸는 순간 남는 건 정수 산술뿐이다.

이런 판단에는 이름이 있다. **정규화**다. 문제에 단위가 둘 이상 섞여 있으면 가장 작은 단위 하나로 먼저 통일한다. 좌표는 정수 쌍으로, 시각은 분으로, 대소문자 섞인 문자열은 `lower()` 로. 이 습관 하나가 시뮬레이션 문제([11.4](#/array-grid))의 절반을 해결한다.

::: warn 올림 나눗셈에서 절반이 틀린다
"10분 미만도 한 단위"라는 문장을 `//` 로 그냥 쓰면 조용히 틀린다. `("09:00", "09:31")` 에서 초과 시간은 1분인데, `1 // 10` 은 `0` 이라 요금이 1000원으로 나온다. 정답은 1500원이다.

올림 나눗셈은 세 가지 표기가 있고, 음이 아닌 정수에서는 전부 같다(0~59 전 구간에서 일치를 확인했다).

```python
units = -(-over // 10)          # ✅ 정수만, import 없음. 관용구
units = (over + 10 - 1) // 10   # ✅ 같은 값. 의도가 더 잘 보인다
units = math.ceil(over / 10)    # ⚠️ float 경유. 큰 수에서 오차 위험
units = over // 10              # ❌ 내림. 이 문제의 오답
```

`math.ceil` 이 위험한 이유는 나눗셈이 부동소수점을 한 번 거치기 때문이다. `float` 는 $2^{53}$(= 9007199254740992)까지만 정수를 정확히 표현한다. 그보다 큰 값에서는 `over / 10` 이 이미 원래 값을 잃는다.

```pyrepl
>>> import math
>>> over = 10**18 + 1
>>> math.ceil(over / 10)
100000000000000000
>>> -(-over // 10)
100000000000000001
>>> over / 10          # 나누기 전에 이미 뭉개졌다
1e+17
```

`math.ceil` 은 1을 덜 세었다. 주차 요금에서 이만한 수가 나올 일은 없지만, 좌표 압축이나 큰 수 계산에서는 나온다. **정수만 다루는 문제에서는 정수만 쓰는 편이 안전하다.**
:::

### 문제 3 — 신호 세 개를 도구 세 개로

::: answer 문제 3 기준 해답
```python title="loans.py"
from collections import Counter


def top_books(records, k):
    pairs = {tuple(r.split(",")) for r in records}            # 중복 제거
    counts = Counter(book for _member, book in pairs)         # 빈도
    ranked = sorted(counts, key=lambda code: (-counts[code], code))  # 다중 기준 정렬
    return ranked[:k]


records = ["U01,B100", "U02,B100", "U01,B100",
           "U03,B200", "U02,B200", "U01,B300"]
print(top_books(records, 2))
print(top_books(records, 3))
print(top_books(records, 10))
print(top_books([], 3))
```

```text nolines
['B100', 'B200']
['B100', 'B200', 'B300']
['B100', 'B200', 'B300']
[]
```

본문 4줄이다. 문제 문장의 세 요구가 코드 세 줄에 일대일로 대응한다.
:::

문제 문장에는 도구를 가리키는 단어가 그대로 들어 있었다.

| 문장 | 신호 | 도구 |
| --- | --- | --- |
| "같은 회원이 같은 책을 여러 번 빌린 것은 1회" | 중복 제거 | `set` |
| "대출 횟수가 많은 순으로" | 빈도 | `Counter` |
| "횟수가 같으면 도서코드 사전순" | 다중 기준 | `sorted(key=튜플)` |

이 대응을 **읽는 즉시** 떠올릴 수 있는가가 유창함이다. 몰라서 못 하는 게 아니라, 알지만 **문장과 도구가 아직 연결돼 있지 않아서** 못 한다. 그 연결을 만드는 것이 [11.2 표준 라이브러리 무기고](#/stdlib-arsenal)와 [11.5 딕셔너리와 집합](#/dict-set-patterns)의 목적이다.

중간 상태를 REPL에서 눈으로 확인하는 습관도 여기서 든다.

```pyrepl
>>> from collections import Counter
>>> records = ["U01,B100", "U02,B100", "U01,B100", "U03,B200"]
>>> pairs = {tuple(r.split(",")) for r in records}
>>> len(pairs)
3
>>> counts = Counter(book for _member, book in pairs)
>>> sorted(counts.items())
[('B100', 2), ('B200', 1)]
>>> sorted(counts, key=lambda code: (-counts[code], code))
['B100', 'B200']
```

::: tip 조건 하나가 바뀌면 무엇이 바뀌는가
- 중복을 세는 것으로 바뀌면 → `set` 을 빼고 `Counter(r.split(",")[1] for r in records)`.
- 동점일 때 사전 **역순**이면 → 두 기준이 모두 내림차순이니 `sorted(counts, key=lambda c: (counts[c], c), reverse=True)` 한 번으로 끝난다. 함정은 **두 기준의 방향이 엇갈릴 때**다. 문자열에는 음수를 못 붙이니, 그때는 `sorted` 를 두 번 겹치거나 `(-counts[c], c)` 처럼 뒤집을 수 있는 쪽만 음수로 만들어야 한다. 이 함정은 [11.6 정렬을 무기로](#/sorting-as-tool)에서 제대로 다룬다.
- 상위 `k`개만 필요하고 `k` 가 아주 작으면 → 전체 정렬 대신 `heapq.nlargest`. 판단 기준은 [11.2](#/stdlib-arsenal)에.
:::

## 지식과 유창함은 서로 다른 능력이다

이 파트 전체를 관통하는 진단은 한 문장이다.

> **당신에게 부족한 것은 알고리즘 지식이 아니라 유창함이다.**

둘은 뇌에서 하는 일이 다르다. 지식은 **알아보는 능력**이고, 유창함은 **만들어 내는 능력**이다. 남의 풀이를 읽고 "아 그렇지"가 되는 것과, 백지에서 그 풀이가 나오는 것은 별개의 기술이다.

::: note 두 능력의 차이
| | 지식 | 유창함 |
| --- | --- | --- |
| 하는 일 | 알아본다(recognition) | 만들어 낸다(production) |
| 확인 방법 | 해설을 읽고 이해된다 | 백지에서 15분 안에 나온다 |
| 늘리는 방법 | 읽기, 강의 | **직접 쓰기, 그리고 복기** |
| 늘어나는 속도 | 하루면 개념 하나 | 반복 횟수에 비례 |
| 이 책에서 | Part I~X | **Part XI~XII** |

외국어에 비유하면 정확하다. 독해는 되는데 말은 안 나오는 상태가 딱 이것이다. 단어를 더 외워도 말은 안 나온다. 말을 해 봐야 나온다.
:::

::: warn 세그먼트 트리를 공부해도 이 3문제는 못 푼다
막히면 더 어려운 걸 공부하고 싶어진다. [7.25 세그먼트 트리](#/segment-tree)를 파고, [7.21 DP 심화](#/dp-advanced)를 다시 읽는다. 기분은 좋아지지만 위 3문제는 여전히 못 푼다. **셋 중 어느 것도 세그먼트 트리가 필요 없기 때문**이다.

Part VII은 필요하다. 다만 **그건 다른 병에 듣는 약**이다. 유형이 보이는데 코드가 안 나오면 유창함 문제고, 코드는 나오는데 시간 초과가 나면 그때가 Part VII과 [8.3 시간 초과를 피하는 관용구](#/tle)의 차례다. 자기 증상을 먼저 확인해라.
:::

### 손이 멈추는 지점은 네 곳뿐이다

문제를 읽고 제출하기까지의 과정을 넷으로 쪼개면, 자기가 어디서 멈추는지 매번 같다는 걸 알게 된다.

```text nolines
  ┌──────────────┐
  │ 1. TRANSLATE │  문제 문장 -> 내 말로 다시 쓰기
  └──────┬───────┘  막히면: 문제를 끝까지 안 읽은 것이다
         │
         ▼
  ┌──────────────┐
  │ 2. CHOOSE    │  무엇을 세고 무엇을 찾는가 -> 자료구조
  └──────┬───────┘  막히면: 무기고가 비었다 (11.2, 11.5)
         │
         ▼
  ┌──────────────┐
  │ 3. SKELETON  │  함수 이름, 인자, 반환 타입을 먼저 적는다
  └──────┬───────┘  막히면: 완결된 프로그램을 짜 본 적이 없다 (11.7)
         │
         ▼
  ┌──────────────┐
  │ 4. VERIFY    │  예시를 손으로 굴려 맞춰 본다
  └──────────────┘  막히면: 제출은 하는데 계속 틀린다 (11.14)
```

대부분의 사람은 네 지점 중 **하나에서만** 반복해서 막힌다. 그런데 진단 없이 무작정 문제 수를 늘리면 나머지 세 단계만 계속 연습하게 된다. 그래서 200문제를 풀어도 같은 자리에서 막힌다. **막힌 지점을 매번 기록해라.** 그것만 해도 훈련 효율이 달라진다.

## 읽기로는 안 생긴다

이건 취향 문제가 아니라 이 파트의 설계 원칙이다.

::: danger 해답을 먼저 보는 습관이 가장 비싸다
해답을 보면 "이해된다". 그 이해는 진짜다. 문제는 **그 이해가 다음 백지 앞에서 재현되지 않는다**는 것이다. 알아보기(recognition)만 강화되고 만들어 내기(production)는 전혀 훈련되지 않기 때문이다.

가장 흔한 실패 경로가 이것이다.

1. 문제를 5분 본다 → 안 풀린다 → 해답을 본다 → "쉽네" → 다음 문제.
2. 이걸 100번 반복한다.
3. 시험장에서 여전히 첫 줄이 안 나온다.

규칙 하나만 지켜라. **정해진 시간을 다 쓰기 전에는 해답을 보지 않는다.** 그리고 **해답을 본 문제는 그날로 끝이 아니다.** 반드시 다시 백지에서 푼다.
:::

### 무식한 방법으로라도 완성해라

시간이 다 돼 가는데 좋은 방법이 안 떠오르면, **일단 되는 대로 짜서 끝내라.** 미완성 최적해보다 완성된 무식한 풀이가 낫다. 동작하는 코드가 있으면 거기서부터 고칠 수 있지만, 백지에서는 고칠 것도 없다.

다만 무식한 방법의 값은 알고 있어야 한다. 문제 3의 빈도 세기를 도구 없이 짜면 이렇게 된다.

```python title="같은 빈도 세기, 도구 없이"
def count_naive(data):
    result = {}
    for x in set(data):        # 항목마다 전체를 다시 훑는다 -> O(n*d)
        result[x] = data.count(x)
    return result
```

::: perf 무식한 방법의 실제 값
같은 결과를 내는 두 코드의 실행 시간이다. 입력은 문제 3과 같은 도서코드 꼴로 만들었다.

```python title="측정 입력 (n, d 는 표의 값)"
import random

codes = [f"B{i:04d}" for i in range(d)]          # 서로 다른 값 d종
data = [random.choice(codes) for _ in range(n)]  # 길이 n
```

| 입력 | `data.count` 반복 | `Counter(data)` | 배수 |
| --- | --- | --- | --- |
| n=1,000 / d=100 | 1.90~1.96 ms | 0.038~0.039 ms | 49~51배 |
| n=50,000 / d=1,000 | 962~980 ms | 1.94~2.04 ms | 470~500배 |

(Python 3.14.0rc2 / Linux 기준, `timeit.repeat` 최소값을 3패스 재측정한 범위. 절대값은 기기마다 다르고 배수는 값의 자료형에 따라 흔들리지만 — 정수 데이터로 바꾸면 5만 개에서 450배 근처로 내려간다 — 자릿수 차이는 어디서나 같다.)

읽어야 할 것은 배수가 아니라 **절대 시간**이다. 입력이 1,000개면 무식한 방법도 2밀리초 안쪽이라 아무도 눈치채지 못한다. 5만 개가 되면 1초에 가까워지고, 이게 테스트 케이스마다 반복되면 시간 초과다.

그래서 판단은 이렇게 한다. **"입력 크기가 명시돼 있는가"** 를 먼저 보고, 작으면 무식하게 완성부터 하고, 크면 처음부터 도구를 쓴다. 자료구조별 실제 비용은 [7.2 파이썬 자료구조의 실제 비용](#/py-ds-cost)에 정리돼 있다.
:::

줄 수도 같이 보라. 위 문제 3에서 `set`·`Counter`·`sorted` 를 쓴 풀이는 본문 4줄이다. 같은 동작을 리스트와 이중 루프로만 짜면 — 중복 제거를 리스트 탐색으로, 빈도를 두 개의 병렬 리스트로, 정렬을 선택 정렬로 — 최대한 압축해도 본문 20줄 남짓이 된다. 동점 비교를 읽히게 두 줄로 쪼개면 23줄이다. 늘어난 줄 수만큼 실수할 자리도 늘어난다. **유창함은 결국 실수할 자리를 줄이는 일이다.** (직접 짜서 줄 수를 세어 보는 것이 아래 연습문제 4번이다.)

## 훈련을 어떻게 설계하는가

여기부터는 구체적인 실행 계획이다. 애매하게 "많이 풀어라"로 두면 안 한다.

### 하루 분량

**하루 2문제, 60~75분.** 새 문제 1개와 예전 문제 복기 1개다.

- 새 문제: easy 15분, medium 30분. **타이머를 켠다.**
- 시간이 다 되면 손을 뗀다. 해답을 보고, 아래 복기 노트를 쓴다.
- 복기 문제: 48시간 전에 못 풀었던 문제를 **백지에서 다시** 푼다. 답을 기억해도 상관없다. 손이 그 순서를 다시 내는 것이 목적이다.

문제 수를 늘리는 것보다 **재시도가 중요하다.** 못 푼 문제를 그냥 넘기면 그 문제는 영원히 못 푸는 문제로 남는다.

::: tip 복기 노트 — 다섯 줄이면 충분하다
길게 쓰면 안 쓴다. 이 다섯 줄만 채워라.

```text nolines
[날짜] [문제 이름] [유형: 문자열/격자/해시/정렬/기타]
1. 막힌 단계:      TRANSLATE / CHOOSE / SKELETON / VERIFY 중 하나
2. 결정적 한 줄:   이걸 알았으면 바로 풀렸을 표현 (예: sorted(key=lambda x: (-a, b)))
3. 내 줄 수 / 기준 해답 줄 수:
4. 재시도 예정일:  (오늘 + 2일)
```

2주치가 쌓이면 1번 항목의 분포가 보인다. **한 단계에 몰려 있을 것이다.** 그 단계에 해당하는 절만 다시 읽고, 그 단계만 골라 훈련해라. 이게 이 노트를 쓰는 유일한 이유다.
:::

이 파트의 절 순서는 그대로 4주 훈련 계획이다.

| 2주 | [11.4](#/array-grid) | [11.10 격자 드릴](#/drill-grid) | 슬라이싱·방향 벡터가 손에서 나온다 |
| 3주 | [11.5](#/dict-set-patterns), [11.6](#/sorting-as-tool) | [11.11 해시 드릴](#/drill-hash) | 정렬 키를 설계할 수 있다 |

그다음이 [11.13 라이브 코딩](#/live-coding)과 [11.14 시험장 디버깅](#/exam-debug)이다. 실제 시험 유형이 정해져 있다면 [8.1 코딩테스트의 구조와 전략](#/cote-strategy)과 [8.4 문제 유형 분류와 신호 읽기](#/problem-signals)를 병행해라.

::: cote 시험장에서의 자가 진단
시험 중에 손이 멈추면 아래를 **순서대로** 30초씩만 시도해라. 30분을 태우는 것보다 낫다.

1. 문제를 **내 말로 한 문장으로** 다시 쓴다. 안 되면 문제를 다 안 읽은 것이다. 다시 읽어라.
2. "무엇을 **세는가**, 무엇을 **찾는가**, 무엇을 **순서 지어야** 하는가" 셋 중 어디에 해당하는지 고른다. 각각 `Counter`, `set`/`dict`, `sorted` 로 간다.
3. 함수 이름과 반환 타입을 **먼저** 적는다. `def solve(...) -> list[int]:` 한 줄이면 나머지가 따라 나온다.
4. 그래도 안 되면 **입력을 최소로 줄여** 손으로 답을 낸다. 손으로 한 절차가 곧 코드다.
5. 여기까지 해도 안 되면 넘어간다. 시험에서 가장 비싼 실수는 한 문제에 매달리는 것이다.
:::

### 이 파트가 기존 파트와 겹치지 않는 이유

같은 도구가 여러 곳에 나오지만 다루는 각도가 다르다.

- [1.6 dict](#/dict), [1.7 set](#/sets)은 **해시 테이블이 어떻게 동작하는가**.
- [7.2](#/py-ds-cost), [7.6 해시](#/hashing)는 **비용이 얼마인가**.
- [11.2](#/stdlib-arsenal), [11.5](#/dict-set-patterns)는 **문제 문장의 어떤 단어를 보면 이걸 꺼내는가**.

앞의 둘을 다 읽어도 셋째는 안 생긴다. 반대도 마찬가지다. 그래서 이 파트가 따로 있다.

## 요약

- 백지에서 손이 안 움직이는 원인은 알고리즘 지식이 아니라 **유창함**이다. 알아보는 능력과 만들어 내는 능력은 서로 다른 기술이다.
- 자가 진단 3문제에는 알고리즘이 없다. 그런데도 막힌다면 [Part VII](#/complexity)을 더 파는 것은 잘못된 처방이다.
- 손이 멈추는 지점은 **번역 / 도구 선택 / 골격 / 검증** 네 곳뿐이고, 사람마다 막히는 곳은 거의 고정돼 있다. 그것부터 기록해라.
- 문제 문장의 단어가 도구를 가리킨다. "여러 번을 1회로" → `set`, "많은 순으로" → `Counter`, "같으면 사전순" → `sorted(key=튜플)`.
- 단위가 섞이면 **가장 작은 단위 하나로 정규화**한다. 시각은 분으로. 이 한 걸음이 문제를 반으로 줄인다.
- 무식한 방법도 완성이면 정답이다. 다만 입력 5만 개에서 `Counter` 대신 `count` 를 반복하면 400배 이상 느리다(실측 470~500배). 입력 크기를 먼저 보고 결정해라.
- 훈련은 **하루 2문제 + 타이머 + 48시간 뒤 재시도 + 다섯 줄 복기 노트**다. 읽기로는 절대 생기지 않는다.

::: quiz 연습문제 — 전부 코드를 쓰는 과제다
읽고 답하는 문제가 아니다. 편집기를 열고 실제로 실행해서 확인해라.

1. **위 자가 진단 3문제를 다시, 기준 해답을 덮고 처음부터 짜라.** 시간을 재라. 세 문제 합쳐 10분 안에 끝나야 한다. 안 되면 이 절을 덮고 이틀 뒤에 다시 하라.

2. **문제 2를 확장하라.** 다음 두 규칙을 추가한 `parking_fee_v2(enter, leave)` 를 쓰라.
   - 하루 요금 상한은 20000원이다. 계산 결과가 그보다 크면 20000원.
   - 출차 시각이 입차 시각보다 이르면 자정을 넘긴 것으로 보고 24시간을 더한다.
   `("23:30", "00:20") -> 2000`, `("06:00", "23:59") -> 20000` 이 나오는지 확인해라.
   **상한 검사를 어느 줄에 넣어야 하는지**가 이 문제의 핵심이다.

3. **문제 3을 뒤집어라.** 같은 `records` 를 받아 **회원별로 가장 많이 빌린 도서코드**를 담은 딕셔너리를 반환하는 `favorite_by_member(records) -> dict[str, str]` 를 쓰라. 동점이면 도서코드 사전순. **여기서는 문제 3의 중복 제거 규칙을 적용하지 않는다** — 같은 회원이 같은 책을 두 번 빌리면 2회로 센다. 위 예시 입력에서 결과가 `{'U01': 'B100', 'U02': 'B100', 'U03': 'B200'}` 인지 확인해라.
   (힌트가 필요하면 아직 이 문제를 풀 때가 아니다. [11.5](#/dict-set-patterns)를 먼저 읽어라.)

4. **같은 문제를 두 번 짜라.** 문제 3을 (a) 표준 라이브러리 없이 리스트와 반복문만으로, (b) `set`·`Counter`·`sorted` 로 각각 구현하고, 두 결과가 무작위 입력 1000개에 대해 항상 같은지 `assert` 로 대조하라. 그리고 **두 코드의 본문 줄 수를 세어 적어라.**

5. **자기 문제를 만들어라.** 엘리베이터, 재고 관리, 좌석 예약 중 하나를 골라 **입출력 예시 3개가 붙은 easy 문제**를 직접 쓰고, 그것을 15분 타이머로 풀어라. 문제를 만드는 동안 "이건 무엇을 세는 문제인가"를 스스로 정해야 하는데, 그게 이 절 전체의 훈련이다.
:::
