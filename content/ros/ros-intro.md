## 로봇 소프트웨어에 표준이 필요한 이유

로봇 하나를 움직이는 데 필요한 소프트웨어를 나열해 보자. 카메라 드라이버, 라이다 드라이버, 모터 제어기, 배터리 모니터, 경로 계획기, 장애물 회피, 사용자 인터페이스. 이 조각들은 보통 서로 다른 팀이, 서로 다른 언어로, 서로 다른 시점에 짠다. 그런데 전부 한 로봇 안에서 실시간으로 데이터를 주고받아야 한다.

표준이 없으면 무슨 일이 생기는지는 상상하기 쉽다. 라이다 드라이버 팀이 자체 프로토콜로 포인트클라우드를 내보내고, 경로 계획 팀이 그 포맷을 몰라서 다시 파서를 짜고, 회사가 라이다 기종을 바꾸면 그 파서가 전부 무용지물이 된다. **각 조각을 재사용 가능하게 만들려면, 조각들 사이의 통신 방식과 데이터 형식이 회사·프로젝트를 넘어 똑같아야 한다.** 이게 표준화의 핵심 동기다.

ROS(Robot Operating System)는 정확히 이 문제를 풀려고 만들어졌다. 이름과 달리 운영체제가 아니다. 프로세스 사이의 통신 규약(발행-구독, 요청-응답)과 그 위에 얹힌 도구 모음(빌드 시스템, 시각화, 로그 기록/재생)이다. 라이다 드라이버가 `sensor_msgs/msg/LaserScan`이라는 표준 메시지 타입으로 데이터를 내보내면, 어떤 회사의 어떤 경로 계획 패키지든 그 타입만 알면 바로 갖다 쓸 수 있다. 이게 로봇 업계가 ROS를 사실상 공용어로 받아들인 이유다.

::: note ROS 1의 성공은 실제로 있었다
ROS 1(2007년~)은 연구실 로봇 생태계를 완전히 바꿔 놓았다. PR2 로봇 프로젝트에서 시작해서, 대학·연구소가 서로의 코드를 그대로 재사용할 수 있게 만들었다. 이 절에서 ROS 1의 한계를 이야기하는 것은 ROS 1이 실패해서가 아니라, **연구용으로 짠 설계가 상용 배포 단계에서 부딪힌 구체적인 벽**을 짚기 위해서다.
:::

## ROS 1의 한계: 왜 다시 설계해야 했나

ROS 1의 아키텍처는 처음부터 하나의 전제를 깔고 있었다. **연구실 안, 하나의 로봇, 안정적인 네트워크.** 이 전제가 깨지는 순간 세 가지 벽이 드러난다.

### 단일 마스터라는 단일 장애점

ROS 1의 모든 노드는 `roscore`라는 프로세스 하나에 등록한다. 노드 A가 토픽을 발행하고 싶으면 먼저 마스터에게 "나 이 토픽 발행한다"고 알리고, 노드 B가 구독하고 싶으면 마스터에게 "이 토픽 구독자가 누구냐"고 물어서 A의 주소를 받은 뒤에야 A와 직접 연결한다.

```text nolines
                    roscore (master)
                   ┌────────────────┐
                   │ name -> address │
                   └────────────────┘
                     ▲            ▲
                register      register
                     │            │
                ┌────────┐   ┌────────┐
                │ Node A │   │ Node B │
                └────────┘   └────────┘

   Node A ──────────── direct data ────────────▶ Node B
```

`Node A`, `Node B`가 각각 마스터에 등록·조회한 뒤에는, 실제 데이터는 마스터를 거치지 않고 두 노드가 직접 주고받는다.

일단 연결되면 데이터는 마스터를 거치지 않고 A와 B가 직접 주고받는다. 그런데 **연결을 맺는 단계, 즉 "누가 누구인지 알아내는" 단계가 마스터 하나에 몰려 있다.** `roscore`가 죽으면 이미 연결된 노드들은 잠깐 살아남지만, 새로 뜨는 노드는 아무도 찾을 수 없다. 로봇 두 대가 서로를 알아야 하는 다중 로봇 시스템에서는 이 구조가 특히 어색해진다. 마스터를 어느 로봇에 둘지, 마스터가 죽으면 어떻게 할지에 대한 표준 답이 ROS 1에는 없었다.

### 실시간성을 보장할 수 없는 전송 계층

ROS 1의 기본 전송(TCPROS)은 TCP 위에 얹은 자체 포맷이다. TCP는 안정적이지만 **패킷 손실 시 재전송을 기다리느라 지연이 얼마나 늘어날지 예측할 수 없다.** 로봇 제어 루프처럼 "이번 주기 안에 반드시 도착해야 하는" 데이터에는 안 맞는 특성이다. ROS 1에는 이걸 조정할 표준화된 방법, 즉 "이 토픽은 최신 값만 중요하니 손실을 감수하고 빠르게, 저 토픽은 하나도 빠짐없이 안전하게" 같은 설정 체계가 없었다. 전송 신뢰성이 애초에 선택 사항이 아니었다.

### 보안이 설계에 없었다

ROS 1은 인증도 암호화도 없다. 같은 네트워크에 있는 아무나 `roscore`에 접속해서 토픽을 엿듣거나, 가짜 메시지를 발행하거나, 로봇에게 임의의 명령을 내릴 수 있다. 연구실 안 폐쇄망에서는 문제가 안 됐지만, 공장·물류창고·공공장소에 배치되는 로봇에서는 치명적이다. 보안을 나중에 덧붙이려면 통신 계층 전체를 다시 설계해야 하는데, ROS 1의 커스텀 프로토콜에는 그럴 여지가 없었다.

::: hist 왜 처음부터 이렇게 짜지 않았나
ROS 1은 2007년 PR2라는 특정 연구용 로봇을 위해 만들어졌다. 그 시점의 목표는 "대학원생이 최대한 빨리 로봇 실험을 돌릴 수 있게"였지 "공장에 수백 대를 배치했을 때 안전하게"가 아니었다. 요구사항이 바뀐 뒤에 기존 아키텍처를 억지로 늘리기보다, 처음부터 새 요구사항(다중 로봇, 실시간, 보안, 임베디드)을 전제로 다시 설계한 것이 ROS 2다.
:::

## ROS 2의 해법: 바퀴를 다시 발명하지 않는다

ROS 2 설계팀이 내린 핵심 결정은 이거다. **통신 계층을 직접 짜지 말고, 이미 검증된 산업 표준 위에 올라타자.** 그 표준이 **DDS**(Data Distribution Service)다.

DDS는 로봇과 무관하게 존재해 온 실시간 분산 시스템 표준이다. 금융 거래 시스템, 항공 관제, 국방 시스템에서 수십 년 검증된 발행-구독 미들웨어다. ROS 2는 이 DDS 표준 위에 로봇 친화적인 API(`rclpy`, `rclcpp`)를 얹었다.

```text nolines
        rclpy / rclcpp                <- 당신이 짜는 코드 (10.3절부터)
             │
             ▼
            rcl                       <- 언어 중립 공통 로직
             │
             ▼
            rmw                       <- DDS 미들웨어 추상화 계층
             │
             ▼
     DDS 구현체 (Fast DDS, Cyclone DDS, ...)   <- 실제 통신
```

이 그림은 [10.16 다음 단계: C++로](#/ros-next)에서 rclpy와 rclcpp의 관계를 설명할 때 다시 정확히 이 형태로 나온다. 지금은 맨 아래 층만 기억하면 된다 — **거기가 DDS다.**

### 마스터가 사라진다

DDS는 **동적 발견**(dynamic discovery)을 표준 기능으로 제공한다. 각 노드가 네트워크에 자신을 알리는 멀티캐스트 신호를 주기적으로 내보내고, 다른 노드들이 그걸 듣고 서로를 찾는다. 중앙 등록소가 없다. `roscore`에 해당하는 프로세스 자체가 ROS 2에는 없다.

```text nolines
   Node A ◀──────── discovery announcements ────────▶ Node B
      ▲                                                 ▲
      └──────────────── mutual discovery ───────────────┘

           (no central master in the middle)
```

두 노드가 서로 발견 신호를 주고받으며 상대를 직접 찾는다. 중앙에 있던 마스터가 없다.

노드 하나가 죽어도 나머지는 서로를 계속 찾고 통신한다. 단일 장애점이 구조적으로 사라진 것이다. 대신 대가도 있다 — 발견 트래픽 자체가 네트워크 부하를 만들고, 노드 수가 많아지면 이 발견 트래픽이 체감될 만큼 커진다. 이건 [10.8 QoS와 DDS](#/qos)에서 설정으로 조정하는 법을 다룬다.

### 신뢰성은 정책으로 선택한다

DDS는 **QoS**(Quality of Service) 정책이라는 개념을 제공한다. 토픽마다 "손실을 감수하고 최신 값만 빠르게 받을지" 아니면 "느려도 하나도 안 놓치고 받을지"를 명시적으로 선택할 수 있다. 라이다 스캔처럼 다음 프레임이 곧 오는 데이터는 전자, 로봇의 목표 지점 명령처럼 한 번 놓치면 안 되는 데이터는 후자를 쓴다. ROS 1에는 이런 선택지 자체가 없었다 — 있었다면 전송 계층 전체를 다시 짜야 했을 것이다. 자세한 내용은 [10.8 QoS와 DDS](#/qos)에서 다룬다.

### 보안은 표준의 일부로 온다

DDS 진영에는 **DDS-Security**라는 별도 명세가 있고, ROS 2는 이 위에 SROS 2라는 이름으로 인증·암호화·접근 제어를 지원한다. 이 책은 SROS 2를 별도 절로 다루지 않지만, "보안이 설계 밖에 있었다"는 ROS 1의 근본적인 약점이 "이미 검증된 표준의 보안 기능을 그대로 상속한다"는 형태로 해결됐다는 점은 기억해 둘 만하다.

::: deep 메시지가 실제로 어떻게 실려 가는가 — 직렬화의 무게
DDS는 메시지를 네트워크로 보내기 전에 **정해진 이진 포맷**(CDR, Common Data Representation)으로 직렬화한다. `.msg` 파일에 필드 타입을 미리 정확히 선언하기 때문에, 어떤 언어로 짠 노드든 같은 바이트 배열을 같은 방식으로 해석할 수 있다.

이게 왜 중요한지, 파이썬에서 익숙한 두 직렬화 방식을 실제로 비교해서 느껴 보자. `pickle`은 파이썬 객체를 그대로 담아서(타입 정보까지) 직렬화하고, `struct`는 스키마를 미리 정해 놓고 순수 숫자만 이진수로 채운다. DDS의 CDR은 후자에 훨씬 가깝다.

```python title="serialize_check.py — LaserScan 메시지를 흉내낸 비교"
import pickle
import struct


class LaserScan:
    """sensor_msgs/msg/LaserScan 을 단순화한 흉내. 실제 필드는 더 많다."""

    def __init__(self, ranges):
        self.angle_min = -1.57
        self.angle_max = 1.57
        self.ranges = ranges


scan = LaserScan([1.2345] * 360)          # 라이다 한 스캔 = 거리값 360개

pickled = pickle.dumps(scan)
packed = struct.pack(f"<2f{len(scan.ranges)}f", scan.angle_min, scan.angle_max, *scan.ranges)

print("pickle 직렬화:", len(pickled), "바이트")
print("고정 바이너리(struct):", len(packed), "바이트")
```

```text nolines
pickle 직렬화: 3340 바이트
고정 바이너리(struct): 1448 바이트
```

(Python 3.14.5 / Windows 기준 실측. 필드 360개짜리 스캔 하나에서 벌써 **두 배 넘는 차이**가 난다.) `pickle`은 클래스 이름, 속성 이름, 프로토콜 헤더까지 매 메시지마다 함께 보낸다 — 어느 쪽 언어에서 왔는지 몰라도 파이썬 `pickle`이 알아서 복원해 주는 대신, 그 자기 서술 정보 자체가 바이트 비용이다. `struct`는 스키마를 양쪽이 미리 합의했다는 전제로 숫자만 보낸다. 이게 CDR이 하는 일이고, ROS 2 메시지 정의(`.msg` 파일)가 필드 타입을 엄격하게 요구하는 이유다 — **양쪽이 스키마를 미리 알고 있으면, 그 스키마 정보 자체를 매번 보낼 필요가 없다.**

여기에 한 가지가 더 있다. `sensor_msgs/msg/LaserScan`의 `ranges` 필드는 실제로 `float32[]`다. 파이썬의 `float`는 항상 64비트인데, 이걸 32비트로 좁혀 담으면 무슨 일이 생기는지 확인해 보자.

```python title="정밀도 손실 확인"
angle_min, angle_max, *ranges = struct.unpack(f"<2f{len(scan.ranges)}f", packed)
print(ranges[0] == scan.ranges[0])
print(ranges[0], scan.ranges[0])
```

```text nolines
False
1.2345000505447388 1.2345
```

(같은 환경 실측.) 32비트로 좁히는 순간 **이미 값이 달라진다.** 이게 버그가 아니라 **의도된 설계**다. 라이다 거리값은 밀리미터 단위 정밀도가 필요 없는 경우가 대부분이고, 필드 하나당 32비트씩 아끼면 초당 수백 번 나가는 스캔 전체에서 그 절약이 누적된다. [1.2 숫자와 수치 연산](#/numbers)에서 배운 부동소수점 정밀도 이야기가 여기서 실제 대역폭 설계 결정으로 다시 나온다. **메시지 타입을 고를 때 필드 정밀도를 그냥 넘기지 마라. `float32`와 `float64`는 네트워크 위에서 실제 비용이 다르다.**
:::

## 배포판 고르기: LTS냐 최신이냐

ROS 2는 매년 5월 새 **배포판**(distribution)을 낸다. 각 배포판은 특정 Ubuntu LTS 버전과 짝지어지고, 코드명이 붙는다(Humble, Iron, Jazzy, Kilted…). 배포판마다 지원 기간이 다르다.

| 배포판 | 성격 | 지원 기간 |
| --- | --- | --- |
| **Rolling** | 계속 업데이트되는 개발판. 다음 정식 배포판에 들어갈 변경이 여기 먼저 들어온다 | 고정 지원 기간 없음, 계속 굴러감 |
| **일반 배포판** (예: Kilted) | 매년 나오는 정식 배포판 중 LTS가 아닌 것 | 대략 1년 |
| **LTS 배포판** (예: Jazzy Jalisco) | Ubuntu LTS와 짝지어 나오는 장기 지원판 | 여러 해 (Jazzy는 2024년 5월 출시, 2029년 5월까지 지원) |

::: tip 어느 쪽을 고를까
**배우는 중이거나 상용 시스템을 만든다면 LTS를 골라라.** Jazzy처럼 몇 년 단위로 보안 패치와 버그 수정을 받는 배포판이 안정적이다. 이 책의 예시와 API 설명도 최신 LTS 기준으로 쓴다.

**Rolling은 다음 릴리스에 들어갈 새 기능을 미리 써야 하거나, ROS 2 자체를 개발하는 입장일 때만 골라라.** 언제든 하위 호환을 깨는 변경이 들어올 수 있다.

일반 배포판(비-LTS)은 지원 기간이 1년 남짓이라, 그 사이에 다음 LTS로 옮길 계획이 없다면 굳이 고를 이유가 적다.
:::

::: warn 배포판마다 API가 조금씩 다르다
이 책의 rclpy 예시는 최신 LTS(Jazzy 기준)로 검증했다. 오래된 배포판(Foxy, Galactic 등)에서는 일부 API 시그니처나 기본 QoS 설정이 다를 수 있다. **공식 문서를 볼 때는 항상 URL의 배포판 이름(`docs.ros.org/en/<배포판명>/...`)을 확인해라.** 같은 페이지도 배포판마다 내용이 다르다.
:::

## 설치 개요

ROS 2는 리눅스(Ubuntu), Windows, macOS를 지원 등급(Tier)으로 나눠 지원한다. **Tier 1**은 공식 바이너리 패키지가 나오고 CI로 테스트되는 플랫폼이고, 최신 LTS 기준 Ubuntu LTS와 Windows가 여기 속한다. 등급이 낮아질수록 소스에서 직접 빌드해야 하는 부담이 커진다.

```text nolines
   설치 방법                    난이도       권장 대상
   ─────────────────────────────────────────────────
   Ubuntu + apt (Debian 패키지)   낮음        이 책의 기본 전제
   Docker 공식 이미지             낮음        환경을 격리하고 싶을 때
   Windows (바이너리)             중간        .NET/Visual Studio 생태계 연동
   소스에서 직접 빌드              높음        임베디드, 특수 플랫폼, RTOS
```

::: tip 이 책은 리눅스를 전제로 진행한다
Ubuntu는 ROS 2의 1순위 지원 플랫폼이고, 대부분의 튜토리얼·패키지·Gazebo 같은 시뮬레이터 문서가 리눅스를 기준으로 쓰인다. Windows에서도 동작하지만 패키지 가용성이 더 좁고, 문제가 생겼을 때 참고할 사례도 적다. **Windows를 쓰고 있다면 WSL2 위에 Ubuntu를 올리는 방법을 가장 먼저 추천한다.**

설치 명령 자체는 배포판·OS 조합마다 달라서 이 절에 그대로 옮기지 않는다. **`docs.ros.org/en/<배포판명>/Installation.html`** 에서 자신의 OS를 선택해 공식 절차를 그대로 따라가라. 이 문서는 apt 저장소 등록, GPG 키 추가, `ros-<배포판명>-desktop` 패키지 설치 순서로 구성돼 있고, 배포판이 바뀌어도 구조는 거의 그대로다.
:::

::: note 설치가 끝났는지 확인하는 법
공식 설치 절차의 마지막 단계는 항상 환경 설정 스크립트를 셸에 등록하는 것이다(`source /opt/ros/<배포판명>/setup.bash`). 이후 터미널에서 `ros2` 명령이 인식되면 설치가 끝난 것이다. 이 책은 여기서부터, 즉 `ros2` CLI가 이미 동작하는 환경을 전제로 [10.2 워크스페이스](#/ros-workspace)부터 실습을 시작한다.
:::

## 왜 파이썬으로, 그리고 왜 파이썬으로 끝나지 않는가

이 책 대부분이 파이썬이었던 이유는 rclpy가 프로토타이핑에 강하기 때문이다. 노드 하나를 스무 줄로 짜고, 바로 실행해서 확인하고, 고치고 다시 실행하는 반복이 빠르다. [1.10 함수](#/functions)와 [1.12 클래스](#/classes)에서 배운 문법 그대로 노드를 만든다.

그런데 이 책의 마지막 절([10.16](#/ros-next))은 C++을 가리킨다. 로봇의 제어 루프처럼 밀리초 단위 예측 가능성이 필요한 영역에서는 GIL과 가비지 컬렉션이라는, [Part IV 동시성](#/concurrency-map)과 [5.2 메모리 모델](#/memory)에서 이미 배운 그 특성들이 다시 발목을 잡는다. 이 책이 파이썬 언어 자체를 깊이 판 이유가 여기서 갚아진다 — GIL이 뭔지, 참조 카운팅이 뭔지 모르는 사람은 "왜 C++로 옮겨야 하는지"조차 제대로 이해할 수 없다. **이 파트는 파이썬으로 시작해서 그 파이썬을 딛고 다음 언어로 넘어가는 자리에서 끝난다.**

## 요약

- ROS는 로봇 소프트웨어 조각들이 회사·프로젝트를 넘어 재사용되게 만드는 표준 통신 규약과 도구 모음이다.
- ROS 1은 단일 마스터(단일 장애점), 예측 불가능한 전송 지연, 설계에 없는 보안이라는 세 가지 벽에 부딪혔다.
- ROS 2는 이 통신 계층을 산업 표준 DDS 위에 새로 얹었다 — 중앙 마스터 없는 동적 발견, QoS로 조정하는 신뢰성, DDS-Security 기반 보안.
- 메시지는 CDR이라는 고정 이진 포맷으로 직렬화된다. `float32`처럼 필드 정밀도를 좁히는 선택은 버그가 아니라 대역폭 설계다 — 실측으로 확인했다.
- 배포판은 LTS(Jazzy 등, 여러 해 지원)와 일반 배포판(약 1년), Rolling(계속 개발 중)으로 나뉜다. 학습·상용은 LTS를 골라라.
- 설치는 리눅스(Ubuntu) Tier 1 플랫폼이 가장 안정적이다. 정확한 명령은 `docs.ros.org/en/<배포판명>/Installation.html`을 그대로 따라가라.
- 이 파트는 16개 절로 기반 → 통신 → 설정/진단 → 공간/시뮬레이션 → 인지/자율성 → 실전 감각 → C++로의 전환 순서로 진행되고, 이 책 전체의 종착점이다.
